# Code Review

## 목적

코드 변경사항을 검증하고 이슈 목록을 산출한다.

**수정은 하지 않는다**: 이슈 목록만 반환하고, 수정 여부와 방법은 호출자가 결정한다.

## 입력

| 입력 | 필수 | 설명 |
|------|------|------|
| **리뷰 대상** | O | PR diff, 커밋, 파일 |
| **coding-standards 목록** (`--coding-standards`) | X | 기준 문서로 읽는다. 모드마다 쓰임이 달라 [1단계 표](#1-컨텍스트-준비)가 정한다 |
| **결정 기록** | X | 사용자 결정이 적힌 파일 경로 |
| **리뷰 모드** (`--mode`) | X | advanced / only-standards (기본: advanced) |

## 출력

맨 앞에 리뷰어가 실제로 Read한 기준 문서 경로 목록, 그 아래에 로드한 외부 스킬 목록, 그 뒤에 이슈 목록. severity (Critical / Minor / Suggestion) 포함.
"기준 문서와 충돌"로 낸 이슈, "사용자 결정이라 다름"으로 뺀 차이, "확인 안 함"으로 올린 가설, "재현 안 됨"으로 기각한 가설(재현 근거와 함께)은 이슈 목록과 따로 싣는다.

---

## 절차

### 1. 컨텍스트 준비

리뷰어를 띄우는 쪽은 기준 문서를 선택해 넘기지 않는다.

호출 프롬프트에 적힌 리뷰 초점·판정 기준·문서 목록은 1단계 2번을 좁히지 못한다. 예외는 아래 표의 only-standards뿐이다.

| 모드 | 기준 문서 |
|---|---|
| advanced | 1단계 2번대로 선택한 문서와 넘어온 문서(호출 프롬프트에 적힌 문서, `--coding-standards` 목록) |
| only-standards | `--coding-standards`가 넘어오면 1단계 2번으로 고르지 않고 그 목록과 호출 프롬프트에 적힌 문서를 읽는다(마이그레이션 의도 보존). 넘어오지 않으면 advanced와 같다 |

"호출 프롬프트에 적힌 문서"에서 Advanced Reviewer 참고 자료([3단계](#3-리뷰-수행))로 넘긴 것은 뺀다.

1. 호출 입력에 **리뷰 대상**이 명시돼 있지 않으면, 추정한 대상을 내보이고 사용자에게 확인받은 뒤 진행한다
2. **리뷰어가** [code-map.md 기준 문서 고르기](../../contexts/code-map.md#기준-문서-고르기)대로 기준 문서를 선택한다

### 2. 리뷰 대상 파악

메인은 PR 본문(description)·커밋 히스토리·diff를 직접 읽어 변경 의도를 파악한다. PR 코멘트·리뷰 스레드는 조회하지 않는다.

인접 테스트는 메인이 읽지 않는다. advanced 모드에서 메인은 일회성 서브에이전트(sonnet) 하나에 리뷰 대상과 diff의 변경 파일 목록을 넘긴다.
그 서브에이전트는 리뷰 대상 구현 파일과 같은 디렉토리·인접 경로의 테스트 파일(`*.test.ts`, `*.test.tsx`)과 그 짝 구현 파일의 경로 목록만 반환한다.
메인은 그 목록을 Advanced Reviewer 프롬프트에 그대로 넣고, 그 리뷰어는 요청에 테스트가 없어도 그 파일들을 리뷰 범위에 넣고, 그 파일들에서는 변경된 구현을 얼마나 검증하는지만 본다.

| 모드 | 리뷰 범위 | 외부 스킬 |
|---|---|---|
| advanced | 작성자가 실제로 수정한 코드 | [external-skills.md](external-skills.md)대로 선택한다 |
| only-standards | 리뷰 대상으로 지정한 기존 파일 전체. 리뷰 대상 diff는 빈 트리 대비 diff(`git diff 4b825dc642cb6eb9a060e54bf8d69288fbee4904 -- <파일...>`)다 | 고르지 않는다 |

결정 기록이 넘어오면 [decision-record.md](decision-record.md)대로 발췌해 리뷰어에게 넘긴다.

### 3. 리뷰 수행

메인이 모드에 따라 아래 리뷰어를 띄운다. diff가 작아도 메인이 기준 문서를 직접 읽어 대조하지 않는다. 대조는 리뷰어가 한다.

| 모드 | 리뷰어 |
|---|---|
| only-standards | 단일 리뷰어(sonnet) 1명이 기준 문서 대조만 한다. 기존 코드를 새 규칙에 맞추는 마이그레이션이라 자유 리뷰가 끼면 범위가 흐려진다 |
| advanced | 아래 표의 리뷰어를 병렬로 띄우고, 메인이 결과를 합치며 중복을 걷는다. 메인이 다시 말을 걸 리뷰어(기준 문서를 대조해 아래 충돌을 되물을 리뷰어, 호출자가 재검까지 같은 리뷰어에게 맡기라고 한 리뷰어)는 [team-agent](../../contexts/team-agent.md#claude-code)의 규칙대로 띄우고, 나머지는 `name` 없이 띄운다. 호출자가 맡긴 리뷰어가 앞 호출에서 이미 떠 있으면 새로 띄우지 않고 그 리뷰어에게 보낸다 |

| advanced 리뷰어 | 맡는 일 |
|---|---|
| Coding-Standards Reviewer ×N (sonnet) | [code-map.md 기준 문서 고르기](../../contexts/code-map.md#기준-문서-고르기)가 훑는 폴더 중 `rules/`와 MP 베스트 프랙티스를 영역으로 나눠 1명씩 맡는다. 메인은 영역만 정하고, 리뷰어가 자기 영역 안에서 code-map의 기준 문서 고르기대로 문서를 선택한다 |
| External-Skill Reviewer ×M (sonnet) | 2단계에서 선택한 외부 스킬마다 1명(없으면 0명). 그 스킬 관점으로만 본다 |
| Official-Way Reviewer (opus) | diff가 직접 구현한 것(다른 목적의 도구를 끌어다 쓴 것 포함)마다 같은 목적의 공식 수단(레포에 설치된 도구, 프레임워크·플랫폼 내장 API, 생태계 표준 라이브러리)이 있는지 공식 문서로 확인한다. 있으면 diff와 비교한 이슈에 공식 문서 URL과 그 페이지 원문을 붙인다. 기준 문서는 고르지 않는다 |
| Advanced Reviewer (opus) | 규칙에 없는 문제를 자유 리뷰로 짚고, `principles/`는 code-map의 기준 문서 고르기대로 선택한다. 메인은 짚을 주제·관점과 호출 프롬프트가 이 리뷰어에게 주라고 넘긴 참고 자료를 넘길 수 있고, 다른 리뷰어에게 맡긴 관점은 빼고 보라고 지시문에 적어 넘긴다 |

메인은 모든 리뷰어 지시문에 `{{skill_dir}}/reviewer-common.md` 경로를 넣고 Read로 읽어 그대로 따르게 한다. 리뷰어는 이 SKILL.md를 읽지 않아, 지시문에 없는 규칙은 리뷰어에게 닿지 않는다.
기준 문서를 대조하는 리뷰어의 지시문에는 넘어온 문서([1단계 표](#1-컨텍스트-준비)) 경로도 넣는다. 선택할 영역도 적는다.
- Coding-Standards Reviewer: 메인이 정한 영역
- Advanced Reviewer: `principles/`
- only-standards 리뷰어: `--coding-standards`가 넘어왔으면 "고르지 않는다", 아니면 code-map이 훑는 폴더 전체

Coding-Standards Reviewer와 only-standards 리뷰어는 [reviewer-checks.md](reviewer-checks.md)대로 전수 대조한다.
메인은 그 리뷰어마다 `{{skill_dir}}/reviewer-checks.md`와 `<리뷰 대상 diff 명령> | node {{skill_dir}}/scripts/added-comments.mjs` 꼴의 완성 명령도 지시문에 넣는다.

리뷰어가 기준 문서가 아닌 근거로 코드를 바꾸라고 했는데 기준 문서(예시 코드 포함)는 지금 코드를 권하거나 그 변경을 금지하면, 이슈 목록과 따로 "기준 문서와 충돌"로 묶어 양쪽 근거를 나란히 사용자에게 올린다. 어느 쪽을 따를지는 사용자가 정한다.
advanced 모드에서는 메인이 그런 권고를 기준 문서를 대조한 리뷰어들에게 보내 부딪히는지 묻는다.

### 4. 이슈 목록 산출

메인은 리뷰어가 낸 위험 가설을 아래대로 재현 결과로 채택·기각한다.
위험 가설은 말꼴로 가리지 않고, 리뷰어가 단정하지 않은 지적 전부를 센다. "~할 수 있음"·"확인하지 못함"뿐 아니라, diff 밖 맥락(호출부·부모 레이아웃·페이지 구조)을 몰라 "판단할 수 없음"·"이슈로 확정하지 않음"으로 적은 것도 든다.

- 가설 하나에 일회성 서브에이전트(sonnet) 하나를 띄워, 가설 원문·리뷰어가 짚은 `파일:줄`·리뷰 대상(브랜치나 diff)과 아래 반환 형식·정리 규칙을 넘기고 가설이 맞으면 생길 결과를 재현(테스트·브라우저·최소 앱. diff 밖 맥락을 몰라 낸 가설은 그 코드를 읽어 확인)하게 한다. 재현은 직접 하지 않는다
- 여러 가설을 한 서브에이전트에 묶지 않는다. 한 가설의 재현이 막히면 같이 묶인 가설의 결과까지 그 시행착오에 섞인다
- 서브에이전트에게서는 "재현됨"·"재현 안 됨"·"시도했으나 못 함(무엇을 시도했고 어디서 막혔는지)" 중 하나와, 그 근거(돌린 명령·출력 요약, 코드를 읽어 확인했으면 읽은 `파일:줄`)를 돌려받는다
- 서브에이전트는 재현하려고 띄운 서버·프로세스를 끄고 끝낸다. 남으면 사용자 PC의 메모리를 계속 쓴다
- 결정·범위 해석만으로 기각하지 않는다
- 이슈로 올리지 않을 것 같거나 재현할 수 없어 보이는 가설도 넘긴다. 재현 결과 없이 보류·제외로 돌리면 기각과 같고, "시도했으나 못 함"은 시도한 서브에이전트만 보고한다
- "시도했으나 못 함"이 돌아오면 그 시도·막힌 곳과 "확인 안 함"을 밝혀 사용자에게 올린다
- "재현됨"은 리뷰어가 붙인 severity로 재현 근거와 함께 이슈 목록에 올린다
