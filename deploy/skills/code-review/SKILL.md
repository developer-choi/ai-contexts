# Code Review

## 목적

코드 변경사항을 검증하고 이슈 목록을 산출한다.

**수정은 하지 않는다** — 이슈 목록만 반환하고, 수정 여부와 방법은 호출자가 결정한다.

## 입력

| 입력 | 필수 | 설명 |
|------|------|------|
| **리뷰 대상** | O | PR diff, 커밋, 파일 |
| **coding-standards 목록** (`--coding-standards`) | X | only-standards 모드에서는 1단계 2번 대신 이 목록만 적용한다 (마이그레이션 의도 보존). 다른 모드에서 넘어오면 리뷰어가 고른 문서와 함께 읽는다 |
| **추가 컨벤션** (`--extra-standards`) | X | 리뷰어가 기본으로 읽는 coding-standards·MP 구현 패턴 밖에 있어 AI가 스스로 찾을 수 없는, 이 레포에 적용되는 규칙 (사내 컨벤션 등). 넘어오면 기준 문서를 대조하는 리뷰어 모두의 지시문에 넣는다 |
| **결정 기록** | X | 사용자 결정이 적힌 파일 경로 |
| **리뷰 모드** (`--mode`) | X | default / advanced / only-standards (기본: default) |

## 출력

맨 앞에 리뷰어가 실제로 Read한 기준 문서 경로 목록, 그 아래에 로드한 외부 스킬 목록, 그 뒤에 이슈 목록. severity (Critical / Minor / Suggestion) 포함. 「기준 문서와 충돌」로 낸 이슈, 「사용자 결정이라 다름」으로 뺀 차이, 「확인 안 함」으로 올린 가설은 이슈 목록과 따로 싣는다.

---

## 절차

### 1. 컨텍스트 준비

리뷰어를 띄우는 쪽은 기준 문서를 골라 넘기지 않는다.

호출 프롬프트에 적힌 리뷰 초점·판정 기준·문서 목록은 1단계 2번을 좁히지 못한다(only-standards 모드의 `--coding-standards` 목록만 예외 — [입력](#입력)).

「사용자 결정이라 다름」으로 뺀 차이마다 그 모양이 직접 적힌 결정 기록 줄의 `파일:줄`과 원문을 붙인다. AI 단독 결정 줄과, 제약만 적혀 그 모양을 추론해야 하는 줄은 근거가 아니다.
붙이지 못하면 호출 프롬프트가 빼라고 해도 이슈 목록에 싣는다.

1. 호출 입력에 **리뷰 대상**이 명시돼 있지 않으면, 추정한 대상을 내보이고 사용자에게 확인받은 뒤 진행한다
2. **리뷰어가** [code-map.md 탐색 절차](../../contexts/code-map.md#critical-탐색-절차)의 후보 선별부터 전체 Read까지만 밟아 기준 문서를 고른다
3. 추가 컨벤션은 빠진 입력을 채우려고, 그런 규칙이 있을 법한 레포에서만 묻는다. 호출 입력에 있으면 채워진 것이다(다른 스킬이 비워 넘긴 것 포함). 답은 기다리지 않고, 뒤에 온 문서는 그것만 대조하는 리뷰어를 더 띄워 합친다

### 2. 리뷰 대상 파악

메인은 PR 본문(description)·커밋 히스토리·diff를 직접 읽어 변경 의도를 파악한다. 이 조회에 코멘트·리뷰를 함께 받지 않는다.

인접 테스트는 메인이 읽지 않는다. 메인은 일회성 서브에이전트(sonnet) 하나에 리뷰 대상과 diff의 변경 파일 목록을 넘긴다.
그 서브에이전트는 리뷰 대상 구현 파일과 같은 디렉토리·인접 경로의 테스트 파일(`*.test.ts`, `*.test.tsx`)과 그 짝 구현 파일의 경로 목록만 돌려준다(테스트 본문은 싣지 않는다).
메인은 그 목록을 모든 리뷰어 프롬프트에 그대로 넣고, 리뷰어는 요청에 테스트가 없어도 그 파일들을 리뷰 범위에 넣어 변경된 구현을 얼마나 검증하는지만 본다.

리뷰 대상은 해당 작성자가 실제로 수정한 코드에 한정한다.
only-standards 모드는 예외로, 리뷰 대상으로 지정한 기존 파일 전체를 본다 — 이 모드에서 리뷰 대상 diff는 빈 트리 대비 diff(`git diff 4b825dc642cb6eb9a060e54bf8d69288fbee4904 -- <파일...>`)다.

결정 기록은 메인이 열지 않는다(Read·`cat`·Grep 모두) — 리뷰어 지시문에 들어갈 몇 줄을 얻으려고 기록 전량을 메인 컨텍스트에 남기지 않기 위해서다.
결정 기록 경로와 diff를 일회성 서브에이전트(sonnet)에 넘겨 이 diff에 닿는 결정의 번호(있으면)·`파일:줄`·원문 줄 목록을 돌려받고(줄 번호는 Read 출력에 찍힌 번호를 그대로 쓰게 한다), 그 목록을 리뷰어 지시문에 그대로 옮겨 넣는다.

#### 외부 스킬 고르기

메인이 위에서 읽은 diff를 아래 표의 「리뷰 대상」 칸에 대어 **외부 베스트 프랙티스 스킬**을 고른다. only-standards 모드는 이 절을 건너뛴다.

| 리뷰 대상 | 외부 스킬 |
|---|---|
| React/Next.js 컴포넌트, 데이터 페칭, 번들 최적화, 성능 | `vercel-react-best-practices` |
| 합성 패턴 리팩토링 (boolean prop 다수, compound, render props, context) | `vercel-composition-patterns` |

메인은 고른 스킬의 본문을 읽지 않는다.
그 스킬을 맡은 리뷰어(advanced 모드면 External-Skill Reviewer, default 모드면 단일 리뷰어)에게 스킬 이름과, 형제 경로 `../<name>/SKILL.md`를 이 스킬 위치 기준 절대경로로 풀어 넘긴다.
리뷰어는 Skill tool로 그 스킬을 직접 로드하고, Skill tool이 없으면 메인이 준 그 경로를 Read한다.
리뷰어는 로드한 스킬 이름을 보고에 적고, 로드하지 못한 스킬은 이름 옆에 「로드 못 함」과 사유를 적는다.

외부 스킬이 설치돼 있지 않거나(Skill tool 목록에 없거나 형제 경로 `../<name>/` 부재) 리뷰어가 「로드 못 함」으로 보고하면, 사용자에게 https://vercel.com/docs/agent-resources/skills 에서 설치하도록 안내하고 리뷰는 이어 간다.

### 3. 리뷰 수행

메인(advanced 모드에서는 Lead)이 모드에 따라 아래 리뷰어를 띄운다. diff가 작아도 메인이 기준 문서를 직접 읽어 대조하지 않는다 — 대조는 리뷰어가 한다.

| 모드 | 리뷰어 |
|---|---|
| default | 단일 리뷰어(sonnet) 1명이 기준 문서 대조와 자유 리뷰를 함께 하고, 2단계에서 고른 외부 스킬이 있으면 그 관점도 적용한다 |
| only-standards | 단일 리뷰어(sonnet) 1명이 기준 문서 대조만 한다. 기존 코드를 새 규칙에 맞추는 마이그레이션이라 자유 리뷰가 끼면 범위가 흐려진다 |
| advanced | 아래 네 종류를 병렬로 띄우고, Lead가 결과를 합치며 중복을 걷는다 |

| advanced 리뷰어 | 맡는 일 |
|---|---|
| Coding-Standards Reviewer ×N (sonnet) | [code-map.md 탐색 절차](../../contexts/code-map.md#critical-탐색-절차)가 훑는 폴더 중 `rules/`와 MP 베스트 프랙티스를 영역으로 나눠 1명씩 맡는다. Lead는 영역만 정하고, 리뷰어가 자기 영역 안에서 1단계 2번대로 문서를 고른다 |
| External-Skill Reviewer ×M (sonnet) | 2단계에서 고른 외부 스킬마다 1명(없으면 0명). 그 스킬 관점으로만 본다 |
| Official-Way Reviewer (opus) | diff가 직접 구현한 것(다른 목적의 도구를 끌어다 쓴 것 포함)마다 같은 목적의 공식 수단(레포에 깔린 도구, 프레임워크·플랫폼 내장 API, 생태계 표준 라이브러리)이 있는지 공식 문서로 확인한다. 있으면 diff와 비교한 이슈에 공식 문서 URL과 그 페이지 원문을 붙인다. 기준 문서는 고르지 않는다 |
| Advanced Reviewer (opus) | 규칙에 없는 문제를 자유 리뷰로 짚고, `principles/`는 1단계 2번대로 고른다. Lead는 짚을 주제·관점을 지시할 수 있고, 다른 리뷰어에게 맡긴 관점은 지시문에 적어 넘긴다. Advanced Reviewer는 그 관점으로는 이슈를 싣지 않는다. 그 관점의 권고라도 Lead가 아래 충돌 여부를 되물으면 답한다 |

advanced 모드에서 기준 문서를 대조하는 리뷰어(1단계 2번대로 고르는 리뷰어, 1단계 3번의 추가 컨벤션 리뷰어)는 아래 충돌 여부를 Lead가 되물으므로 [team-agent](../../contexts/team-agent.md#claude-code)의 규칙대로 이름 있는 팀원으로 띄우고, 나머지는 `name` 없이 띄운다.

기준 문서를 대조하는 리뷰어는 고른 문서와 넘어온 문서(호출 프롬프트에 적힌 문서, `--coding-standards`·`--extra-standards` 목록)를 모두 Read 도구로 파일째 읽는다. 셸로 잘라 읽지 않는다.
그리고 문서마다 규칙을 하나씩(절이 있으면 절, 없으면 문단·항목 단위) diff에 대보고, [reviewer-checks.md](reviewer-checks.md)대로 MP 예시와 코드 모양을 대조하고 추가된 주석을 전수 대조한다.
메인은 `{{skill_dir}}/reviewer-checks.md`와, 리뷰 대상 diff를 출력하는 명령을 `node {{skill_dir}}/scripts/added-comments.mjs` 앞에 이어 붙인 완성 명령을 그 리뷰어 모두의 지시문에 넣는다.
메인은 이 스크립트를 돌리지 않는다. 명령이 도는지, 주석이 있는지 미리 보려는 실행도 하지 않는다 — 출력은 판정표를 만드는 리뷰어만 쓴다.

리뷰어는 이슈를 하나 찾으면 같은 패턴이 리뷰 대상 전체에 있는지 찾아 함께 싣는다.

리뷰어가 기준 문서가 아닌 근거로 코드를 바꾸라고 했는데 기준 문서(예시 코드 포함)는 지금 코드를 권하거나 그 변경을 금지하면, 이슈 목록과 따로 「기준 문서와 충돌」로 묶어 양쪽 근거를 나란히 사용자에게 올린다. 어느 쪽을 따를지는 사용자가 정한다.
advanced 모드에서는 Lead가 그런 권고를 기준 문서를 대조한 리뷰어들에게 보내 부딪히는지 묻는다.

### 4. 이슈 목록 산출

리뷰어 결과를 받아 이슈 목록을 내는 쪽(advanced면 Lead)은 리뷰어가 낸 위험 가설을 아래대로 재현 결과로 채택·기각한다.
위험 가설은 말꼴로 가리지 않고, 리뷰어가 단정하지 않은 지적 전부를 센다 — 「~할 수 있음」·「확인하지 못함」뿐 아니라, diff 밖 맥락(호출부·부모 레이아웃·페이지 구조)을 몰라 「판단할 수 없음」·「이슈로 확정하지 않음」으로 적은 것도 든다.

- 가설 하나에 일회성 서브에이전트 하나를 띄워, 가설 원문·리뷰어가 짚은 `파일:줄`·리뷰 대상(브랜치나 diff)을 넘기고 가설이 맞으면 생길 결과를 재현(테스트·브라우저·최소 앱)하게 한다. 재현은 직접 하지 않는다
- 여러 가설을 한 서브에이전트에 묶지 않는다 — 한 가설의 재현이 막히면 같이 묶인 가설의 결과까지 그 시행착오에 섞인다
- 서브에이전트에게서는 「재현됨」·「재현 안 됨」·「시도했으나 못 함(무엇을 시도했고 어디서 막혔는지)」 중 하나만 돌려받는다
- 결정·범위 해석만으로 기각하지 않는다
- 이슈로 올리지 않을 것 같거나 재현할 수 없어 보이는 가설도 넘긴다 — 재현 결과 없이 보류·제외로 돌리면 기각과 같고, 「시도했으나 못 함」은 시도한 서브에이전트만 낸다
- 「시도했으나 못 함」이 돌아오면 그 시도·막힌 곳과 「확인 안 함」을 밝혀 사용자에게 올린다

리뷰어는 Read한 기준 문서 경로 목록을 결과에 싣고, MP 베스트 프랙티스 파일 아래에는 그 파일에서 따라간 `코드:` 경로를 들여 적는다. [출력](#출력)의 기준 문서 목록은 이것으로 만든다. advanced 모드면 Lead가 리뷰어별 목록을 각각 합친다.

이상한 지적은 사용자에게 확인한다. 기존 코드에 같은 모양의 선례가 있다는 것만으로 기준 문서(예시 포함)를 근거로 한 지적을 기각하지 않는다.

컨벤션 기반 지적에는 근거가 되는 컨벤션 파일 경로와 라인번호를 함께 명시한다.

## 후속 연결 (사용자 판단)

독립 호출이면 사용자가 코멘트할 항목을 고르는 데서 끝난다.
