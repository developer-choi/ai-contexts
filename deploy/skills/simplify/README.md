# Simplify

오픈소스 라이브러리의 소스코드를 읽고 배우기 위한 개인 학습 방법입니다. 실제 서비스에 쓰이는 복잡한 코드에서 핵심 설계만 남기는 과정을 AI와 함께 정해진 순서로 진행합니다.

## 동기

오픈소스 라이브러리의 소스코드를 직접 읽으며 배우고 싶었습니다.

하지만 실제 서비스에 쓰이는 코드에는 학습과 상관없는 것들이 많습니다. 브라우저 호환성 처리, 서버 환경 대응, 더 이상 쓰지 않는 옛 설정 지원, 드물게 일어나는 예외 처리 같은 것들입니다.

이런 코드가 핵심 로직을 가리고 있어서, 파일을 열어봐도 "이 라이브러리가 무슨 생각으로 이렇게 설계했는지"를 파악하기 어렵습니다.

이것들을 걷어내고 핵심 구현만 남기면, 라이브러리의 설계 의도와 패턴을 훨씬 빠르게 이해할 수 있습니다.

## 접근 방식

"무엇을 남기고 무엇을 걷어낼지"를 판단하는 과정 자체가 학습입니다.

이 작업에서 코드는 읽기만 합니다. 라이브러리를 설치하거나 실행하지 않고, 빌드나 테스트도 돌리지 않습니다.

먼저 대상 라이브러리의 전체 구조를 파악합니다. 어떤 모듈이 있고, 서로 어떻게 연결되어 있는지를 이해해야 "이 코드는 핵심이다 / 이 코드는 부수적이다"를 판단할 수 있기 때문입니다.

구조가 파악되면, 간소화할 대상을 여러 개 묶어 고르고 계획을 세웁니다. 묶음이 끝날 때까지 대상마다 멈춰 확인받지 않고 이어서 처리합니다.

한 대상 안에서는 기능을 하나씩 차례로 걷어냅니다.

무엇을 지울지는 기능마다 "이 라이브러리의 핵심 개념을 배우는 데 이 구현이 필요한가"를 물어 정합니다. 이미 간소화해둔 더 단순한 라이브러리와 견주어, 그것과 구별되게 만드는 기능은 배울 거리로 보고 남깁니다.

이 판단은 AI가 근거를 계획서에 적은 뒤 그대로 진행합니다. 제가 직접 확인하는 지점은 새 프로젝트를 처음 세팅할 때입니다.

대상마다 간소화를 시작하기 전에 "원래 코드가 왜 이렇게 작성되었는지"를 먼저 문서로 기록합니다. 원본이 아직 그대로일 때 적어둬야 원본의 의도를 놓치지 않을 수 있기 때문입니다.

간소화를 마친 뒤에는 남은 코드를 읽기 위한 학습 가이드를 따로 작성합니다. 새 프로젝트를 처음 세팅할 때는 결과가 원칙대로 정리됐는지 리뷰 절차로도 점검합니다.

그리고 이 과정에서 발견한 유지/삭제 패턴을 정리합니다. "이런 종류의 코드는 보통 핵심이다", "이런 코드는 학습 목적에서는 제거해도 된다"라는 판단 기준이 쌓이면, 다음 대상을 간소화할 때 더 빠르고 정확하게 진행할 수 있습니다.

예전 방식으로 만들어둔 프로젝트는 소스를 다시 간소화하지 않고, 문서와 폴더 구조만 지금 방식에 맞추는 갱신 절차로 따로 처리합니다.

## 산출물

핵심 구현만 남긴 소스코드가 커밋 단위로 기록됩니다. 각 커밋이 "어떤 기능을 왜 제거했는지"를 담고 있어서, 간소화 과정 자체가 학습 자료가 됩니다.

원본 코드 요약과 간소화된 코드의 학습 가이드도 함께 작성하고, 반복 작업에서 쌓인 유지/삭제 패턴은 한곳에 모아 관리합니다.
