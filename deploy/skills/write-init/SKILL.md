# write-init — 내용 작성

## 목적

글의 내용을 AI와 사용자가 함께 확정해 write-refine에 넘긴다.

## 입력

`/write-init <type> [<subtype>]` 형태로 호출한다.

| type | subtype | 필수/선택 | 설명 |
|------|---------|----------|-----|
| `pr-body` | (없음) | 선택 | 일반 PR 본문 |
| `pr-body` | `recruitment` | 선택 | 채용용 PR 본문 |
| `readme` | — | — | README (subtype 미사용) |
| `pr-comment` | `reviewer` | **필수** | 검토자가 남의 PR에 코멘트 |
| `pr-comment` | `author` | **필수** | 작성자가 자기 PR에 답글 |
| `resume-intro` | — | — | 이력서 한줄소개 — 수치 중심 bullet 다단 |
| `resume-item` | — | — | 이력서 경력기술서 한 항목 |
| `decision` | — | — | 기술적 의사결정 문서 |
| `article` | — | — | 기술 글·가이드 |

필수 subtype이 빠졌거나 오타면 한 번 묻고 진행한다.

## 읽을 파일

`templates/<type>.md`가 있으면 Read한다. type별 가이드는 아래를 함께 Read한다.

| type | 가이드 |
|---|---|
| `pr-body` recruitment | 수치를 증거로 세우는 PR이면 [recruitment-evidence.md](../../contexts/writing-guide/templates/pr-body/recruitment-evidence.md), 사고 과정으로 설득하는 PR이면 [recruitment-narrative.md](../../contexts/writing-guide/templates/pr-body/recruitment-narrative.md). 갈리면 사용자에게 묻는다 |
| `pr-comment` | 없음 — subtype에 따라 질문/제안/해명/감사 구조를 정한다 |
| `readme` | [readme-guide.md](../../contexts/writing-guide/readme-guide.md) — 1차 소스와 구조를 이 가이드가 정한다 |
| `resume-intro`·`resume-item` | [resume-guide.md](../../contexts/writing-guide/resume-guide.md) |
| `decision` | [decision-guide.md](../../contexts/writing-guide/decision-guide.md) |
| `article` | [article-skeletons.md](../../contexts/writing-guide/article-skeletons.md) |

## 흐름

사용자가 지운 절·문장은 어느 단계에서도 다시 넣지 않는다. 필요해 보이면 되살릴지 묻는다.

### 1. 재료 받기

사용자가 들고 온 구상·메모·초안·예전 글과 작업 맥락(git log·diff·코드·대화)을 읽는다. 재료뿐인지, 구조 있는 초안인지, 고쳐 쓸 예전 글인지 사용자가 밝히지 않았으면 묻는다.

- **[가드2] 사용자 목소리 보존**: 사용자가 쓴 텍스트는 그대로 두고 맥락으로 보강만 한다. 의도를 비틀지 않는다.
- 글이 다른 레포(MP·AC·DC 등)에 들어가면 그 레포의 CLAUDE.md 운영방침·frontmatter 스키마를 따른다.

### 2. 핵심 문장 합의

이 글에서 독자가 딱 하나 가져갈 문장을 사용자와 합의한다. 합의 전에는 문단을 쓰지 않는다. AI가 혼자 정해 통보하지 않는다.

- 재료에 이미 있으면 뽑아 한 줄로 되짚어 확인받는다. 없으면 후보를 여러 개 내 사용자가 고르거나 고치게 한다.
- **주장은 하나**: 나란한 주장 둘은 독자가 무엇을 가져갈지 갈린다. 하나를 다른 하나의 하위 단계로 흡수하거나 잘라낸다. "왜 → 언제 → 어떻게"처럼 단계로 풀리는 것은 분열이 아니다.
- 템플릿이 칸을 주는 type도 핵심 문장은 정한다. 템플릿은 칸을 줄 뿐 골자를 주지 않는다.
- 독자(`audience`)·목적(`purpose`)도 재료에서 뽑아 핵심 문장과 함께 확인받는다.
- 합의된 문장은 패키지를 저장할 때 `key_message`에 그대로 옮긴다.

### 3. 골격

헤딩 구조를 세워 사용자에게 보이고 구조만 검수받는다. 들고 온 초안에 구조가 있으면 그것을 보이고 확인받는다. 예전 글을 고쳐 쓰면 추가·삭제되는 헤딩만 짚는다. 템플릿이 골격을 고정한 type은 선택 섹션만 검수받고, 헤딩이 없는 type(`pr-comment`·`resume-intro`)은 이 단계를 건너뛴다.

- **이미 있는 서사를 먼저 본다**: 같은 시리즈의 형제 문서가 있으면 그 글이 논지를 펴는 방식을 따르고, 다른 구조로 가면 이유를 먼저 말한다. 출처 문서가 있으면 그 구조를 골격으로 삼는다. 시리즈면 글마다 골격을 동시에 세운다.
- **축 이탈 판정**: 각 헤딩이 핵심 문장의 어느 단계인지 말할 수 있어야 한다. 말할 수 없으면 그 헤딩은 넣지 않는다. 들고 온 글에 이미 있으면 다른 절에 흡수하거나 빼는 안을 내고 확인받는다 — 임의로 남겨두면 축이 둘로 갈린 채 내용 채움에 들어간다.
- **이미 다른 헤딩이 맡은 조건인가**: 헤딩마다 그것이 맡는 조건을 적고, 앞선 헤딩과 같은 조건을 맡은 것이 있으면 골격을 내밀 때 그 자리를 짚는다. 위 축 이탈 판정은 각각이 "어느 단계인가"에 답하면 통과시켜서, 같은 단계를 둘이 맡는 것은 안 걸러진다. 같은 소재를 다루는 것과 같은 조건을 맡는 것은 다르다 — 앞이 조건을 말하고 뒤가 그 조건에서 무엇을 하는지를 말하면 중복이 아니다.
- **대비되는 둘은 헤딩으로 가르지 않는다**: 두 항목이 한 짝으로 읽혀야 하는 대비(되는 조건과 안 되는 조건, 같은 것의 앞뒤)면 헤딩 둘로 세우지 말고 같은 리스트의 이웃 항목으로 둔다. 헤딩은 각각이 독립해서 읽혀도 되는 별개 주제에 쓴다.

### 4. 내용 채움

- **(가) 과잉 생성 기본**: 근거가 있는 것은 모두 채운다. 덜어내는 것은 사용자 몫이다. 단 사용자가 지운 것과 type 가이드가 사용자가 채우도록 정한 칸은 채우지 않는다.
- 분량: frontmatter `length_target`도 템플릿 default도 없으면 사용자 텍스트의 2~3배를 상한으로 삼는다. 사용자 텍스트도 없으면 사용자에게 받는다.
- **(나) 빈칸 마크 예외**: AI가 추론 불가한 정보(개인사 등 원문·맥락에 근거 없는 것)는 채우지 말고 `[채울 내용]` 마크로 남겨 사용자에게 받는다. 근거가 애매하면 (나)로 간다.

**[가드1] 날조 방지**: 원문·컨텍스트(git diff·코드·대화) 어디에도 없는 수치·지표·고유명사·도구명·라이브러리명을 추가하지 않는다. "왜 그 선택을 했나"는 풀되 "무엇을 더 했다"는 근거 있을 때만. 보강 문단의 각 문장이 "근거가 어디 있나" 자체 점검을 통과해야 한다.

금지 단위는 토막(수치·고유명사)만이 아니라 **문장**이다. 인용블록(`> `)에 외부 원문을 넣을 때는 1차 소스를 실제로 열어 그 응답에서 문자열을 복사한다. 기억으로 재구성하거나 서로 다른 문장의 조각을 이어붙이면 원문에 없는 문장이 출처를 달고 나간다.

**[가드3] 리서치 디테일을 저자 경험으로 차용 금지** (1인칭 글 — 이력서·블로그 등): 외부 리서치(서브에이전트·웹)로 얻은 구체 사례(고유명사·증상·수치)를 저자가 실제 겪은 일처럼 본문에 1인칭으로 넣지 않는다. 날조가드의 1인칭 확장이다. 저자 확인 전이면 일반화된 표현으로만 쓰거나 `[채울 내용]`으로 묻는다 — 생생함이 그럴듯해도 출처가 "저자 경험"이 아니면 (나)다.

본문에 외부 근거나 수치가 들어가거나 1인칭 글에 리서치 사례를 쓰면 가드1·가드3의 사례집 [accuracy.md](../../contexts/writing-guide/examples/accuracy.md)를 Read한다.

**[가드4] 트레이드오프 점검**: 해법·선택을 제시하는 절이 있으면 [tradeoff-guide.md](../../contexts/writing-guide/tradeoff-guide.md)를 따라 그 선택과 맞바꾼 것을 점검한다.

### 5. 패키지 저장

채운 본문을 frontmatter + 본문 단일 .md로 저장하고 경로를 안내한다. 이후 수정은 이 파일에서 한다. 형식은 [package-format.md](../../contexts/writing-guide/package-format.md)를 따른다.

### 6. 사용자 채움

빈칸 마크가 있으면 채워 달라고 안내하고 사용자가 끝났다고 알릴 때까지 기다린다. 채워지면 사용자 텍스트를 보존한 채 맥락으로 펼치고, 빠진 내용·시각을 묻고 반영한다.

이 단계는 내용만 다룬다. 지적이 표현(어떤 단어로)이면 리라이트 안을 만들지 않고 write-refine으로 넘기고, 한 지적에 내용과 표현이 섞이면 내용만 여기서 확정한다. 반영한 주석 마커는 그 자리에서 모두 지우고 미반영(보류) 주석만 남긴다.

사용자가 거부한 표현은 그때마다 `rejected`에 적는다. 다음 세션의 write-refine이 그 거부를 알 유일한 통로다.

### 7. write-refine으로 넘기기

사용자 채움이 끝나면 아래를 한 번만 안내하고 끝낸다.

- 톤·표현·분량은 `/write-refine <패키지 경로>`로 넘긴다.
- 내용 오류는 refine으로 넘어가기 전에 여기서 확정한다.
