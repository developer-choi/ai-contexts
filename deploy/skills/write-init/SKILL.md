# write-init — 내용 작성

## 목적

외부 공개용 글(PR 본문·README·PR 코멘트·이력서·결정문)의 **내용**을 채운다. 1차 소스에서 끌어올 수 있는 것은 직접 채우고 사용자 의도가 필요한 곳만 받는다. 1차 소스가 작업 맥락(git log·코드·대화)인 type이 대부분이라 그 맥락을 가진 작업 세션에서 호출하며, `readme`처럼 1차 소스가 다른 type은 그 type의 가이드가 소유한다.

## 입력

`/write-init <type> [<subtype>]` 형태로 호출한다.

| type | subtype | 필수/선택 | 설명 |
|------|---------|----------|-----|
| `pr-body` | (없음) | 선택 | 일반 PR 본문 |
| `pr-body` | `recruitment` | 선택 | 채용용 PR 본문 — 어필 포인트 강조 |
| `readme` | — | — | README (subtype 미사용) |
| `pr-comment` | `reviewer` | **필수** | 검토자가 남의 PR에 코멘트 |
| `pr-comment` | `author` | **필수** | 작성자가 자기 PR에 답글 |
| `resume-intro` | — | — | 이력서 한줄소개 — 수치 중심 bullet 다단 |
| `resume-item` | — | — | 이력서 경력기술서 한 항목 |
| `decision` | — | — | 기술적 의사결정 문서 |
| `article` | — | — | 기술 글·가이드 |

subtype 누락·오타 시 한 번 묻고 진행한다.

## 핵심 메시지 확정 — 골격보다 앞

경로 판정·골격 게이트보다 앞이다. 확정 전에는 문단을 쓰지 않는다.

**"이 글에서 독자가 딱 하나 가져갈 문장"을 사용자와 합의한다.** AI가 혼자 정해 통보하지 않는다 — 재료(대상 레포의 형제 문서·참고 지식 문서·기존 초안)를 먼저 읽고 후보를 여러 개 만들어 사용자가 고르거나 고치게 한다.

- **주장은 하나**: 나란한 주장 둘은 독자가 무엇을 가져갈지 갈린다. 하나를 다른 하나의 하위 단계로 흡수하거나 잘라낸다.
- **단계 전개는 허용**: 한 문장이 "왜 → 언제 → 어떻게"처럼 단계로 풀리면 각 단계가 골격의 대목이 된다. 주장이 하나인 한 분열이 아니다.
- **경로별 강도**: 막연이면 후보를 제시해 고르게 한다. 확실·재활용이면 사용자 초안·기존 본문에서 핵심 문장을 뽑아 한 줄로 되짚어 확인만 받는다.
- **전 type 공통**: 템플릿이 골격을 고정하는 type(`resume-item`·`decision`)도 핵심 문장은 필요하다. 템플릿은 칸을 줄 뿐 골자를 주지 않는다.
- **확정 즉시 `key_message`에 적는다**: 「5. 패키지 저장」까지 미루지 않는다. 골격·상세·write-refine이 공유하는 잣대다.

**before** — 핵심을 합의하지 않은 채 문단부터 다듬음. 글의 축을 '세 레벨 개론'으로 오해해 축이 다른 내용(레벨 비율 논쟁·모킹)을 반복 투입하고, 사용자가 이미 지운 문단을 되살리자고 제안 → "왜 자꾸 핵심을 이해 못 하냐"는 지적을 받음.

**after** — 재료(모킹 지식 문서·기존 초안)를 먼저 읽고 후보를 제시 → 사용자가 하나 고르고 "단계별로 가져가자"로 보완 → "모킹은 확신과 맞바꾸는 거래이니, 모킹하려는 이유를 없앨 만큼만 교체한다"로 확정 → 그 한 문장에서 왜/언제/어떻게 세 단계 골격이 바로 나오고, 축이 다른 기존 절이 자동으로 걸러짐.

## 경로 판정 — 사실 질문으로 결정론적으로

모델 추론으로 넘겨짚지 않는다. 아래를 **사실 질문**으로 물어 경로를 고정한다:

> "쓰실 글의 **골격(섹션 구조)이 이미 있으세요**, 아니면 **재료만** 있으세요? 혹은 **기존에 쓴 글을 재활용**하시나요?"

- **막연** (재료만, 뭘 쓸지 추상적) → 골격 게이트 **ON**
- **확실** (내용·구조 다 앎, 사용자가 초안 보유) → 골격 게이트 **OFF**
- **재활용** (기존 확정본 + 새 요구) → **델타 게이트** (추가·삭제되는 헤딩만 미니 검수)

## 작업 흐름

### 1. 템플릿·가이드 로드 (on-demand)

- `templates/<type>.md`가 있으면 Read (pr-body·decision·resume-intro·resume-item·article).
- type별 가이드가 있으면 Read: `resume-item`·`resume-intro` → `../../contexts/writing-guide/resume-guide.md`, `decision` → `../../contexts/writing-guide/decision-guide.md`, `readme` → `../../contexts/writing-guide/readme-guide.md`, `article` → `../../contexts/writing-guide/article-skeletons.md`.
- 해법·선택을 제시하는 절이 있으면 `../../contexts/writing-guide/tradeoff-guide.md`도 Read한다 (아래 [가드4]). `decision`·`resume-*`는 항상 해당하고, 다른 type도 본문에 비교·선택 절이 보이면 해당한다.
- 예외 — `pr-comment`(템플릿 없음, 자유 형식: subtype에 따라 질문/제안/해명/감사 구조를 동적 결정), `readme`(템플릿 없음, `readme-guide.md`가 구조와 1차 소스를 소유).
- **대상 레포 규약 따르기**: 글이 다른 레포(MP·AC·DC 등)에 들어가면 그 레포의 CLAUDE.md 운영방침·frontmatter 스키마를 따른다. 출처 문서가 있으면 그 구조를 골격으로 삼고, 시리즈면 N개 skeleton을 동시에 만든다.

### 2. 골격 + 뼈대 초안

확정된 핵심 문장에서 파생되는 헤딩만 세운다.

**골격을 만들기 전에 이미 있는 서사를 먼저 본다** — 형제 문서와 사례집 중 무엇을 따르는지의 순서는 `../../contexts/writing-guide/article-skeletons.md`가 소유한다. type이 `article`이 아니어도 같은 순서로 본다.

경로별로:

- **막연 (게이트 ON)**: 헤딩 계층(골격)을 먼저 세워 사용자에게 보인다. **헤딩 구조만** 검수받는다(내용 아님). OK 후 내용 채움.
- **확실 (게이트 OFF)**: 사용자 초안을 골격으로 받아 바로 내용 단계로.
- **재활용 (델타)**: 기존 확정본을 기준 골격으로, 추가·삭제되는 헤딩만 짚어 확인.

**축 이탈 판정**: 각 헤딩이 핵심 문장의 어느 단계인지 말할 수 있어야 한다. 말할 수 없으면 그 헤딩은 넣지 않는다. 기존 본문(확실·재활용 경로)에 이미 있으면 다른 절에 흡수하거나 뺀다고 사용자에게 보고한다 — 임의로 남겨두면 축이 둘로 갈린 채 상세 채움에 들어간다.

### 3. 내용 채움 — 두 가드 준수

작업 맥락(git log·diff·코드·대화)과 템플릿을 결합해 채운다.

- **(가) 과잉 생성 기본**: 근거 있으면 왕창 채운다. 덜어내는 것은 사용자가 한다.
- **(나) 빈칸 마크 예외**: AI가 추론 불가한 정보(개인사 등 원문·맥락에 근거 없는 것)는 채우지 말고 `[채울 내용]` 마크로 남겨 사용자에게 받는다.
- **(가)/(나) 경계 = 날조가드**: 원문·맥락에 근거 있으면 (가), 지어내야 하면 (나). **날조할 바엔 빈칸.**

**[가드1] 날조 방지**: 원문·컨텍스트(git diff·코드·대화) 어디에도 없는 수치·지표·고유명사·도구명·라이브러리명을 추가하지 않는다. "왜 그 선택을 했나"는 풀되 "무엇을 더 했다"는 근거 있을 때만. 보강 문단의 각 문장이 "근거가 어디 있나" 자체 점검을 통과해야 한다.

**[가드2] 사용자 목소리 보존**: 사용자가 쓴 텍스트는 그대로 두고 컨텍스트로 보강만. 의도 왜곡 금지.

**[가드3] 리서치 디테일을 저자 경험으로 차용 금지** (1인칭 글 — 이력서·블로그 등): 외부 리서치(서브에이전트·웹)로 얻은 구체 사례(고유명사·증상·수치)를 저자가 실제 겪은 일처럼 본문에 1인칭으로 넣지 않는다. 날조가드의 1인칭 확장이다. 저자 확인 전이면 일반화된 표현으로만 쓰거나 `[채울 내용]`으로 묻는다 — 생생함이 그럴듯해도 출처가 "저자 경험"이 아니면 (나)다.

- **before**: 서브에이전트가 찾은 "스크린리더(VoiceOver/NVDA)에서 접근성 실패" 사례를 저자가 겪은 직접 개발 단점으로 서술.
- **after**: 저자에게 확인 → 실제 경험은 "iOS·안드로이드·크롬 등 모던 브라우저 간헐 버그·디버깅 고통"이라 그것으로 교체, 스크린리더 사례는 제거.

**[가드4] 트레이드오프 누락 점검**: 해법·선택을 제시하는 절마다 그 선택과 맞바꾼 것이 적혀 있는지 점검하고, 빠졌으면 [tradeoff-guide.md](../../contexts/writing-guide/tradeoff-guide.md)를 따라 처리한다.

### 4. 사용자 채움·리뷰

마크가 있으면 채워달라 안내하고 명시적 신호("OK"·"다 적었어")까지 대기. 신호 오면 사용자 텍스트를 보존한 채 컨텍스트로 펼친다. 빠진 내용/시각을 묻고 반영(캡 없음). **이 단계는 내용만 — 톤 수정 요청은 "그건 write-refine에서"로 안내.** 산출물 주석·지적이 단어 선택·표현 다듬기("이 단어 별로", "표현 어떻게 다듬지")면 init에서 리라이트 안을 만들지 말고 write-refine으로 안내한다. 한 주석에 내용(무엇을·어디에)과 표현(어떤 단어로)이 섞이면 내용만 init에서 확정하고 표현은 refine으로 넘긴다. 사용자 인라인 주석을 반영한 뒤에는 반영한 주석 마커를 그 자리에서 모두 제거한다 — 일부만 지우지 않으며, 미반영(보류) 주석만 남긴다.

사용자가 표현을 거부하면 그 자리에서 frontmatter `rejected`에 기록한다. 다음 세션의 write-refine이 그 거부를 알 유일한 통로다.

frontmatter `length_target`도 템플릿 default도 없으면 사용자 텍스트의 2~3배를 분량 상한으로 삼는다.

### 5. 패키지 저장

확정 본문을 frontmatter + 본문 단일 .md로 저장하고 경로를 안내한다. 이 파일이 write-refine 입력. 형식은 [package-format.md](../../contexts/writing-guide/package-format.md) 참조.

- 필수 필드는 사용자와의 합의·작업 맥락에서 채운다. 근거 없는 값을 지어내지 않는다(날조가드).

## 산출 후 1회 안내

패키지 저장 후 아래를 한 번만 안내하고 끝낸다 (반복 넛지 없음).

- 톤·구조·분량은 `/write-refine <패키지 경로>`로 넘긴다. 진입 전 `/compact`를 권한다 — 기각된 초안 문안이 히스토리에 남아 있으면 표현 개선을 핑계로 되살아난다.
- 표면 교정은 사용자가 직접 하는 게 빠르고, 그 외 수정 지시는 산출물에 주석으로 일괄 달면 refine이 모아 반영한다.
- 내용 오류는 refine으로 넘어가기 전에 여기서 확정한다.
