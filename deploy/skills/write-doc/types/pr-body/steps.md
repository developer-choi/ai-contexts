# pr-body — type마다 더 도는 절차

절 제목의 ID는 단계 파일의 절차 ID와 같다. 기본 절차와 부딪치면 이 절을 따른다.

## [RECEIVE_STEP] 재료 받기

재료를 읽기 전에 `node {{skill_dir}}/scripts/plan-materials.mjs <대상 레포 안 아무 경로>`를 돌린다. 대상 레포 메인 체크아웃의 `plan/` 아래 이름 목록과 todo가 든 md 목록이 나온다. `plan/`이 없다고 나오면 건너뛴다.

1. **위치 추론**: 이 PR의 재료가 어디 있는지 이름 목록**만** 보고 추론한다. 파일 내용은 열지 않는다(후보마다 열면 쓰지 않을 재료까지 컨텍스트에 실린다). 사용자가 재료를 직접 들고 왔으면(경로를 알려 줬거나 붙여 넣었으면) 이 추론은 건너뛴다.
   - 이름이 틀리게 읽힐 수 있다고 전제한다(PR 번호와 폴더 번호가 다르거나, 이미 써 둔 패키지를 다듬으러 온 경우).
   - 확신이 서면 추론 근거를 한 줄로 밝히고 진행하고, 아니면 후보 이름을 보여 사용자에게 묻는다.
2. **todo 목록**: 스크립트가 낸 todo 목록을 사용자에게 보인다. 메모 바구니(`plan/background/consumable/todo.md` 등)에 이 PR 본문에 들어갈 항목이 있을 수 있으니, 사용자가 목록을 보고 쓸 항목을 정한다.

## [KEY_MESSAGE_STEP] 핵심 문장 합의

PR 제목 한 줄도 함께 확인받는다 — [가이드의 「PR 제목」](../../../../contexts/writing-guide/types/pr-body/guide.md#pr-제목) 기준.

## [SCAN_STEP] 파악

본문 H1(PR 제목)을 [가이드의 「PR 제목」](../../../../contexts/writing-guide/types/pr-body/guide.md#pr-제목) 기준과 아래로 점검한다.

- `key_message`와 같은 주장인가 — 주장을 받치는 방법·근거만 남고 주장이 빠지지 않았는가
- 본문이 제목의 주장을 뒷받침하는가
- 낱말이 실제 구조와 맞는가 — 공통 패키지를 함께 쓰는데 「서로 공유」라 하는 식으로 구조를 다르게 말하지 않았는가
- 사람이 확인한 것을 자동 테스트로 읽히게 하는 「테스트」를 쓰지 않았는가
- 명사가 조사 없이 줄줄이 붙지 않았는가

걸린 것이 있으면 제목을 제자리에서 고치지 않는다.

- 걸린 것을 짚고, 시안을 여럿 텍스트로 내 사용자가 고르게 한 뒤 고른 것을 H1에 반영한다.
- 시안도 같은 점검을 거치고, 걸린 시안은 내지 않는다.
- `key_message`나 본문과 주장이 어긋난 것은 시안을 `key_message`에 맞춰 내되, 본문 쪽이 틀렸을 수 있으니 그 어긋남을 사용자에게 함께 알린다.

## [PUBLISH_STEP] 발행

- 발행처가 이미 열린 GitHub PR이면 `node {{skill_dir}}/scripts/publish-pr.mjs <패키지> --pr <번호> [--repo owner/name] --apply`로 게시한다.
- PR이 아직 없으면 게시하지 않고 패키지 경로를 보고한다. PR 본문 칸에 패키지를 그대로 붙이지 않게, PR을 연 뒤 위 명령으로 제목·본문을 덮어쓰라고 함께 안내한다.
