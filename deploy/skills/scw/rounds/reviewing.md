# 리뷰·감사 회차

이미 있는 프롬프트 문서를 훑어 의심 지점을 찾는 회차에서 읽는다. 찾은 것을 고쳐 쓰는 규칙은 [editing.md](editing.md)에 있다.

## 프롬프트 감사 렌즈

프롬프트 문서가 **잘 쓰였는가**를 보는 관점. [의심 지점 개선 루프](#의심-지점-개선-루프)의 스캔 단계에서 이 렌즈로 의심 지점을 수집한다. 발견 항목의 분류·검증·반영·보고는 루프가 담당한다 — AI가 판단하고 사용자는 커밋 diff로 확인하며, 별도 판정 파일은 만들지 않는다.

### 리뷰 범위

- 명확성 — AI가 오해 없이 실행할 수 있는가
- 정합성 — 문서 내부, 또는 참조하는 다른 문서와 모순이 없는가
- 구조 — 정보가 효과적으로 배치되어 있는가
- 간결성 — 더 적은 토큰으로 같은 효과를 낼 수 있는가
  - 군더더기 표현 제거: 의미 없는 부사·접속어(`기본적으로`, `사실상`, `즉`, `또한`, `이러한`, `~의 경우`, `~를 통해`), 동어 반복(`반드시 필수로`, `미리 사전에`), 늘어진 명사구(`~에 대한 검증을 수행한다` → `~를 검증한다`)는 삭제·압축
- 에이전트 설계 — 서브에이전트/메인 에이전트 구조가 최적인가 (해당 시에만). 병렬화 여부는 안 적어도 걸리므로 아래 넷만 본다
  - 메인이 이미 가진 컨텍스트를 서브에이전트가 다시 로드하는가
  - 반복 사이클에서 이전 반복의 맥락이 유실되는가
  - 위임하는 이유가 무엇인가 — 컨텍스트 격리·병렬화·객관성 중 어느 것도 아니면 나눌 이유가 없다
  - 에이전트 간 결과 전달 구조가 명확한가 (산출물 → 입력 체이닝)

대상 경로별로 어떤 특화 체크리스트를 함께 읽는지는 SKILL.md 「특화 리뷰」 표가 정한다.

범위 밖: "문서 속 규칙이 실제로 동작하는가"는 [기능테스트](benching.md#기능테스트)의 영역이다.

## 의심 지점 개선 루프

스킬·프롬프트의 의심 지점을 AI가 자동 분류·검증·적용한다 — 사용자 판정 없이 커밋까지. 스캔은 [프롬프트 감사 렌즈](#프롬프트-감사-렌즈)로 수행하고, 사용자는 커밋 diff로 결과를 확인한다.

상세는 [improve-loop.md](../improve-loop.md) 참조.

진입 트리거: "스킬 의심 지점 찾아 개선", "비판적으로 따져 다듬어", "벤치 돌려서 개선" 등.

## 자기 검증

- 리뷰 완료 후, 자신의 리뷰를 비판적으로 되돌아본다. 특히 **제거한 항목이 실제로 필요해지는 상황을 테스트가 압박했는지** 본다 — 압박하지 못한 케이스는 델타 0이 "불필요"가 아니라 "안 재봄"이다. 부족한 케이스를 발견하면 사용자 승인 없이 바로 추가 벤치마크를 돌린다
