# 리뷰·감사 회차

이미 있는 프롬프트 문서를 훑어 의심 지점을 찾는 회차에서 읽는다. 찾은 것을 고쳐 쓰는 규칙은 [editing.md](editing.md)에 있다.

## 프롬프트 감사 렌즈

프롬프트 문서가 **잘 쓰였는가**를 보는 관점. [의심 지점 개선 루프](#의심-지점-개선-루프)의 스캔 단계에서 이 렌즈로 의심 지점을 수집한다. 발견 항목의 분류·검증·반영·보고는 루프가 담당한다 — AI가 판단하고 사용자는 커밋 diff로 확인하며, 별도 판정 파일은 만들지 않는다.

### 리뷰 범위

- 명확성 — AI가 오해 없이 실행할 수 있는가
- 정합성 — 문서 내부, 또는 참조하는 다른 문서와 모순이 없는가
- 구조 — 정보가 효과적으로 배치되어 있는가. [파일·폴더 나누기](../../../contexts/prompt-standards/file-layout.md)로 본다
- 간결성 — 더 적은 토큰으로 같은 효과를 낼 수 있는가
  - 문장은 [문장 다듬기](../../../contexts/prompt-standards/wording.md)로 한 줄씩 본다
- 에이전트 설계 — 서브에이전트/메인 에이전트 구조가 최적인가 (해당 시에만). [스킬 짜임](../../../contexts/prompt-standards/skill-structure.md#에이전트-설계)으로 본다

대상 경로별로 어떤 특화 체크리스트를 함께 읽는지는 SKILL.md 「특화 리뷰」 표가 정한다.

범위 밖: "문서 속 규칙이 실제로 동작하는가"는 [기능테스트](../benching/kinds/function-test.md)의 영역이다.

## 의심 지점 개선 루프

스킬·프롬프트의 의심 지점을 AI가 자동 분류·검증·적용한다 — 사용자 판정 없이 커밋까지. 스캔은 [프롬프트 감사 렌즈](#프롬프트-감사-렌즈)로 수행하고, 사용자는 커밋 diff로 결과를 확인한다.

진입 트리거: "스킬 의심 지점 찾아 개선", "비판적으로 따져 다듬어", "벤치 돌려서 개선" 등.

### 사전 작업 (워크트리)

작업 전 git 상태 점검:
- 현재 브랜치가 master/main이 아니거나 uncommitted가 있으면 워크트리 사용
- master에서 워크트리 + 브랜치 생성. 이름은 작업 대상이 드러나게
- 사용자에게 워크트리 경로·브랜치명 보고

이 **작업** 워크트리는 사용자 지시를 받고 삭제한다 — 병합 여부를 사용자가 정하기 전까지 결과물이 여기에만 있기 때문이다. 벤치가 측정용으로 만든 워크트리는 반대로 지시를 안 받고 삭제한다 — 시점과 예외는 bench-operations 「벤치 산출물 정리」가 정한다.

### 자동 진행 디폴트

라운드 사이 사용자 확인 질문 금지. 한 라운드(스캔→분류→적용→보고)가 끝나면 잔류 의심 지점이 있는 한 자동으로 다음 라운드에 진입한다. "다음 라운드 진행할까요?", "다음은 어느 파일 볼까요?" 같은 진행 의사 확인을 사용자에게 묻지 않는다.

사용자가 명시적으로 "멈춰", "여기까지", "다음 세션으로" 라고 말할 때만 중단. 결과 보고는 매 라운드 짧게(채택/반려·근거 한 줄) 흘려두고, 사용자가 끼어들면 그때 방향 전환.

### 5단계 워크플로우

#### 1. 스캔

대상 스킬과 참조 파일을 모두 Read한다. 의심 지점을 모두 수집한 뒤 분류로 넘어간다 (한 건씩 보고 처리하지 않는다).

수집 관점: [프롬프트 감사 렌즈](#프롬프트-감사-렌즈)(명확성·정합성·구조·간결성·에이전트 설계 + 특화 리뷰)를 기본 렌즈로 삼고, 여기에 사문·중복·how 과잉([editing.md 「how 최소화 원칙」](editing.md#how-최소화-원칙))·정의 모순·사용되지 않는 분기 등을 더한다.

#### 2. 2-tier 분류

| Tier | 기준 | 검증 요구 |
|------|------|-----------|
| 객관적 정리 | 사문(어디서도 참조 안 됨)·중복(다른 곳에 그대로 있음)·모순·버그 — **외부 사실로 증명 가능**한 것만 | 불필요 — 즉시 수정 |
| 벤치 필수 | 위에 해당하지 않는 모든 의심 지점. "이 줄을 빼도 같은 동작" 같은 행동 예측은 전부 벤치로 보낸다 | [editing.md 「how 최소화 원칙」](editing.md#how-최소화-원칙) 비교 테스트 절차로 OLD vs NEW 검증. 대상이 `deploy/rules/` 등 지침/규칙 나열 문서면 추가로 [rule-ablation.md](../benching/kinds/rule-ablation.md) 적용 |

판단 원칙: 의심되면 벤치 필수 쪽으로 분류한다. "이건 명백해 보인다"고 객관적 정리로 미루지 않는다. 분류 근거가 약하면 벤치로 보낸다.

#### 3. 적용

- 객관적 정리: 수정 → 항목당 커밋 1개
- 벤치 필수: [editing.md 「how 최소화 원칙」](editing.md#how-최소화-원칙) 비교 테스트 → 결과 분석 → 채택/반려 결정 → 채택 시 커밋
- 스코프 외 발견: 5단계로 백로그 이관

수정한 파일만 명시 staging.

#### 4. 보고

사용자에게 표 형식으로 보고. 필수 컬럼:
- 커밋 해시
- 무엇을 수정했는가
- 왜 수정했는가
- 어떤 벤치 결과가 근거인가 (없으면 분류 명시: 객관적)

추상 설명 금지. 벤치 결과는 OLD/NEW 실제 출력의 핵심 차이를 1-2줄로 인용한다.

#### 5. 백로그 이관

스코프 외 이슈는 `/backlog`로 넘긴다. 넘길 때 이 세션에서만 아는 것을 다 실어 보낸다 — 어느 파일 어느 절에서 무엇을 보다 걸렸는지, 왜 스코프 밖으로 뺐는지. 항목을 받는 세션은 이 대화를 못 보므로, 요약하면 착수 자체가 불가능해진다.

### gotchas

- 검증 없이 수정한 항목을 "벤치 기반"이라고 보고하지 말 것 — tier를 정확히 명시한다
- "의심된다 → 검증한다"가 원칙. "이건 명백해 보인다"고 벤치 스킵 금지 — [editing.md 「how 최소화 원칙」](editing.md#how-최소화-원칙) 비교 테스트는 AI 판단만으로 결정하지 않는다는 원칙 재확인
- 백로그 이관 시 항목을 짧게 요약하면 인수인계 불가. 같은 영역의 다른 기존 항목을 참고해 분량을 맞춘다

## 자기 검증

- 리뷰 완료 후, 자신의 리뷰를 비판적으로 되돌아본다. 특히 **제거한 항목이 실제로 필요해지는 상황을 테스트가 압박했는지** 본다 — 압박하지 못한 케이스는 델타 0이 "불필요"가 아니라 "안 재봄"이다. 부족한 케이스를 발견하면 사용자 승인 없이 바로 추가 벤치마크를 돌린다. 「의심 지점 개선 루프」의 보고 뒤에도 이 절을 적용한다
