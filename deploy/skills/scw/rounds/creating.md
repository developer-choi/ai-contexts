# 새 스킬을 만드는 회차

없던 스킬을 새로 세우는 회차에서 읽는다. 만든 뒤 본문을 쓰는 규칙은 [editing.md](editing.md)에 있다 — 두 파일을 함께 읽는다.

## 전제

[CRITICAL] `skill-creator`를 로드한다. Claude Code에서는 플러그인/스킬로, Codex에서는 시스템 스킬로 제공될 수 있다. 실패하면 즉시 중단하고 사용자에게 skill-creator 설치 또는 활성화가 필요하다고 안내한다.

skill-creator를 사용하되, 이 프로젝트에서는 추가로 아래를 따른다.

Codex 시스템 skill-creator는 지침 로드와 `init_skill.py` 기반 초기화에 쓸 수 있다. 검증 스크립트가 PyYAML을 요구하는데, 없으면 전역 Python을 건드리지 말고 임시 위치에 격리해 설치하고 그 명령 세션에서만 잡히게 한다. `init_skill.py`가 채워두는 기본 `description: [TODO: ...]`는 YAML 리스트로 해석돼 validator가 실패하므로, 실제 문자열로 바꾼 뒤 검증한다.

## skill-discovery

신규 스킬을 만들기 전에 `deploy/skills/` 하위 SKILL.md들의 description을 읽어 유사한 스킬을 찾고, 있으면 그 구조·패턴을 참고해 설계한다.

## 설계 토론 (Capture Intent 보강)

skill-creator의 Capture Intent / Interview 단계에서, 사용자에게 바로 질문하지 않는다. 에이전트팀을 만들어 설계 토론을 거친 뒤 정제된 제안을 가져온다.

### 팀 구성

| 역할 | 책임 |
|------|------|
| 설계자 | 사용자 목표(마이그레이션 문서 등)를 달성하는 설계안을 만든다. 목표 수호 책임 |
| 토론자 | 설계안의 결함을 찾고 도전한다. 구현 후에는 리뷰어 역할도 겸한다 |
| 구현자 | 합의된 설계안을 실행한다. 설계자와 세트로 움직인다 |

설계자+구현자가 한 세트, 토론자가 독립이다.

### 인프라

[CRITICAL] [team-agent](../../../contexts/team-agent.md)의 규칙을 따른다.

설계 토론 팀은 현재 런타임의 team-agent 경로로 구성한다. Codex에서는 허용된 subagent 도구를 사용하되, 같은 역할 작업자를 재사용해 다라운드 맥락을 유지한다. 팀/서브에이전트 구성이 불가능하면 메인이 역할을 직접 수행하고, 그 이유를 사용자 제안에 포함한다.

### 절차

1. **사용자 의도 최소 확인** — 뭘 하고 싶은지, 왜 하는지만 파악한다
2. **설계 토론** — 설계자가 기존 파일을 분석하고 설계안을 만든다. 토론자가 도전한다. 2-3라운드 토론 후 합의. 폴더/파일 구조가 관련된 작업이면, 구조의 합리성(파일 위치, 공용 vs 개별, 참조 경로)도 토론 범위에 포함한다.
3. **사용자에게 제안** — 합의된 설계안을 가져온다. 사용자는 승인/수정/반려한다
4. **구현** — 구현자가 실행한다. 토론자가 리뷰한다

### 왜 이 구조인가

- **설계자가 목표를 수호한다**: 토론자 2명이면 누구도 사용자 목표에 책임이 없다. 설계자가 사용자 목표 달성을 책임지면서 토론자의 도전을 받는다
- **설계 토론이 구현 전에 일어난다**: 구현 후 리뷰에서 설계 문제가 터지면 수정 비용이 높다. 설계안 단계에서 토론하면 비용이 낮다
- **토론자가 설계 맥락을 안다**: 설계 토론에 참여했으므로 구현 리뷰 품질이 높다
