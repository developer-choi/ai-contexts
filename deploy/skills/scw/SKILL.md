# Skill Creator & Prompt Auditor

## 목적

이미 있는 스킬·프롬프트 문서를 잘 고친다.

프롬프트는 고칠수록 늘어난다 — 문장을 더하는 쪽은 효과가 있어 보이고 빼는 쪽은 근거를 대야 해서, 아무도 안 뺀다. 고치는 일과 잘 고쳐졌는지 따지는 일을 한자리에 묶어 그 자리에서 검증하게 한다.

## 전제

[CRITICAL] `skill-creator`를 로드한다. Claude Code에서는 플러그인/스킬로, Codex에서는 시스템 스킬로 제공될 수 있다. 실패하면 즉시 중단하고 사용자에게 skill-creator 설치 또는 활성화가 필요하다고 안내한다.

## 스킬 개선

스킬을 고칠 때 [guide.md](guide.md)의 규칙을 따른다. 새 스킬 작성은 skill-creator가 맡고, 그때도 guide.md를 함께 적용한다.

## 책임 분리 (SRP)

스킬·문서에 규칙을 추가하려 할 때, 그 규칙이 본인 행위인지 다른 곳(다른 스킬·프로젝트·메타 파일)의 행위인지 점검한다. 다른 곳 행위면 그 단일 출처에 추가하고, 본인 본문은 한 줄 위임만 둔다.

예:

- 라우팅 스킬에 행선지 양식·변환 절차를 박지 않는다 → 행선지가 단일 출처
- 작성 스킬에 검증 절차를 박지 않는다 → 검증 스킬이 단일 출처

위반 신호: 같은 규칙이 두 곳에 적혀 동기화 부담이 생긴다.

### 위임 문구는 목적지에 실제로 닿아야 한다

다른 문서의 절을 가리킬 때는 **앵커 링크**로 적는다. 표시 글자는 평소 부르던 짧은 이름으로 둬도 된다 — 닿게 하는 것은 주소 쪽이다.

```markdown
[서술 규칙](tradeoff-guide.md#서술-규칙)
```

재기술을 걷어내는 목적이 "한 곳만 보게 하기"인데, 그 한 곳을 못 찾게 만들면 걷어내기 전보다 나쁘다 — 재기술은 틀리기라도 하지만 도착 못 하는 위임은 아무것도 남기지 않는다.

절 이름을 기억으로 적지 않는다. 가리키려는 문서를 열어 실제 헤딩을 확인한 뒤 앵커를 적는다.

### 다른 파일의 단계는 번호로 가리키지 않는다

한 파일이 자기 안의 단계를 「Step 2」로 부르는 것은 그 파일만 보면 끝나니 괜찮다. 다른 파일의 단계를 번호나 번호 범위로 가리키면(`prep.md Step 2에서 만든 X`, `본 절차(Step 1~3)와 함께 수행한다`) 가리켜지는 쪽에 단계가 하나 끼는 순간 가리키는 쪽이 전부 조용히 틀린다. 「본 절차」·「트레이닝 단계」처럼 역할 이름으로 부르면 번호가 밀려도 안 낡는다.

낡은 번호 참조를 만나면 새 번호로 갱신하지 말고 역할 이름으로 바꾼다. 번호를 맞추는 것은 이번 밀림만 덮는 것이라, 다음에 단계가 또 끼면 같은 일이 난다.

예외는 그 자체가 인덱스·참조표인 자리다 — 진행 순서표는 단계를 번호로 세는 것이 본질이라 대상이 아니다.

## 행동 룰 단일화 — 메타 룰 vs 본문 분산

「책임 분리(SRP)」가 다른 스킬·출처 간 단일화라면, 본 절은 같은 스킬 안에서 메타 룰 vs 본문 분산의 단일화를 다룬다.

### 왜

같은 행동 룰을 여러 위치(step·세션·sub-skill·sub-file 본문 등)에 각각 박으면 한 곳을 빠뜨려도 비대칭으로만 노출되어 사용자가 사례로 짚어줘야 발견된다. SKILL.md [CRITICAL] 지킬 원칙에 메타 룰을 박으면 분산 누락이 원천 차단된다.

### 어떻게

둘 이상의 위치에 같게 적용되는 룰은 「세션 종료 시 ~」·「산출물 작성 시 ~」 꼴로 추상화해 SKILL.md `[CRITICAL] 지킬 원칙`에 신설 절로 박고, 분산 위치 본문에는 박지 않는다. "검토 범위 한정"·"추가 컨텍스트 로드 금지" 같은 특화 제약도 추상화할 수 있는지 함께 본다.

### 사례

workflow 스킬에서 「이전 PR 산출물 비판적 검토」가 step-4 본문에만 박혀 step-3에는 비대칭으로 누락. 사용자가 PR4 사례(BG의 `crypto.getRandomValues` 결정을 step-3 진입 시 무비판 수용)로 짚어줌. 해결: 메타 룰 「입력 산출물 비판적 검토」로 workflow SKILL.md에 박고 step-4 본문 절 제거.

### 메타 룰 단일화 시 자가검토 (4점검)

메타 룰로 흡수할 때 다음 4점을 확인:

1. **트리거 시점 명시** — 메타 룰이 "언제 발동되는지" 명시 (세션 진입 시·step 진입 시·산출물 작성 직후 등). 시점 모호하면 트리거 안 됨
2. **대상 범위 명시** — "어떤 입력에 적용되는지" 명시 (AI 결정·narrative 한정 vs 진실 원천 제외 등). 범위 모호하면 「검증 기준 = 진실 원천」 같은 다른 메타 룰과 충돌
3. **기준 일반화 가능 여부** — 위치별 특화 기준이 추상화 가능한가. 안 되면 메타 룰 분할 또는 메타 룰 + 본문 보조
4. **트리거 보강** — 메타 룰이 본문 호출 없이 발동되는지. 약하면 표 컬럼 헤더에 마커 1회 또는 본문 cross-reference 1줄 보강. 분산 명시는 재발 패턴이므로 회피

### 점검

- 본문에 "비판적으로 검토", "자가 검토", "산출물 검증" 같은 룰성 표현이 있으면 메타 룰 후보
- 비슷한 룰이 다른 위치에도 박혀 있거나, 안 박혀 비대칭이 보이면 메타 룰로 단일화 제안
- 검증 대상 스킬·SKILL.md의 기존 메타 룰(예: workflow의 「자가 검토 필수」)과 책임 분담이 명확한지 확인 — 중복되면 통합

## 프롬프트 감사 렌즈

프롬프트 문서가 **잘 쓰였는가**를 보는 관점. 「의심 지점 개선 루프」의 스캔 단계에서 이 렌즈로 의심 지점을 수집한다. 발견 항목의 분류·검증·반영·보고는 루프가 담당한다 — AI가 판단하고 사용자는 커밋 diff로 확인하며, 별도 판정 파일은 만들지 않는다.

### 리뷰 범위

- 명확성 — AI가 오해 없이 실행할 수 있는가
- 정합성 — 문서 내부, 또는 참조하는 다른 문서와 모순이 없는가
- 구조 — 정보가 효과적으로 배치되어 있는가
- 간결성 — 더 적은 토큰으로 같은 효과를 낼 수 있는가
  - 군더더기 표현 제거: 의미 없는 부사·접속어(`기본적으로`, `사실상`, `즉`, `또한`, `이러한`, `~의 경우`, `~를 통해`), 동어 반복(`반드시 필수로`, `미리 사전에`), 늘어진 명사구(`~에 대한 검증을 수행한다` → `~를 검증한다`)는 삭제·압축
- 에이전트 설계 — 서브에이전트/메인 에이전트 구조가 최적인가 (해당 시에만). 병렬화 여부는 안 적어도 걸리므로 아래 넷만 본다
  - 메인이 이미 가진 컨텍스트를 서브에이전트가 다시 로드하는가
  - 반복 사이클에서 이전 반복의 맥락이 유실되는가
  - 위임하는 이유가 무엇인가 — 컨텍스트 격리·병렬화·객관성 중 어느 것도 아니면 나눌 이유가 없다
  - 에이전트 간 결과 전달 구조가 명확한가 (산출물 → 입력 체이닝)

범위 밖: "문서 속 규칙이 실제로 동작하는가"는 [기능테스트](#기능테스트)의 영역이다.

### 특화 리뷰

프롬프트·스킬 md를 만들거나 고치는 작업이면 레포·경로와 무관하게 항상 [lean-prompt.md](specialized/lean-prompt.md)를 읽고 적용한다 — 아래 표와 달리 조건이 없다. 새로 쓰는 산문에도 적용되며, 리뷰 때만 보는 것이 아니다.

대상이 SKILL.md거나 스킬이 읽는 문서면 [cross-cli.md](specialized/cross-cli.md)도 같이 적용한다. 스킬은 여러 CLI로 함께 배포되는데 한쪽에서만 도는 표현은 에러 없이 무시되므로, 쓰는 시점에 걸러야 한다.

그에 더해, 검증 대상이 아래 경로에 해당하면 해당 파일을 읽고 추가 관점으로 리뷰한다.

| 대상 경로 | 특화 파일 |
|-----------|-----------|
| `deploy/contexts/coding-standards/` | [coding-standards.md](specialized/coding-standards.md) |
| `deploy/skills/workflow/` | [workflow.md](specialized/workflow.md) |
| `deploy/skills/workflow/requirement-review/` | [requirement-review.md](specialized/requirement-review.md) |
| `deploy/contexts/writing-guide/` | [writing-guide.md](specialized/writing-guide.md) |
| `deploy/rules/`, 그 외 지침·규칙 나열 문서 (ablation 벤치) | [rule-ablation-bench.md](specialized/rule-ablation-bench.md) |
| `SKILL.md` 또는 sub-skill 라우터 파일 | [skill-orchestration.md](specialized/skill-orchestration.md) |

대상 경로에 `map.md`가 있으면 추가로 점검한다:
- **중복**: 하위 파일 간 같거나 비슷한 내용이 있는가

## 의심 지점 개선 루프

스킬·프롬프트의 의심 지점을 AI가 자동 분류·검증·적용한다 — 사용자 판정 없이 커밋까지. 스캔은 「프롬프트 감사 렌즈」로 수행하고, 사용자는 커밋 diff로 결과를 확인한다.

상세는 [improve-loop.md](improve-loop.md) 참조.

진입 트리거: "스킬 의심 지점 찾아 개선", "비판적으로 따져 다듬어", "벤치 돌려서 개선" 등.

## 0건 수렴까지 재벤치

벤치 라운드에서 잔류 이슈가 1건이라도 남으면 다음 라운드로 넘어간다. 사용자가 명시적으로 "이 정도면 됐다"·"여기서 멈추자"고 말하기 전에는 자체 판단으로 라운드를 종료하지 않는다. 사용자가 매번 "더 돌려"라고 시키지 않아도 0건 수렴까지 자동 진행한다.

- 다음 라운드는 **같은 시나리오로** 재측정한다. 시나리오를 바꾸면 0건이 보강 효과인지 압박이 약해진 것인지 안 갈린다.
- 보강 변경은 라운드별 커밋으로 분리해 사용자가 diff로 라운드별 효과를 검토할 수 있게 한다.
- 반복 상한은 글로벌 규칙 「검증은 수렴할 때까지 반복」을 따른다.
- "97% 통과면 충분하다"·"잔류 1건은 자연 표현이라 어쩔 수 없다" 같은 자체 만족 종료 금지. 잔류 1건이 다음 사용 때 같은 누설로 재발하면서 가이드 신뢰도가 무너진다.
- 적용 범위: 「의심 지점 개선 루프」, 「기능테스트」에서 벤치를 돌린 모든 경우.

## 기능테스트

스킬이 **설계대로 동작하는가**를 검증한다. 출력 품질이 아니라 오케스트레이션(분기, 순서, 에이전트 구성)이 대상이다.

### 정답은 위임한 문서까지 따라가 확정한다

벤치의 정답을 세울 때 스킬 본문에 적힌 요약을 그대로 쓰지 않는다. 그 요약이 원본과 어긋나 있을 가능성이 바로 벤치가 잡아야 할 대상이라, 그걸 정답으로 삼으면 처음부터 못 잰다. 스킬이 "저쪽이 단일 출처"라고 위임하고 있으면 그 문서를 열어 확정한다. 위임 대상이 또 다른 원본(마커·용어 정의 등)을 가리키면 거기까지 따라간다.

확정한 정답이 실제로 발동 가능한지도 함께 본다. 그 해석대로면 한 번도 발동할 수 없는 규칙이면 해석이 틀린 것이다.

- 서브에이전트 위임 구조 테스트와 gotchas는 [eval-delegation.md](eval-delegation.md) 참조. 특정 스킬의 벤치 대입값(단위 매핑·오라클·fixture)은 해당 스킬의 `specialized/` 파일 참조.
- description 트리거 정확도 측정(false negative/positive 정량)은 [trigger-eval-bench.md](specialized/trigger-eval-bench.md)를 따른다. skill-creator 표준 도구는 쓰지 않는다 — 사유와 대체 도구는 그 파일에 있다.
- 벤치를 돌리면 환경 격리·측정 도구 감사·종결 시 정리는 [bench-operations.md](specialized/bench-operations.md)를 따른다 — 회차 운용이든 단발이든 해당한다.

## Eval

- eval은 반드시 sonnet 모델로 실행한다. 이유: 스킬은 비용 효율적인 모델이 이해할 수 있는 수준으로 작성돼야 한다. opus에서만 동작하는 스킬은 실용적이지 않다.
- 예외: write-init·write-refine 스킬은 opus로 실행한다. 내용 풍부화와 톤·구조·분량 판단이 핵심이라 sonnet 기준으로 작성하면 가치가 휘발한다.
