# 여러 CLI에서 같이 도는 스킬 체크리스트

스킬은 한 CLI만 보고 쓰이지만 여러 CLI로 동시에 배포된다(전역 스킬은 Claude·Codex·Gemini로, 로컬 스킬은 `.claude/skills/`·`.agents/skills/`로). 그래서 한쪽 런타임이 채워주는 것에 기대어 쓴 문장은 다른 쪽에서 조용히 죽는다 — 에러가 아니라 **그 지시가 없었던 것처럼 진행**되므로, 산출물을 봐야 비로소 드러난다.

아래는 실측으로 확인된 차이만 담는다. 추정으로 항목을 늘리지 않는다.

## 스킬 파일 위치를 기준으로 다른 문서를 가리키지 않는다

런타임이 "이 스킬이 어디 있는지"를 모델에게 알려주는지가 갈린다. Claude Code는 스킬을 로드할 때 `Base directory for this skill: <절대경로>`를 함께 넣는다. Antigravity(Gemini)는 넣지 않는다 — 스킬 본문만 텍스트로 들어간다.

그래서 `../../contexts/foo.md` 같은 표기는 Claude에서는 풀리고, Gemini에서는 **기준점이 없어 못 푼다.** 실측에서 Gemini는 이 표기를 보고 엉뚱한 절대경로를 지어내 열려다 실패했다.

경로 문자열 자체는 멀쩡하다. 배포 타겟은 `skills/`와 `contexts/`를 형제로 두는 같은 모양이라 `../../contexts/`는 어느 타겟에서도 디스크상 정확하고, 없는 건 기준점뿐이다. 그래서 배포가 스킬 폴더의 각 md 맨 앞에 그 파일이 있는 절대 경로를 한 줄 심는다.

**다만 이 한 줄이 실제로 쓰이는지는 아직 측정되지 않았다.** 모델이 그 줄을 보고 경로를 계산해 준다는 전제이고, 안 되면 예전처럼 조용히 무시된다. 측정될 때까지는 아래 판정을 함께 적용한다.

판정 질문: **이 문서를 못 열어도 스킬이 성립하는가.**

- 성립한다(맥락 보강용 링크) → 상대 경로 그대로 둔다
- 성립하지 않는다(그 문서가 있어야 판단이 선다) → 레포 안에서 도는 스킬이면 레포 루트 기준 경로로 적는다. 작업 디렉터리가 레포 루트인 것은 양쪽에서 확인된 사실이라, 앵커와 달리 모델의 해석에 기대지 않는다

그리고 배포본을 직접 손대 앵커를 지우지 않는다 — 다음 sync에 덮이고, 그 사이 기준점 없는 스킬이 돈다.

규칙(`rules/`)은 스킬과 사정이 다르다. 타겟마다 사는 곳이 달라 상대 경로로는 맞출 수 없어서 `{{contexts}}` 자리표시자를 쓴다.

### 읽는 문서와 실행하는 스크립트는 표기가 다르다

전역 규칙 「글로벌 스킬 작성 규칙」에서 옮겨왔다. 위 판정과 같은 사정을 표기 쪽에서 본 것이다.

- **컨텍스트 파일 상대 경로 참조**: 전역 스킬(`SKILL.md`) 내에서 공통 컨텍스트 자산을 지시하거나 참조할 때는 절대 경로(예: `~/.gemini/contexts/`) 대신 배포 위치 기준의 상대 경로(`../../contexts/`)를 사용한다. 집 폴더 경로가 기기마다 달라 절대 경로는 깨진다.
- **단, 스크립트를 실행하라고 할 때는 자리표시자로 적는다**: 위 항목은 *읽는* 문서에만 해당한다. 실행은 자기 스킬 폴더 안이면 `{{skill_dir}}/<경로>`, 여러 스킬이 함께 쓰는 공용 스크립트면 `{{contexts}}/<파일>`로 적는다. 배포가 읽는 에이전트의 절대 경로로 채워주므로 어느 도구에서 불려도 같은 곳에 닿는다. 상대 경로나 특정 에이전트의 홈 경로(`~/.claude/...`)를 직접 적지 않는다.

## "찾아서 읽어라"에 기대지 않는다

Antigravity의 검색 도구는 시스템 `grep`을 호출한다. Windows 기본 환경에는 `grep`이 PATH에 없어 검색이 통째로 실패한다(`executable file not found in %PATH%`). 경로를 못 풀면 검색으로 대신 찾는 우회로가 있을 것 같지만, 그 우회로가 같은 환경에서 함께 막힌다.

- 위반: "해당 문서를 찾아서 읽는다", "레포에서 관련 규칙을 검색한다"처럼 탐색을 전제한 지시
- 정답: 읽어야 할 문서를 이름과 위치로 지목한다

검색이 스킬의 본체인 경우(코드 탐색 스킬 등)는 이 항목으로 잡지 않는다 — 그건 그 CLI에서 그 스킬이 안 도는 것이고, 문장을 고쳐 해결할 문제가 아니다.

## 이미 있는 규칙이 여기서 더 크게 문다

새 규칙이 아니라, 위반했을 때의 대가가 CLI가 갈릴 때 커지는 것들이다.

- **위임한 규칙의 부분 재기술** — 「책임 분리(SRP)」. 단일 출처와 재기술이 어긋나면 두 CLI가 서로 다른 판정을 내리고, 재기술 쪽이 틀렸어도 단일 출처를 못 여는 CLI에서는 바로잡을 방법이 없다
- **본문에 박은 셸 명령** — [lean-prompt.md 「상세 CLI 명령어 나열 금지」](lean-prompt.md). 한 CLI에서 되는 명령이 다른 쪽에서 안 먹으면, 스킬이 시킨 대로 한 모델이 실패한다

## 확인 방법

"읽으라고 한 문서를 실제로 읽었는가"는 산출물만 봐서는 모른다. 각 CLI가 남기는 대화 기록에 도구 호출이 인자까지 남으므로, 그걸 열어 확인한다.

- Claude Code — `~/.claude/projects/<인코딩된 경로>/<세션 id>.jsonl`
- Antigravity — `~/.gemini/antigravity-cli/conversations/<대화 id>.db` (SQLite `steps` 테이블)

스킬을 고친 뒤 같은 입력으로 양쪽을 돌려 이 기록을 대조하면, 고친 문장이 실제로 효과가 있었는지 판정된다.
