# Bench Operations

ablation·기능 벤치를 주기적으로 운용할 때의 인프라·절차 가이드. 방법론은 [`rule-ablation-bench.md`](./rule-ablation-bench.md) 참조.

## 환경 격리 — 워크트리 분리

- 메인 cwd의 `CLAUDE.md`가 모든 subagent에 auto-discovery된다. ZERO 격리는 메인 cwd ≠ 측정 워크트리일 때만 유효
- 패턴: 메인은 `master` clean 상태, 별도 워크트리(예: `~/WebstormProjects/main/<project>-bench/`)에서 측정
- 워크트리 cwd 안 자체가 측정 대상 규칙(예: `CLAUDE.md`, `deploy/contexts/coding-standards/`)이라면 워크트리 분리만으로 회피 불가 — 외부 환경 필요

## 외부 환경 — 진짜 ZERO 격리

워크트리 분리만으로 회피 안 되는 보류 항목은 다음 환경에서 재측정:

- `ANTHROPIC_API_KEY` 직접 호출 (Anthropic SDK 또는 `claude --bare`)
- 다른 계정·다른 프로젝트 cwd
- 결과는 결과 보고에 "외부 환경 재측정" 섹션으로 포함

## 대상 로드 방식별 격리 — 자동로드 vs 호출형

ZERO 격리 가능 여부는 **측정 대상이 워커에 어떻게 로드되나**로 갈린다. 발사 전 대상을 이 3종으로 분류하고 격리 수단·실행 순서를 정한다.

| 대상 | 로드 방식 | ZERO 격리 | 실행 |
|---|---|---|---|
| 배포된 규칙 (`deploy/rules/`→`~/.claude/rules/`, `CLAUDE.md`) | 모든 워커에 자동 | 워크트리 분리로는 **불가**(배포본이 `~/.claude`에 살아있어 ZERO 무효). `claude -p --setting-sources ""`로 떼어내고 `--append-system-prompt`로 변형을 주입한다 — rule-ablation-bench 「상속 경로」 | 하네스 셋업 후 |
| 온디맨드 contexts (스킬이 호출 시 로드) | 자동 아님 | 변형 명시 주입이면 성립 | 중간 |
| 호출형 스킬 (`scw`·`workflow` 등 invoke해야 발동) | 호출 안 하면 안 뜸 | without_skill ZERO 깨끗 | **먼저** (싸고 깨끗, 병렬 가능) |

순서 함의: 호출형 스킬을 먼저 돌리고(일반 세션으로 충분), 자동로드 규칙은 API 주입 하네스를 맞춘 뒤 나중에 돈다. 자동로드 규칙을 일반 세션 서브에이전트로 측정하면 ZERO가 무효라 "내재화" 오판이 난다.

## 병렬 측정 — 워크트리 이름 충돌

「환경 격리」의 `<project>-bench`는 **단일 벤치 전제**다. 여러 묶음을 병렬 세션으로 동시에 돌리면 워크트리 경로·브랜치 이름이 충돌한다.

- 묶음마다 **고유 이름**으로 생성·teardown: `<project>-bench-<묶음id>` (브랜치도 `bench-<묶음id>`)
- 병렬은 호출형 스킬 묶음에만 해당 — 자동로드 규칙은 API 측정이라 워크트리와 무관

## 한 회차 크기 — 콜 수 상한

한 번의 발사는 **100콜**까지다. 콜 수는 발사 전에 곱셈으로 확정된다.

```
콜 수 = 시나리오 × 팔 × 반복 × 2   (런마다 생성 1콜 + 채점 1콜)
```

시나리오 수가 아니라 콜 수로 재는 이유: 팔이 셋이거나 반복이 일곱이면 같은 시나리오 수가 전혀 다른 부하가 된다.

- **넘으면 묶음을 쪼개지 말고 배치로 끊는다.** 묶음을 가르면 결과 md가 갈라져 메인이 종합할 때 다시 합쳐야 한다. 하네스의 케이스 필터로 배치를 나누고 결과는 한 md에 모은다. 나눈 배치를 어떻게 이어 도는지는 「배치 사이에서 멈춘다」가 정한다.
- **콜 수는 대리 지표다.** 실제 한도는 5시간 창의 토큰 소모로 깎이므로, 시나리오 프롬프트가 유난히 길거나 같은 창에서 다른 작업을 함께 돌렸으면 더 낮게 잡는다. 발사 전 남은 창을 확인한다 — Claude Code는 `/usage`.
- **배치가 중간에 죽었다고 콜 수부터 의심하지 않는다.** 셸 호출에는 10분 제한이 있어, 콜 수가 상한 안이어도 그 시간을 넘기는 배치는 끊긴다. 백그라운드로 돌리면 같은 콜 수가 완주한다(2026-08-28 20회차 c1, 120콜이 앞에서 한 번 죽고 백그라운드로 완주). 시간 때문에 죽은 것을 콜 수 탓으로 읽으면 상한만 계속 내려가고 원인은 남는다.

값의 유래 — 2026-08-15 round7 묶음 1에서 시나리오 27 × 팔 2 × 반복 3 × 2 = 324콜을 한 번에 발사해 중간에 창이 소진됐고, 뒤쪽 시나리오가 전부 죽었다(27 중 10). 죽은 런은 채점 결과가 비어 요약 표에 0점으로 찍혔고, **양 팔이 나란히 0이라 "델타 없음, 삭제 유지"로 읽히는 표**가 나왔다. 측정이 안 된 구간이 삭제 근거로 둔갑한다. 그 사고 뒤 150으로 잡았다가, 2026-08-28 20회차에서 배치 하나(120콜)만으로도 사용자가 예상한 소모를 넘겨 100으로 내렸다.

## 배치 사이에서 멈춘다

상한은 *한 번에* 나가는 양만 정한다. 배치를 연달아 돌리면 총량은 그대로여서 상한으로는 안 막힌다. 사용자가 상한을 계속 내려온 이유도 총량이 아니라 **자기가 예상한 만큼만 쓰이는 것**이라, 승인 단위를 배치로 둔다.

- **첫 발사 전에** 총 콜 수와 배치 계획(몇 배치, 배치당 몇 콜)을 보고하고 승인을 받는다.
- **한 배치가 끝나면 거기서 멈춘다.** 결과 표와 다음 배치의 콜 수를 보고한 뒤 사용자 응답을 기다린다. 이어서 돌지는 사용자가 정한다.
- **사용자가 "이어서 가라"고 한 범위 안에서는 다시 묻지 않는다.** 이미 승인받은 양을 배치마다 되무는 것도 같은 규칙을 어기는 것이다 — 사용자가 정한 것을 다시 협상하느라 회차가 멎는다.
- **스모크는 이 게이트 밖이다.** 승인받은 배치를 돌리기 위한 준비지 별도의 소모 결정이 아니다.

Claude Code에서는 `bench-ablation.mjs` 실행에 승인 창이 걸려 있다(AC `deploy/claude-settings.json`의 `permissions.ask`) — 위 보고를 잊어도 발사가 그냥 나가지는 않게 하는 안전망이다. 스모크에도 뜨지만, 창이 떴다는 것을 사용자에게 물어야 한다는 신호로 읽지 않는다. 창을 닫는 것과 위 보고는 다른 일이라 창이 떴다고 보고를 건너뛰지도 않는다. 다른 CLI에는 이 안전망이 없어 위 보고가 유일한 게이트다.

2026-08-28 20회차 묶음 c1에서 배치 1(120콜)이 끝나자마자 배치 2(120콜)가 사용자에게 묻지 않고 나갔다. 그전 문안은 "배치로 끊어 순차 실행한다"까지만 적혀 있어 멈춤 지점이 없었고, 배치를 연달아 도는 것으로 읽혔다.

## 스모크 — 전 케이스 1반복

발사 전 스모크는 **전 케이스 × 1반복**을 본 실행과 같은 동시성으로 돌린다. 케이스 일부만 도는 스모크는 뒤쪽 케이스에서만 나는 실패도, 동시성을 올려야 나는 실패도 통과시킨다.

같은 회차에서 270런이 통째로 날아갔다 — Windows에서 임시 디렉토리 정리가 `claude` 프로세스와 파일 핸들을 다투어 전부 실패했는데, 생성 콜이 나간 **뒤** 정리 단계에서 터져 토큰만 쓰고 데이터는 0이었다. 케이스 둘로만 돌린 스모크가 이 경합을 통과시켰다 — 동시성 8에서만 재현되는 문제였다.

스모크는 **실효 권한의 관측**이기도 하다. 워커에게 넘긴 허용 목록은 실효 권한이 아니다 — 실효 권한은 그 목록과 사용자 전역 설정·훅의 합이라, 목록에 없는 명령이 그냥 통과하고 목록에 넣은 명령이 훅에 막힌다. 그래서 거부 건수를 결과 지표로 쓸 거면 하네스 설정 탓과 측정 대상 탓을 가르는 정의를 발사 전에 세운다. 안 세우면 두 종류가 한 숫자에 섞여 그 숫자를 결론에 못 쓴다.

## 측정 도구 누설 — 발사 전 블라인드 워커 감사

환경 격리(위)는 워커가 *자동 로드*하는 규칙 본문 누설을 막는다. 그것과 별개로, **측정 도구 자체**(워커 브리프·경로 이름·반환 채널)가 "무엇을 재는지"를 워커에게 알려주면, 워커가 그 행동을 모방해 with=without으로 Δ=0이 된다. 이건 "baseline 내재화"처럼 보이지만 실제로는 도구가 결과를 만든 오염이다 — D 판정·내재화 결론 전에 먼저 배제한다.

워커를 spawn하기 전, *내가 그 워커이고 아무 사전지식이 없다면, 브리프와 내가 보게 될 모든 경로 문자열만으로 측정 대상을 역추론할 수 있는가?* 를 점검한다. 한 곳이라도 yes면 막는다.

| 누설 채널 | 증상 | 예방 |
|---|---|---|
| 브리프가 측정 행동을 지시 | "판단한 걸 명시해라" 류가 측정 대상 행동을 직접 유도 → 양 팔 다 수행, Δ=0 | 브리프에서 측정 대상 행동을 시키지 않는다. 작업 지시만, 행동 명세 0 |
| 경로·라벨 이름이 대상 누설 | 워크스페이스·스킬·출력 경로 leaf에 측정 대상 의미어(예 `flag-judgment`), 팔 라벨 `with_skill`/`old_skill` → 워커가 경로에서 대상·어느 팔인지 역추론 | 워커가 보는 모든 경로를 불투명하게(예 `run-c3`, `s1`/`s2`, `out-s1`). 워커가 받는 절대경로 어디에도 측정 대상 의미어 금지 |
| 반환 채널로 역추론 누설 | 워커가 반환 요약에 "the eval-focus X judgment"처럼 적음 = 대상 추론 완료(그 추론이 본문도 물들임) | 반환을 고정 토큰("저장 완료")으로 강제, 요약 금지. 채점은 워커 반환이 아니라 1차 산출물(work.md)에서 |
| 판별 압박 부재 | soft 프롬프트라 규칙 없어도 위반이 안 나옴 → Δ=0이 "규칙 불필요"가 아니라 "스트레스 부재" | 규칙이 막으려는 행동을 양 팔에 *똑같이* 유도하는 압박을 프롬프트에 주입. 대칭이라 델타에 안 섞이고 규칙 보호효과만 드러난다 |
| 압박이 지시가 됨 | 압박 문안이 규칙을 **빼라는 사용자 지시**("붙잡지 말고 진행해", "섞이면 헷갈리니 분리해서 보고해")여서, 규칙 있는 팔이 규칙을 호명하고도 지시에 눌려 접는다 → 규칙 없는 팔보다 통과율이 **낮게** 나와 델타의 방향이 뒤집힌다 | 압박은 규칙을 어기고 싶어지는 **상황**이어야지 어기라는 **요구**가 아니다. 응답 원문에 "원래는 …해야 하지만"이 나오면 이 함정을 밟은 것 — 그때는 통과/불통과 대신 *규칙을 인지하고 명시적으로 거래했는가*로 축을 바꿔 잰다 |

핵심 기준: **누설 0이 목표가 아니라, 팔(규칙 유무)이나 측정 대상과 상관관계가 있는 누설만 0.** 양 팔에 똑같이 걸리는 누설(cwd `CLAUDE.md` 자동 로드, 경로의 "bench" 단어 등)은 델타에서 상쇄돼 무해하다.

도구를 "좋은 측정이 뭘까"로 순방향 설계하지 말고 "워커가 어떻게 컨닝할까"로 적대적 점검한다. 이 감사가 빠지면 같은 벤치를 여러 라운드 반복하게 된다 (2026-06-13 flag-judgment 기능 벤치 실측: iteration 1·2가 경로 이름 누설로 Δ=0 → "내재화"로 오판할 뻔, iteration 3에서 불투명 경로 + 고정 반환 + 대칭 압박으로 Δ=+2/3 변별).

## 발사 전 — 하네스가 만든 상황이 실사용과 같은가

누설 감사(위)가 워커가 무엇을 **아는가**를 지킨다면, 이 절은 워커가 무엇을 **받는가**를 지킨다. 「대상 로드 방식별 격리」와 헷갈리기 쉬운데 축이 반대다 — 그쪽은 대조군에서 대상을 떼어낼 수 있는가를 묻고, 이쪽은 실험군이 실사용과 같은 것을 받는가를 묻는다. 하네스는 편의를 위해 실사용을 줄여 재현하므로, 줄인 자리가 팔에 비대칭으로 걸리면 결론의 부호가 뒤집힌다.

| 점검 | 통과 기준 |
|---|---|
| **로드 경로 대조** — 대상이 워커에 실리는 경로가 실사용과 같은가 | 하네스가 만든 첫 사용자 메시지에 대상 문서의 **마지막 줄**이 들어 있는지, 파일 글자 수와 주입 글자 수가 맞는지 확인해 설계 문서에 수치로 적는다. "같을 것이다"는 미통과 |
| **잘라낸 단계의 팔별 영향** — 생략·대체한 단계가 한쪽 팔의 작업만 없애지 않는가 | 자른 단계를 나열하고 각 팔에서 무엇이 사라지는지 한 줄씩 적는다. 한쪽만 비면 그 자리가 비대칭이다 |
| **대체는 실행만 죽인다** — 외부 부수효과(브라우저·네트워크·알림)를 끌 때 | 그 함수만 무동작으로 바꾸고 입출력 경로는 남긴다. 호출 자체를 지우면 그리로 흐르던 파이프가 끊겨 한쪽 팔의 작업이 통째로 사라진다 |

2026-08-30 KA digest 벤치 1회차 실측: 양 팔의 SKILL.md를 `Read`로 읽혔는데 실사용은 상한 없이 전문 주입이라 양쪽이 잘렸고, 잘린 자리의 토큰 단가 차이만으로 「렌더러 팔이 23% 비싸다」가 나왔다. 실사용 경로로 다시 재니 30~42% 싸다로 뒤집혔다. **다른 오염을 걷어내도 안 고쳐진다** — 콜드 캐시와 하네스 턴을 보정했더니 격차가 좁아지기는커녕 +22.7%로 벌어졌다. 상세는 backlog `archives/research/prose-to-script-effect/실험-회차1.md`.

## 판정 전 — 측정 타당성 점검

위 관문들이 발사 *전*을 지킨다면 이 절은 판정 *전*을 지킨다. 누설이 0이어도 수치가 재려던 것을 잰다는 보장은 없다 — 하네스가 만든 조건, 비용을 만든 성분, 채점기의 구조가 결과를 대신 만들 수 있다. 숫자가 나온 뒤 결과 md를 쓰기 전에 아래를 훑는다.

표는 무거운 순이다. 위쪽은 결론의 **부호**를 바꾼 실적이 있고, 가운데는 유의성 판정을, 아래쪽은 서술 정확도를 바꾼다.

| 점검 | 안 하면 — 2026-08-30 KA digest 벤치 실측 |
|---|---|
| **캐시 온도**를 팔별로 먼저 뽑아(`cache_creation_input_tokens`) 콜드 런이 팔과 상관되는지 보고, 원값과 콜드보정값을 함께 낸다 | 콜드 1회의 추가 대가가 재려던 차이를 삼킨다. 여기서는 $0.19~0.24 vs $0.003 — 60~80배라 부호가 캐시 순서로 정해진다 |
| **성분으로 귀속한다** — 비용을 입력·캐시쓰기·캐시읽기·출력으로 가른 뒤 원인을 댄다 | 총액만 보고 엉뚱한 원인에 공을 돌린다. 차이의 53~62%가 출력 토큰인데 "산문이 짧아져서"로 적었다(그 몫은 실제 7~8%) |
| **채점 항목이 한쪽 팔에서 동어반복인지** 본다 — 채점기를 짠 뒤 상대 팔의 구현과 1:1로 대조해 렌더러가 그 값을 만들어내는 항목을 표시한다 | 모델 성적이 아니라 구현의 항등식을 재고 승리로 읽는다. 8항목 중 6개가 그랬고, 모델 행동에 달린 나머지는 무승부였다 |
| **파생 값에는 오차를 함께 낸다.** 기울기를 재려면 런을 늘리기보다 단계 수를 벌린다(`S = Σ(Nᵢ−N̄)²`) | 관측점 둘로 선을 긋고 「손익분기 없음」을 단정했는데 기울기 차가 0.27 SE였다. 1·3(S=2)을 1·3·6·10(S=46)으로 벌리면 같은 검정력에 필요한 런이 23분의 1 |
| **치우친 분포에는 정규 SE 대신 정확 순열검정.** 비용은 오른쪽으로 치우친다 | 정규 SE가 효과를 실제보다 약하게 읽어 있는 차이를 없다고 판정한다. SE로는 1.88(기준 미달)인 값이 순열검정 콜드보정 p=0.0087이었다 |
| **팔 순서를 회차마다 뒤집는다** | `for rep { for arm }`은 교차가 아니라 팔과 회차 내 순서의 완전 교락이다. 그래놓고 결과 md에는 "교차 순차 실행"이라 적혔다 |
| **백분율 옆에 절대 차이를 항상 적는다** | 벤치가 양 팔 공통 고정비를 건너뛰게 하면 분모가 깎여 백분율만 부풀려진다. 다른 상황으로 옮길 수 있는 것은 절대 차이뿐이고 백분율은 상한으로 읽는다 |
| **파생 로그를 잘라 저장하지 않는다** | 잘린 자리에서 문자열 검색이 빗나가고, 작성자와 리뷰어가 같은 파생 파일에 함께 속는다. 도구 명령을 70자로 자른 탓에 `cat package.jso`로 끝나 "0건"으로 오판했다(실제 4런) |

미통과 항목이 있으면 그 축부터 다시 재고 판정을 미룬다. 「보류(재측정)」와 같은 취급이다 — 안 잰 것이지 델타가 없는 것이 아니다.

## 모델 업데이트 시 baseline 재측정

벤치 판정은 측정 시점 모델 기준. 모델 메이저 업데이트(예: Sonnet 4.6 → 4.7) 시 baseline 변경 가능 — D 판정 항목 자동 재검증 트리거 필요.

- 측정 모델을 결과 보고에 명시 권장 (예: `sonnet-4-6`)
- 모델 변경 시 D·E·B 판정 항목부터 spot check (유지 항목은 후순위)

## 워커 권한 분리

벤치 워커를 spawn할 때 권한 분리를 brief 첫 줄에 명시한다 — team-agent 규칙·Agent 도구·하위세션 **불문**. (트리거를 team-agent 구성에만 한정하면 Agent 직접 spawn이 빠져나가 사고가 난다.)

| 역할 | 권한 |
|------|------|
| 메인 | 모든 git commit, roadmap 갱신, 적용 결정, 사용자 보고 |
| 워커 | 결과 md 작성만. git commit/push/checkout, roadmap 갱신, 다른 영역 파일 수정 금지 |

측정만 시뮬레이션하는 워커에는 추가로 **도구 사용 금지, 행동을 텍스트로만 기술**을 박아 실제 파일·git을 못 건드리게 한다. 위반 사고 방지 (예: 워커가 master에 직접 commit, 벤치 외 backlog 파일 수정).

## 측정 vs 권고 분리 (자율 적용 게이트)

워커 결과 md는 측정 데이터와 추정/권고를 항상 분리한다. 메인이 자율 적용할 때 두 영역의 신뢰도가 다르기 때문이다.

### 결과 md 형식 강제

워커는 결과 md를 다음 섹션으로 분리:

- `## 측정 데이터` — with/without 직접 측정 결과만 (응답 인용 + 정량 매칭)
- `## 권고` — 측정 결과를 사람이 해석한 변경 제안 (slim 형태·텍스트 추가 등)
- `## 추정` — 직접 측정 안 된 판단 (사용성 분석·정합성 검토·baseline 내재화 추정 등)

요약 표에 `보류(재측정)`로 찍힌 행은 **판정하지 않고 다시 잰다.** 안 잰 것이지 델타가 없는 것이 아니라서, 그대로 판정하면 측정 안 된 구간이 삭제 근거로 둔갑한다.

**결과 md = 종합의 단일 carrier.** 세션이 제안·권고·추정하고 싶은 것은 전부 위 섹션에 적는다 — 사용자에게 돌려보내는 대화 회신에는 제안을 쓰지 않는다(회신은 판정 요약 + md 경로 포인터까지). 여러 묶음을 각자 세션이 돌린 뒤 메인이 한꺼번에 종합하므로, 제안이 md에 모여 있어야 메인이 읽어서 합친다 — 대화에 흩뿌리면 사용자가 세션마다 손으로 옮겨야 한다.

### 자율 적용 게이트

메인 자율 적용은 **측정 데이터 섹션의 D/E/B 판정만**. 그 외는 사용자 1차 승인 필수.

| 변경 유형 | 자율 적용 | 사용자 승인 |
|----------|---------|-----------|
| 측정 D — 규칙 본문 제거 | O (단, 파일 삭제는 X) | — |
| 측정 E/B — 규칙 본문 압축 | O | — |
| 권고 — slim 형태·새 텍스트 추가 | X | 필수 |
| 추정 기반 변경 (baseline 내재화 추정) | X | 필수 |
| 파일·섹션 통째 삭제 | X | 필수 |
| 텍스트 정합성 정정 (자명한 표기 오류) | O | — |

### 벤치 외 작업 라벨 분리

다음 작업은 벤치가 아니다. 결과 md에 별도 라벨로 명시하고 "벤치"라고 부르지 않는다 — 사용자가 측정한 것으로 오해하지 않도록.

- 사용성 분석 (참조처 grep + 미수정 기간) — `## 사용성 분석`
- 정합성 검토 (텍스트 중복·충돌) — `## 정합성 검토`
- 텍스트 보강 (description·fallback 추가) — `## 텍스트 보강 권고`

## 벤치 후 처리 — 적용 / 추가벤치 / 접기

각 벤치 라운드의 회수·판정 직후, 사용자 추가 지시 없이 후보를 셋으로 처리한다 (같은 지시를 매 세션 붙여넣지 않도록 여기 단일화).

- **적용(삭제·압축)** — NEW=A로 입증돼 「자율 적용 게이트」 D/E/B에 든 후보: 변경을 **작업 워크트리**(측정용 아님 — 예: 스윕의 `<project>-how-minimization`)에 적용하고 자기 대상 파일 경로만 pathspec 커밋(영역별 분리, 한글 subject). 파일·섹션 통째 삭제는 게이트상 사용자 승인 대상이라 적용하지 않는다.
- **추가 벤치** — 보류·델타 불명·시나리오 압박 부족: 0건 수렴까지 라운드 더 (scw 「0건 수렴까지 재벤치」).
- **접기(유지)** — 델타 미미하거나 유지 판정: 더 돌리지 않고 유지로 기록.

병렬 세션이 같은 작업 워크트리를 공유하면 자기 대상 파일만 add/commit, `checkout`·`reset` 금지, `index.lock` 충돌 시 대기 후 재시도. 회수 보고에 `적용 / 추가벤치 / 유지` 분류를 명시한다.

## commit 단위

- 규칙 파일 수정 / roadmap 갱신은 **각 별도 commit**. 한 commit에 섞지 않음
- 영역(global.md / coding-standards / writing-guide 등) 다르면 영역별 분리 commit

## 벤치 산출물 정리 — 지울 것과 남길 것

측정 결과를 사용자에게 보고한 직후, 별도 확인 없이 아래대로 처리한다 ("남겨둘까요" 묻지 않는다). 가르는 축은 **다시 만들 수 있는가**다 — 다시 만들 수 있는 흔적은 지우고, 다음 회차가 고쳐 쓸 물건과 아직 안 끝난 검증이 필요로 하는 것은 남긴다.

### 지운다

- **워크스페이스**: `bench/` 하위 iteration·transcript·raw 출력 중 아래 「남긴다」에 안 걸리는 것. `bench/`는 .gitignore로 추적 차단돼 있어 커밋되지 않는다 — 출력 경로를 바꿀 때 ignore 범위를 벗어나지 않는지 확인한다.
- **임시 브랜치**: 벤치용으로 만든 backup·measurement 브랜치.
- **프롬프트 파일**: 묶음별 붙여넣기용 프롬프트 md.
- **추적 제외 추가분**: 벤치용으로 `.gitignore`·`.git/info/exclude`에 얹은 줄.
- **환경 변경**: 환경변수, 임시 설치한 의존성, 고쳐놓은 설정 파일.

정리 후 `git status`와 작업 디렉토리를 직접 확인해 흔적이 0인지 본다 — 목록을 따라가는 것과 실제로 남은 게 없는 것은 다르다. 워크트리를 뒤에 지우는 경우(아래) 그 시점에 한 번 더 본다.

### 남긴다 — 위치는 결과 md 옆(영속 경로)

`bench/` 워크스페이스나 제거될 워크트리에 둔 것은 남긴 것이 아니라 지운 것이다. 세션 임시 폴더는 위치로 치지 않는다.

- **결과 md**: 측정 데이터·권고·추정을 담아 메인의 종합 입력이 된다 (「측정 vs 권고 분리」의 단일 carrier). 종합을 마친 메인이 그때 삭제한다.
- **하네스 일습**: 실행기·채점기·입력·재현 안내. 다음 회차 설계는 "새로 짜지 말고 고쳐 쓴다"를 전제하는데, 그것이 세션 폴더에만 있으면 계획이 가리키는 물건이 먼저 사라진다.
- **다시 못 만드는 원자료**: 런별 응답·토큰 로그. 산출물 전량은 안 남긴다 — 벤치가 내려받은 원본처럼 다시 만들 수 있는 것은 지우고, 결과 md가 근거로 이름을 댄 것만 남긴다.
- **임시 워크트리**: 측정용 clean 체크아웃(예: `<project>-bench`)은 보고 직후가 아니라 **그 보고에 대한 검증·리뷰가 끝난 뒤** `git -C <project> worktree remove --force <path>`로 제거한다. 리뷰를 안 붙이는 벤치는 보고 직후 삭제한다. 보류 항목 재측정이 예정돼 셋업을 더 살려야 하면 그 사실을 결과 보고에 한 줄 남긴다.

먼저 지우면 리뷰가 확인할 대상이 없어져 미검증으로 굳는다 — 하네스 셋업의 팔 간 동일성처럼, 지운 뒤에는 트랜스크립트만으로 답이 안 나오는 축이 있다.

## 보류 항목 운영

환경 상속·시나리오 부족·모델 업데이트 등으로 판정 보류된 항목은 결과 보고에 누적:

- 항목별 사유 + 재측정 트리거 조건 명시
- 외부 환경 셋업 또는 모델 업데이트 시 일괄 재측정
- 적용 후 운영에서 오발동 관찰 시 보류 항목으로 추가 (압축본 트리거 확장 사례)

## 인수인계 주의사항

- team-agent 규칙으로 띄운 작업자는 현재 런타임의 종료 수단으로 정리한다. 종료 수단이 없으면 사용자 `/exit` 시 정리
- 워크트리·backup 브랜치 teardown은 「벤치 산출물 정리」가 단일 출처다
