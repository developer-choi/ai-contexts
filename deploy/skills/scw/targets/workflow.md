# Workflow 특화 체크리스트

`skills/workflow/` 리뷰 시 추가로 점검하는 항목.

## 신설 룰의 일반화 — 세션 직접 호명 회피

세션 이름 직접 호명은 [다른 파일의 번호·내부 구조는 역할 이름으로](../../../contexts/prompt-standards/sources-and-links.md#다른-파일의-번호내부-구조는-역할-이름으로-부른다)로 본다. 리뷰 시 본문에 다음이 등장하면 후보다:

- **세션 이름 직접 호명** — `BACKGROUND_SESSION`, `PLANNING_SESSION`, `IMPLEMENTATION_SESSION`, `WRITING_SESSION` 등

## 산출물 정의의 옵션 인식 유발 문구

[약한 어휘는 지우고 강조 라벨은 붙이지 않는다](../../../contexts/prompt-standards/wording.md#약한-어휘는-지우고-강조-라벨은-붙이지-않는다)로 본다. 적용 대상: step-4 산출물 정의 표 등.

## 산출물 라이프사이클

산출물이 살아있는 동안 결정 진화에 따라 동기화 부담이 누적되는 패턴 방지.

라이프사이클 폴더(`persistent/`·`retained/`·`consumable/`)는 그 자체가 정리 시점을 표현하는 메커니즘이다. 본문 룰은 그 메커니즘을 보조하는 형태로, 폴더 분류가 일관·정합·최소 수명으로 유지되는지를 본다. 폴더 구조 정의는 workflow SKILL.md 「/plan/ 폴더 구조」 참조.

### 폴더 분류 부재 검토

새로 도입되거나 기존에 존재하는 산출물이 라이프사이클 폴더 중 하나에 분류되어 있는지 본다.

- `pr{N}/` 또는 `background/` **직속에 박혀 있는 산출물**(폴더 분류 없음)이 있는지 — 미분류 항목은 정리 시점이 메커니즘으로 표현되지 못하므로 별도 식별해 분류 결정을 유도한다.
- 분류 보류 사유가 산출물 정의(또는 폴더 구조 다이어그램 주석)에 적혀 있는지 — 없으면 "왜 미분류인지" 사유를 함께 박도록 보강 제안.

### 폴더 디폴트 매핑 가이드

새 산출물을 도입하거나 기존 산출물의 폴더 분류를 검토할 때 적용하는 디폴트:

| 산출물 특성 | 디폴트 폴더 |
|---|---|
| 한 step만 소비 / 큐 모델 적용 가능 (절 단위 소비) | `consumable/` |
| 본 PR 여러 step이 소비, PR 종료 후 폐기 OK | `retained/` |
| PR·프로젝트 종료 후에도 가치 (회사 컨텍스트 의존 결정·컨벤션 인덱스 등) 또는 보존 기간이 PR 라이프타임을 넘는 경우 (구현 인수인계 등) | `persistent/` |

`consumable/`이 기본값이다. `retained/`·`persistent/`로 올리는 산출물은 그 사유가 산출물 정의에 명시되어 있는지 본다 — 사유 없이 올라가 있으면 수명을 부풀리는 방향으로 흘러간 흔적이다.

### 폴더 분류와 사용처의 정합

산출물의 폴더 분류와 사용처 step 목록이 일관되는지 본다.

- **`consumable/`인데 복수 step이 소비**하는 경우 — 큐 모델(절 단위 소비)이 실제로 적용 가능한지 확인. 절 단위로 깔끔히 갈라지지 않으면 `retained/`로 올리는 게 맞다.
- **`persistent/`인데 PR 라이프타임 안에서만 소비**되고 외부 가치가 없는 경우 — `retained/`로 내리는 게 맞다. 단 보존 기간이 PR 라이프타임을 넘어야 하는 구현 인수인계 산출물(`implementation.md`)은 예외 — `persistent/`에 두고 사용자 명시 폐기 시점까지 보존.

폴더가 정리 시점을 표현하므로 본문 규칙으로 "어느 step 직후 정리" 같은 정리 시점을 반복 명시하지 않는다. 그 대신 폴더 분류 자체의 적정성에 무게를 둔다.

## step-4 vs step-5 코드 작성 경계

step-4(stub)와 step-5(IMPL) 모두 코드를 작성하므로 경계가 흐려진다. 항목별 경계를 직접 명시.

### 모든 파일·함수·컴포넌트 stub 필수

PR에서 만들 **모든 파일·함수·컴포넌트는 step-4에서 stub으로 생성**한다. 외부 공개 여부 무관 — 내부 헬퍼·내부 컴포넌트도 시그니처 + `throw new Error('not implemented')`로 stub.

두 가치:
- **구조 가시화**: PR이 가져온 마크업을 로직 컨테이너로 감싸고 hook을 호출하면, 그 컨테이너·hook도 stub으로 만들어 로직 구조를 한눈에 파악. IMPL은 본문만 채움
- **PR 병렬 기반**: 외부 공개 인터페이스가 stub에 드러나야 후속 PR이 의존 가능

### 항목별 경계 매핑

| 항목 | step-4 | step-5 |
|---|---|---|
| 외부 공개 모듈 시그니처 (export 함수·컴포넌트·hook) | ○ 필수 | — |
| 내부 함수·컴포넌트 시그니처 | ○ 필수 (시그니처 + throw) | — |
| 함수 본문 (짧고 결정됨) | ○ 직접 적어도 OK | — |
| 결정된 분기 (짧은 가드) | ○ 직접 | — |
| 복잡 분기 (가드 + switch + 매핑) | 한글 명세 | ○ 본문 |
| 타입·상수 정의 | ○ | — |
| 테스트 케이스 시그니처 | ○ `it.todo('자연어')` | — |
| 테스트 본문 | — | ○ `it(...)` |

### 점검 항목 (scw 리뷰)

- step-4 stub에 함수 본문이 길게 박혀 있는지 — 한글 명세로 바꿔야 하는 후보
- step-4에서 **내부 로직 함수·컴포넌트 stub이 누락**됐는지 — 로직 구조 가시화 깨짐 신호 (PR 안 호출 그래프·로직 컨테이너 트리가 stub에 드러나지 않음)
- step-5에서 **외부 공개 시그니처가 변경**됐는지 — step-4 누락 신호 (후속 PR 의존 깨짐)
- step-5에서 결정된 분기·매핑·상수가 새로 추가됐는지 — step-4 누락 또는 step-5에서 새 결정 발생

### 사례

- ❌ Bad: step-4에 외부 공개만 stub하고 내부 로직 컨테이너·hook 누락 — 구조 파악 불가
- ❌ Bad: step-5에서 `add(a, b)` → `add(a, b, options)` 시그니처 변경 — step-4 누락. 후속 PR 의존 깨짐

### 엄격도

- **필수 (위반 카운트)**: 모든 로직 파일·함수·컴포넌트 stub 생성, 외부 공개 시그니처 안정성
- **방향 가이드 (후보 식별 → 사용자 보고)**: 함수 본문이 짧으면 직접 / 길면 한글 명세 — 분량 경계는 case by case

## 의존성 그래프 점검

step·세션을 추가·이동하거나 순서를 손볼 때, 직렬로 적힌 것이 진짜 산출물 의존인지 양방향으로 본다.

- **산출물 단위로 식별한다** — "세션 X 끝나면" 같은 거친 단위가 아니라 `X.step-N의 산출물 파일`로. 그 단위로 현 본문의 "X 다음에 Y" 표기와 1:1 대조한다
- **과직렬** — 산출물 의존이 없는데 직렬로 박힌 것은 "X·Y 병렬 진행 가능"으로 푼다. 부분 의존이면 충돌 조건만 짚고 전체 순서를 강제하지 않는다
- **새 항목의 파급** — 새 세션·step이 기존 선행/후속 관계를 깨거나 가짜 의존으로 만드는지. 모드별 그래프가 따로 있으면 각각 확인

## Step-Skill 오케스트레이션

step이 스킬을 오케스트레이션하는 구조를 따르고 있는지.

- 오케스트레이터 step에 **스킬 선택 테이블**이 있는지 (작업 종류 → 스킬 매핑)
- 새로 추가된 스킬이 해당 step의 스킬 선택 테이블에 등록되어 있는지
- 스킬 선택 테이블의 스킬은 [독립 호출](../../../contexts/prompt-standards/skill-structure.md#독립-호출)로 본다

### 산출물 체이닝

각 step의 산출물이 다음 step의 입력으로 연결되는지.

- 산출물 경로가 스킬의 SKILL.md와 step 파일 **양쪽에** 명시되어 있는지
- 다음 step의 **참고 자료**가 이전 step의 산출물 경로와 일치하는지
- Lead가 `/plan/` 하위를 탐색하여 산출물을 파악하고 팀에게 분배하는지
- 파생 산출물이 그것을 읽어야 하는 에이전트에게 실제로 주입되는지

### 스킬 로드 테이블 정합성

- 오케스트레이션 step에 스킬 로드 테이블이 있는가

### 컨텍스트 비대화 검토

[한 파일에는 같은 시점에 읽히는 것만](../../../contexts/prompt-standards/file-layout.md#한-파일에는-같은-시점에-읽히는-것만-담는다)로 본다. 대상: 세션/에이전트가 이후 step에서 불필요한 컨텍스트를 누적하고 있지 않은가.

- 분리가 필요하다면 서브에이전트(일회성 분석)로 충분한가, 별도 세션(지속적 작업)이 필요한가
- 에이전트가 스스로 폴더를 탐색(glob/grep)하지 않고, Lead가 주입한 경로의 파일만 읽는지
- Markup/Feature Implementer의 컨텍스트가 격리되는지 (CSS 컨텍스트가 Feature에 오염되지 않는지)

### 팀 에이전트 소통 구조

- 호출하는 step이 구현자별로 (구현자·재료·진실검사 A·규칙검사 B·증분 단위)를 주입하는지
- 진실검사 A가 non-null로 강제되는지 (어떤 호출도 진실원천 대조 없이 종료 못 하는지)
- 규칙검사 B가 진실원천 충실도를 직접 판정하지 않고 A로 라우팅하는지
- 리뷰어 직접 루프(Reviewer ↔ Implementer, Lead 개입 없이)와 Lead 종합(sonnet 오탐 필터링)이 엔진 절차에 반영됐는지
- 리뷰어는 code-review SKILL.md의 절차를 따르는지
- 계획과 달라지는 경우 사용자에게 보고하는지

### 컨벤션 커버리지

`contexts/coding-standards/{rules,principles}/**/*.md`를 Glob해 전체 규칙 목록을 얻고, 각 규칙이 workflow step에서 적절한 시점에 참조되고 있는지 점검한다.

- 참조 시점이 부적절한 규칙이 있는지 (예: 코딩 컨벤션이 구현 step이 아닌 곳에만 있는 경우)
- 새로 추가된 규칙이 적절한 step에 참조되지 않은 경우

### 코드 컨벤션 위치 — workflow/conventions/

워크플로우 자체가 생성하는 코드(stub·IMPL 산출)에 대한 코드 컨벤션은 `deploy/skills/workflow/conventions/` 하위 단일 출처로 두고, step·다른 스킬은 cross-reference만 둔다. [여러 곳에 걸리는 규칙은 한 곳에 모으고 트리거만 흩는다](../../../contexts/prompt-standards/sources-and-links.md#여러-곳에-걸리는-규칙은-한-곳에-모으고-트리거만-흩는다)로 본다.

- `/code-review` 스킬이 호출 시 `conventions/` 파일을 컨텍스트로 로드하는지 (자동 로드 또는 호출자 명시 전달)
- 같은 코드 룰이 step 본문과 `conventions/` 양쪽에 분산되어 있지 않은가 (단일 출처 위반 — 본문은 cross-ref만)

## 절차·산출물 명세 단일 출처

[여러 곳에 걸리는 규칙은 한 곳에 모으고 트리거만 흩는다](../../../contexts/prompt-standards/sources-and-links.md#여러-곳에-걸리는-규칙은-한-곳에-모으고-트리거만-흩는다)로 본다. workflow에서 대상은 step·세션·SKILL 파일이다.

### 사례

step-5에 "IMPL 중 디자인 변경 감지 시 figma URL 받는 법" 박으려던 시도. figma URL 받는 절차는 `conventions/plan-folder.md` 「피그마 URL·캡처 캐싱」, MARKUP 절, step-3, step-4 markup.md 양식 4곳에 이미 명세. 5번째 위치에 절차 본문 박지 않고 트리거(언제) + cross-reference(어디 절차 따름)만 박음.

### 점검

- step·세션·SKILL 본문에 절차·산출물 작성법이 박힐 때 다른 위치 grep
- 중복 발견 시 1차 명세 위치 정하고 다른 위치는 cross-reference로 단일화
- 같은 절차의 양식·예시가 두 곳에 동시 존재하면 한 곳 선정 후 나머지는 참조로 전환
