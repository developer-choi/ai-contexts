# 구현↔리뷰 루프

## 목적

구현 결과가 정답과 맞는지와 코딩 스탠다드에 맞는지를 지적 0건이 될 때까지 함께 좁힌다.

팀 구성은 [team-agent](../../../contexts/team-agent.md)를 따른다.

## 입력 (호출자가 주입)

| 인자 | 의미 | 비고 |
|---|---|---|
| 구현자 | 커밋 단위를 만드는 주체 (+ 모델) | |
| 재료(context) | 무엇을·어떻게 만들지 — 계획·결정·stub·정답 등 구현 입력 일체 | AI 산출물 포함 |
| **정답 대조 A** | (정답 위치 · 커밋 단위 통과 기준 · 종료 커버리지 기준 · 검증 메커니즘) | **필수·non-null** |
| 규칙검사 B | code-review에 더 넘길 입력 — 추가 컨벤션, Advanced Reviewer에게 넘길 참고 자료·짚게 할 관점 | 없으면 비운다(비워도 축 B는 돈다). 리뷰어 구성·기준 문서 선별은 넣지 않는다 |
| 커밋 단위 | 두 축 검사를 함께 받는 변경 묶음. 커밋은 하나 이상이다 | |

**재료 ≠ 정답 대조 A.** 정답 자체는 재료에도(구현 시 참조) 정답 대조 A에도(검사 기준) 들어간다. 그러나 AI가 만든 산출물은 재료에만 들어가고 A의 검사 기준이 될 수 없다([진행 중](../SKILL.md#진행-중)). 단, 사용자가 정했거나 승인한 값(그 값을 박아 커밋한 stub, 승인받은 implementation.md의 값)은 정답으로 친다.

## 출력

- 워크트리에 **검증 완료된 커밋들** — 모든 커밋 단위가 A·B 0건으로 수렴한 상태.
- 호출자에게 **수렴 보고** — 커밋 단위별 라운드 결과 + 종료 커버리지 점검 결과 + 수정 사항.

## 두 검증 축

### A. 정답 대조 (non-null · 커밋 단위마다 통과 필요)

- 주입된 정답을 **직접 fetch/실행**해 커밋 단위와 대조한다.
- 검증 메커니즘은 정답의 성질로 주입된다: 실행 결과로 판정할 수 있으면(실행 결과 판정형) 그 결과로, 없으면(리뷰어 대조형) Reviewer ↔ 구현자 직접 대조 루프로.
- 테스트·린트·타입 검사처럼 도구를 돌려 통과 여부를 보는 경우, 커밋마다 그 도구는 구현자가 돌려 통과할 때까지 고친다. 리뷰어 대조형이면 Reviewer도 판정에 쓰는 도구를 직접 돌린다.
- 구현자가 Lead와 다른 팀원이면 Lead에게는 통과했다는 것만 알리고, 스스로 못 고쳐 멈출 때만 실패한 항목과 에러 메시지를 보낸다. Lead가 도구를 다시 돌리면 출력이 커밋마다 Lead 대화에 쌓인다.
- Reviewer는 루프 내내 같은 팀원을 쓴다.

### B. 코딩 스탠다드 (공통 루프)

- 커밋 단위마다 [code-review](../../code-review/SKILL.md)를 advanced 모드로 호출해 0건까지 돌린다. 규칙검사 B로 주입된 입력은 그 호출에 함께 넘긴다.
- code-review가 낸 이슈 중 정답과 어긋남을 짚은 것은 **축 A로 넘겨** 정답과 다시 대조한다(Reviewer가 없는 실행 결과 판정형이면 Lead가 정답을 직접 열어 대조하고, 어긋남이 맞으면 구현자에게 보낸다). 나머지 이슈는 구현자에게 한번에 전달한다.

## 루프

커밋 단위마다:

1. 구현자가 커밋 단위를 만든다.
2. 두 축으로 검증한다 — 미달 시 구현자 수정 → 재검. 커밋 단위는 마지막 수정 뒤에 두 축이 모두 0건이어야 통과한다.
3. 다음 커밋 단위로.

모든 커밋 단위가 끝나면 주입된 **종료 커버리지 기준**으로 누락 0건을 점검한다(축 A). 누락은 커밋 단위로 삼아 위 루프를 돈다.
