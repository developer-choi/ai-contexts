# 채용 과제 제출과 자산 회수

## 목적

채용 과제를 제출하고, 제출 레포가 사라져도 남을 자산으로 회수한다.

`/plan/`에서 과제 요구사항을, `/write-doc pr-body recruitment`로 쓴 각 PR 본문 패키지와 함께 찾아 참조한다.

아래 어느 절에서든 **PR 본문의 정본은 GitHub 게시본이다** — 로컬 패키지는 게시 시점 이전 판일 수 있다.

## 1. 바뀐 코드 점검 — AI + 사용자

전 PR 최종화에서 코드가 바뀌었으면(재배치 중 충돌 해소, 리뷰 수정 합치기), 그 변경이 닿는 범위(그 파일을 참조하는 곳, 바뀔 수 있는 동작)를 사용자에게 보고하고 크면 다시 테스트하도록 안내한다.

## 2. PR 작성 — 사용자에게 안내

게시에 들어가기 전에 전 PR 최종화가 force-push까지 끝났는지 확인하고, 안 끝났으면 그것부터 마친다.

PR 본문은 `/write-doc pr-body recruitment`로 쓴다. PR이 스택이면 아래 순서로 올린다.

1. 첫 PR을 연다. base는 기본 브랜치다. 연 뒤 write-doc pr-body의 [발행](../../write-doc/types/pr-body/steps.md#publish_step-발행)대로 제목·본문을 올리고 [2-1](#2-1-pr-본문-검증--ai-작업)로 검증한다
2. 사용자가 머지한다
3. 로컬 기본 브랜치를 머지분까지 당긴다. 보호 브랜치라 사용자가 실행하므로 명령을 안내한다
4. 다음 PR 브랜치를 그 기본 브랜치 위로 옮겨 붙인다(rebase)
   - 옮기는 것은 그 PR 자기 커밋뿐이다 — squash 머지였으면 앞 PR 커밋이 기본 브랜치에 다른 모양으로 들어가 있다
   - 옮긴 브랜치를 원격에 다시 올리는 것(force-push)도 사용자에게 요청한다
   - `node {{skill_dir}}/scripts/steps.mjs pr set`으로 그 PR의 base를 기본 브랜치로 기록한다
   - 충돌을 풀었으면 그 PR에 [바뀐 코드 점검](#1-바뀐-코드-점검--ai--사용자)을 다시 한다
5. 그 PR을 연다. base는 처음부터 기본 브랜치다. 첫 PR처럼 연 뒤 제목·본문을 올리고 검증한다
6. 남은 PR마다 2~5를 반복한다

## 2-1. PR 본문 검증 — AI 작업

PR 본문을 올릴 때마다 실제 올라간 본문을 파일로 받아 검증한다. **제출 후에는 못 고치고, 다음에 그 본문을 보는 사람이 채용담당자다.**

기계가 보는 것:
- `node {{skill_dir}}/recruitment/scripts/check-submission.mjs pr-body <본문.md> --check-urls` — 플레이스홀더 잔존, 내부 문서 링크, 이미지 URL 유효성. 짚힌 내부 문서 링크는 지운다.
- `node {{skill_dir}}/scripts/steps.mjs pr links` — 커밋 링크가 그 PR의 커밋을 가리키는지. 기본 브랜치 위로 옮기는 rebase로 SHA가 바뀌어 미리 써 둔 링크가 어긋난다. 어긋난 링크는 고쳐 다시 올린다.

사람이 보는 것 — 원본 프로젝트 용어 잔재(상품, product, 과제 등), 다른 레포를 가리키는 커밋 링크가 맞는 레포인지, 수치 불일치(제목의 수치와 본문의 수치).

## 3. README.md 작성 — AI 작업

README는 `/plan/`의 과제 요구사항, 각 PR의 GitHub 게시본, 아래 공통 스펙을 재료로 넘겨 `/write-doc readme`로 쓴다. 발행처는 저장소 루트 README.md다.

**README.md 공통 스펙:**

1. 개요
2. 배포 링크
3. PR 링크별 요약

실행 방법·폴더 구조는 공통이 아니다 — 요구하는 회사와 안 하는 회사가 갈리므로 과제 요구사항에 있을 때만 넣는다. 기술 선택 근거·완성/미완성 등 다른 추가 섹션도 같다.

`/write-doc readme` 패키지의 `audience_knowledge`는 「과제 요구사항은 앎, 코드를 열어 봄」으로 둔다.

## 3-1. 산출물 문서 채용담당자 시점 리뷰 — AI 작업

### 리뷰 대상

- **README.md** — 외부 채용 과제 프로젝트의 저장소 루트
- **GitHub PR 본문** — PR 분할이면 각 PR 본문

넘기기 전에 README도 같은 검사(`check-submission.mjs pr-body`)로 돌려 내부 문서 링크를 지운다 — 이미지 참조는 유지한다.

### 리뷰 에이전트에 넘길 것·막을 것

채용담당자 시점 리뷰는 **지원자 쪽 맥락 없이** 읽는 에이전트가 수행한다. 채용담당자가 손에 쥔 것만 넘기고, 지원자만 아는 것은 막는다.

- 넘긴다: 리뷰 대상 문서, 과제 요구사항 원문(`/plan/background/persistent/과제요구사항.md`), 채용 메일 원본(`/plan/background/persistent/메일.md`). 경로가 아니라 본문을 프롬프트에 담아 준다
- 막는다: `/plan/`의 그 밖의 산출물(계획·결정·구현 인수인계 등), 구현 맥락, 코드. 프롬프트에 「위 본문 밖의 파일은 열지 않는다」를 적는다

### 에이전트 프롬프트 핵심

- 리뷰어의 위치: **이 과제 요구사항을 직접 작성해 지원자에게 보낸 사람**. 요구사항에 이미 적힌 내용은 문서가 다시 설명하지 않아도 알고 있다
- 각 문서에 대해 다음 관점을 보고:
  - **첫인상** — 문서를 처음 본 사람이 느끼는 흐름
  - **한 번에 이해되지 않는 문장** — 재독·문맥 추론이 필요한 표현
  - **요구사항 대비 빠진 것** — 요구사항 조항이 요구했는데 문서에서 근거가 안 잡히는 것. 지적마다 요구사항의 몇 번 조항인지 함께 적는다
  - **불필요하게 긴 부분** — 압축 가능한 영역
- **수정 없이 리뷰 결과만 보고**

메인은 리뷰 결과를 사용자에게 내고, 무엇을 고칠지는 사용자가 정한다.

## 4. 제출 절차 — AI + 사용자

`/plan/background/persistent/`의 과제 요구사항과 메일 원본을 읽고, 해당 과제의 제출 방식에 맞는 체크리스트를 생성하여 사용자에게 안내한다.

공통 점검:
- `node {{skill_dir}}/recruitment/scripts/check-submission.mjs submission` — 환경변수 파일·`plan/` 혼입
- [클린 환경 실행 확인](#클린-환경-실행-확인) 통과
- GitHub 제출이면 Private 확인 뒤 collaborator 초대
- README.md의 이미지·링크는 `check-submission.mjs pr-body <README.md> --check-urls`로 확인
- 과제가 AI 세션 대화 내역 제출을 요구하면 [session-timeline/SKILL.md](../session-timeline/SKILL.md)로 대화록을 만들고, 그 파일을 `plan/` 밖 제출물 안으로 옮겨 넣는다

### 클린 환경 실행 확인

작업 폴더에는 `node_modules/`·미커밋 파일·`.env.local`이 그대로 있어, 빠뜨린 것이 있어도 빌드가 통과한다.

- 리뷰어가 받는 것만 든 빈 머신(GitHub Actions)에서 설치→빌드→실행→홈페이지 응답까지 돌린다.
- 빨간불이면 제출하지 않고 실패 로그로 빠진 것을 사용자에게 보고한다.
- 절차는 [clean-env/procedure.md](clean-env/procedure.md).

### 제출 메일 작성

제출 시 보낼 메일 본문 초안(MAIL.md)을 작성하여 사용자에게 제시한다. 메일이 가리키는 README·PR 본문은 3-1 리뷰 결과까지 반영한 최종본을 기준으로 삼는다.

- `.env.local` 등 환경변수 파일을 메일에 첨부하도록 안내 포함

## 5. 제출 뒤 회수 (AI + 사용자)

제출까지 끝나면 [after-submission.md](after-submission.md)를 읽고 이어서 수행한다. 컨텍스트가 커졌으면 이 절을 새 세션으로 옮겨도 된다고 안내하고, 옮기면 그 파일 경로를 새 세션에 넘기게 한다.
