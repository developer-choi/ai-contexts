# 채용 과제 제출과 자산 회수

## 목적

채용 과제를 제출하고, 제출 레포가 사라져도 남을 자산으로 회수한다.

`/plan/`에서 과제 요구사항과 각 PR의 pr-body를 찾아 참조한다.

아래 어느 절에서든 **PR 본문의 진실 원천은 GitHub 게시본이다** — 로컬 `pr-body.md`는 게시 시점 이전 판일 수 있다.

PR 분할 안내·최종 제출 QA체크리스트·어필·회고 양식은 완성본 라이브러리의 `meta-submission` 주제에 재사용 자산으로 모은다 — 있으면 [pr-body/](pr-body/)에서 글롭해 복사 기점으로 삼는다.

## 1. 커밋 정리 — 사용자에게 안내

메시지 최종화·오배치 커밋 재배치는 앞선 최종화 본문에서 이미 끝났다 — 여기서 다시 하지 않는다. 본 절은 제출 리뷰만 남긴다.

- 커밋 히스토리를 코드리뷰 관점으로 훑어 이상 유무 확인. `/plan/`은 전역 gitignore라 애초에 커밋되지 않으므로 산출물 커밋을 삭제하는 단계는 없다.

## 2. 제출 직전 수정 점검 — AI + 사용자

커밋 정리 과정에서 마지막에 수정한 내용이 있으면, 제출 전에 점검합니다.

1. PR 순서대로 커밋 목록을 나열하고, 커밋 정리 중 추가/수정한 커밋을 표시한다
2. 커밋 정리 중 코드를 수정한 부분이 있었는지 사용자에게 확인한다
3. 수정이 있으면 AI가 해당 변경의 영향 범위를 분석하여 보고한다:
   - 수정된 파일을 참조하는 다른 파일이 있는지
   - 기존 동작이 변경될 가능성이 있는지
4. 영향 범위가 크다고 판단되면 해당 부분을 다시 테스트하도록 안내한다

## 3. PR 작성 — 사용자에게 안내

게시에 들어가기 전에 최종화 본문(오배치 커밋 재배치·메시지 최종화·force-push)이 끝났는지 확인한다. 안 끝났으면 게시하지 않고 그 본문부터 마친다.

`/plan/`의 pr-body를 기반으로 GitHub PR을 작성한다. PR이 스택이면 한꺼번에 올리지 않고 하나씩 올린다.

1. 첫 PR을 올린다. base는 기본 브랜치다
2. 사용자가 머지한다
3. 로컬 기본 브랜치를 머지분까지 당긴다. 보호 브랜치라 사용자가 실행하므로 명령을 안내한다
4. 다음 PR 브랜치를 그 기본 브랜치 위로 옮겨 붙인다(rebase). 브랜치는 구현 단계에서 스택으로 이미 만들어져 있으니 새로 따는 것이 아니다. 옮기는 것은 그 PR 자기 커밋뿐이다 — squash 머지였으면 앞 PR 커밋이 기본 브랜치에 다른 모양으로 들어가 있다. 옮긴 브랜치를 원격에 다시 올리는 것(force-push)도 사용자에게 요청한다
5. 그 PR을 올린다. base는 처음부터 기본 브랜치다
6. 남은 PR마다 2~5를 반복한다

## 3-1. PR 본문 검증 — AI 작업

사용자가 GitHub PR URL을 제공하면, 실제 올라간 본문을 파일로 받아 검증한다. **제출 후에는 못 고치고, 다음에 그 본문을 보는 사람이 채용담당자다.**

기계가 보는 것 — `node {{skill_dir}}/recruitment/scripts/check-submission.mjs pr-body <본문.md> --check-urls`: 플레이스홀더 잔존, 내부 문서 링크, 이미지 URL 유효성. 짚힌 내부 문서 링크는 지운다.

사람이 보는 것 — 원본 프로젝트 용어 잔재(상품, product, 과제 등), 커밋 링크가 **올바른** 레포/커밋을 가리키는지, 수치 불일치(제목의 수치와 본문의 수치).

## 4. README.md 작성 — AI 작업

`/plan/`에서 과제 요구사항과 각 PR의 pr-body를 모두 읽고, 과제 요구사항에 맞는 프로젝트 소개 문서 README.md를 작성하여 사용자에게 제시합니다.

**README.md 공통 스펙:**

1. 개요
2. 배포 링크
3. PR 링크별 요약

실행 방법·폴더 구조는 공통이 아니다 — 요구하는 회사와 안 하는 회사가 갈리므로 과제 요구사항에 있을 때만 넣는다. 기술 선택 근거·완성/미완성 등 다른 추가 섹션도 같다.

초안을 쓰면 사용자에게 내밀기 전에 `/write-refine <README 경로>`를 부른다. 사용자와 초안을 함께 보는 일도 그 스킬 안에서 한다. 채점기 적발 0과 리뷰어 `block` 0까지 그 스킬이 닫으며, 확정본을 제시할 때 두 결과를 함께 보고한다.

이 README의 독자는 코드를 열어볼 평가자라, [readme-guide.md](../../../contexts/writing-guide/readme-guide.md)가 잡은 독자(비개발자)와 다르다. 그 가이드에서는 톤과 1인칭 서술만 가져오고 금지 목록은 적용하지 않는다 — 과제 요구사항이 코드 구조 설명을 요구하면 그대로 쓴다.

## 4-1. 산출물 문서 채용담당자 시점 리뷰 — AI 작업

### 리뷰 대상

- **README.md** — 외부 채용 과제 프로젝트의 저장소 루트
- **GitHub PR 본문** — PR 분할이면 각 PR 본문

넘기기 전에 README도 같은 게이트(`check-submission.mjs pr-body`)로 돌려 내부 문서 링크를 지운다 — 이미지 참조는 유지한다.

### 리뷰 에이전트에 넘길 것·막을 것

채용담당자 시점 리뷰는 **지원자 쪽 맥락 없이** 읽는 에이전트가 수행한다. 채용담당자가 손에 쥔 것만 넘기고, 지원자만 아는 것은 막는다.

- 넘긴다: 과제 요구사항 원문(`/plan/background/persistent/과제요구사항.md`), 채용 메일 원본(`/plan/background/persistent/메일.md`)
- 막는다: `/plan/`의 그 밖의 산출물(계획·결정·구현 인수인계 등), 구현 맥락, 코드

### 에이전트 프롬프트 핵심

- 리뷰어의 위치: **이 과제 요구사항을 직접 작성해 지원자에게 보낸 사람**. 요구사항에 이미 적힌 내용은 문서가 다시 설명하지 않아도 알고 있다
- 각 문서에 대해 다음 관점을 보고:
  - **첫인상** — 문서를 처음 본 사람이 느끼는 흐름
  - **한 번에 이해되지 않는 문장** — 재독·문맥 추론이 필요한 표현
  - **요구사항 대비 빠진 것** — 요구사항 조항이 요구했는데 문서에서 근거가 안 잡히는 것. 지적마다 요구사항의 몇 번 조항인지 함께 적는다
  - **불필요하게 긴 부분** — 압축 가능한 영역
- **수정 없이 리뷰 결과만 보고**

메인은 리뷰 결과를 사용자에게 내고, 무엇을 고칠지는 사용자가 정한다.

## 5. 제출 절차 — AI + 사용자

`/plan/background/persistent/`의 과제 요구사항과 메일 원본을 읽고, 해당 과제의 제출 방식에 맞는 체크리스트를 생성하여 사용자에게 안내한다.

공통 점검:
- `node {{skill_dir}}/recruitment/scripts/check-submission.mjs submission <레포>` — 환경변수 파일·`plan/` 혼입
- 빌드가 에러 없이 완료되는지 확인
- [클린 환경 실행 확인](#클린-환경-실행-확인) 통과 — 작업 폴더 빌드 통과만으로 제출하지 않는다
- GitHub 제출이면 Private 확인 뒤 collaborator 초대
- README.md의 이미지·링크는 `check-submission.mjs pr-body <README.md> --check-urls`로 확인
- 과제가 AI 세션 대화 내역 제출을 요구하면 [session-timeline/SKILL.md](../session-timeline/SKILL.md)로 대화록을 만들어 제출물에 넣는다

### 클린 환경 실행 확인

작업 폴더에는 `node_modules/`·미커밋 파일·`.env.local`이 그대로 있어, 빠뜨린 것이 있어도 빌드가 통과한다. 리뷰어가 받는 것만 든 빈 머신(GitHub Actions)에서 설치→빌드→실행→홈페이지 응답까지 돌려, 빨간불이면 제출하지 않고 실패 로그로 빠진 것을 사용자에게 보고한다. 절차는 [clean-env/procedure.md](clean-env/procedure.md).

### 제출 메일 작성

제출 시 보낼 메일 본문 초안(MAIL.md)을 작성하여 사용자에게 제시한다. 메일이 가리키는 README·PR 본문은 4-1 리뷰 결과까지 반영한 최종본을 기준으로 삼는다.

- `.env.local` 등 환경변수 파일을 메일에 첨부하도록 안내 포함

## 6. 제출 뒤 회수 (AI + 사용자)

제출까지 끝나면 [after-submission.md](after-submission.md)를 읽고 이어서 수행한다. 컨텍스트가 커졌으면 이 절을 새 세션으로 옮겨도 된다고 안내하고, 옮기면 그 파일 경로를 새 세션에 넘기게 한다.
