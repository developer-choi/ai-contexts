# 제출 뒤 회수

## 1. 완성본 라이브러리 갱신 (AI + 사용자)

이번 과제 각 PR의 GitHub 게시본을 주제별 완성본 라이브러리([recruitment/library/](../../../contexts/writing-guide/types/pr-body/recruitment/library/))에 반영한다.

**PR 단위가 아니라 재료(섹션) 단위로 분해해 분류한다.** 한 PR 본문은 여러 `#` 섹션으로 나뉘고 섹션마다 다른 주제(재료)를 담으므로, PR 하나가 완성본 재료 여러 개를 기여할 수 있다. 각 PR 본문을 섹션별 재료로 갈라, 재료마다:

- **주제 식별** — 그 재료(섹션)의 성격으로 슬러그를 정하고 `recruitment/library/`를 글롭해 해당 완성본을 찾는다.
- **주제당 한 벌** — 이미 있으면 이번이 명백히 나은 부분(더 정확한 근거·트레이드오프, 더 나은 섹션 구조·표현)만 갈아끼운다.

- **자족 인라이닝** — 제출 레포는 삭제되므로 완성본에 제출 레포 PR·커밋 링크를 남기지 않고, 근거·인용의 핵심 내용을 파일 안에 직접 담는다.
- AI가 주제별 변경 초안을 diff로 제시하고, 반영은 사용자가 판단한다.

## 2. 자산 회수 (AI + 사용자)

1번 외의 자산 — 원본 자료, 인터뷰 준비 자료, 미병합 브랜치, 이번 과제 패턴 — 을 제출 레포를 삭제해도 무방하도록 별도 보존한다.

### 2-0. 먼저 회수할 것

자산 회수의 첫 명령으로 `node {{skill_dir}}/recruitment/scripts/archive-repo.mjs collect`를 돌려 PR 본문과 PR 커밋을 회수한다. PR 본문은 브랜치에 없어 제출 레포와 함께 사라진다.

### 2-1. 아카이브 레포 생성 + 원본 자산 옮기기

로컬 작업 저장소를 복사해 제출 레포(collaborator 초대된 실제 제출용)와 별개의 **영구 보존용 private 레포**를 만든다.

복사부터 PR 재생성까지는 2-0과 같은 `archive-repo.mjs`로 `create` → `push` → `relink` → `recreate-prs` 순서로 돌린다. 명령마다 넘길 것과 다음 할 일은 출력이 알린다.

- `create`에 넘길 아카이브 이름의 slug는 회사명·과제명 중 아무거나로 정한다.
- **전제**: 복사는 로컬 저장소에 더 이상 커밋이 추가되지 않는 시점(게시한 PR 본문·README를 검토해 고친 것까지 반영된 뒤)에 한다. 복사 이후 로컬에 생긴 커밋은 아카이브에 안 들어간다.
- **브랜치**: 기본 브랜치는 제출 레포 미러로 두고 제출 관련 변경(README의 제출 레포 링크 치환)만 얹는다. 아래 레포 구성은 기본 브랜치에서 뻗은 `plan` 브랜치에 커밋한다.
- **레포 구성** (`plan` 브랜치):
  - `original/` — 과제 메일·요구사항 문서·피그마 캡처 등 원본 (`/plan/background/persistent/`에서 복사)
  - 인터뷰 준비 자료 — 아래 「인터뷰 준비」
  - `archived-plan/` — 아카이브에 남길 `/plan/` 산출물. `/plan/`은 전역 gitignore라 그대로 두면 push되지 않는다. 불필요한 폴더 뎁스는 평탄화한다.
- **옮긴 산출물은 PR 본문과 중복 제거(SSOT=게시본)**: 옮겨 담는 산출물이 PR 본문과 같은 주제를 다루면(특히 `decisions.md`), PR 게시본이 정본이므로 **본문에 이미 있는 내용은 빼고 본문에 없는 측면만 남긴다**.
- 커밋한 뒤 `push`를 다시 돌린다 — 맨 `git push`는 origin이 아카이브 레포인지 확인하지 않는다.
- **완료 판정**: 레포가 GitHub에 존재 + 위 항목이 실제로 커밋·push됐는지로 확인.

#### PR 재생성

`recreate-prs`가 2-0에서 회수한 본문·커밋으로 같은 번호·같은 스택의 PR을 만들어 닫고, 만든 PR을 회수한 본문 파일과 대조한 결과를 낸다. 사람이 정할 것은 둘이다.

- **제목은 외부 독자가 읽을 서술형으로** — 원본 제목이 브랜치명에서 자동 생성된 것(`Refactor/folder` 등)이면 그대로 옮길 가치가 없다. README의 PR 요약 제목을 넘긴다.
- **제출 레포를 가리키는 링크를 치환할 문서를 고른다** — 회수한 PR 본문 말고도 README 등 아카이브 안 문서가 제출 레포 PR·커밋을 링크하면 지금 링크가 살아 있어도 `relink`에 넘긴다.

#### 인터뷰 준비

면접관은 제출된 PR 본문을 읽고 "왜 그렇게 했느냐"를 묻는다. 그러므로 인터뷰 준비의 **1차 소스는 PR 본문**이다.

- **1차: PR 본문 정독** — 각 PR 본문이 내세운 근거·트레이드오프·거부한 대안을 예상 질문("왜 X 대신 Y?", "이 판단의 리스크는?")과 짝지어 정리한다.
- **2차: `decisions.md`로 보강** — PR 본문엔 지면상 못 담은 판단·기각 사유를 각 PR `persistent/decisions.md`에서 주워 1차 정리에 덧댄다.

### 2-2. best-practice 갱신

이번 과제에서 얻은 패턴·결정을 MP(monorepo-playground) `docs/best-practices/`의 해당 분야 문서에 반영한다 — 분야 목록은 그 폴더를 글롭해 확인하고, 패턴은 각 PR 게시본과 `decisions.md`에서 뽑는다. 1번 절과 같은 방식으로 한다.

무엇을 옮기고 무엇을 접었는지는 아카이브 `plan` 브랜치의 `HANDOFF.md`에 적고 `push`를 다시 돌린다. 2-1의 레포 구성 어느 종류에도 안 들어가는 자유 메모도 여기 둔다.

### 2-3. 제출 레포 로컬 폴더 삭제 (삭제는 사용자 실행 — 마지막 절차)

2-1~2-2를 마치면 제출 레포 로컬 작업 폴더는 삭제해도 된다. 채용 마무리의 **마지막 절차**다.

- **서버 종료는 AI가 먼저 한다** — `node {{contexts}}/stop-servers.mjs stop <폴더> --worktrees`로 그 폴더와 거기서 뻗은 워크트리 경로의 서버를 끄고 결과를 보고한다.
  - 세션을 닫아도 그 세션이 띄운 서버는 남아 파일을 잡는다.
  - 2-1 이후에 다시 띄운 서버가 있을 수 있으므로 2-1에서 껐어도 다시 돈다.
- **폴더 삭제는 AI가 실행하지 않는다** — 그 폴더(또는 그 폴더에서 만든 워크트리)를 cwd로 둔 세션이 파일을 잡고 있어 삭제가 막힌다. 사용자가 **해당 세션들을 모두 닫은 뒤** 직접 지운다.
  - 사용자가 지우다 막혔다고 하면 서버 끄기를 다시 돌리고, 그래도 남는 경로와 에러를 함께 짚는다.
- 삭제 전 아카이브가 GitHub에 실제로 push됐는지(2-1·2-2에서 올린 것) 재확인한다 — 로컬 폴더가 유일본이 아님을 확인한 뒤 지운다.
