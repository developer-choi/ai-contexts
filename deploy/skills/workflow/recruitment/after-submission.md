# 제출 뒤 회수

## 1. 완성본 라이브러리 갱신 (AI + 사용자)

이번 과제 각 PR의 GitHub 게시본을 주제별 완성본 라이브러리([pr-body/](pr-body/))에 반영한다.

**PR 단위가 아니라 재료(섹션) 단위로 분해해 분류한다.** 한 PR 본문은 여러 `#` 섹션으로 나뉘고 섹션마다 다른 주제(재료)를 담으므로, PR 하나가 완성본 재료 여러 개를 기여할 수 있다. 각 PR 본문을 섹션별 재료로 갈라, 재료마다:

- **주제 식별** — 그 재료(섹션)의 성격으로 슬러그를 정하고 `pr-body/`를 글롭해 해당 완성본을 찾는다.
- **없으면 신규** — 이 재료를 기점으로 그 주제 완성본을 새로 만든다.
- **있고 이번이 더 나으면 교체** — 기존 완성본보다 나은 부분(더 정확한 근거·트레이드오프, 더 나은 섹션 구조·표현)만 골라 그 부분을 갈아끼운다. 나머지는 두고, 새 벌을 더하지 않는다(주제당 한 벌).

- **자족 인라이닝** — 제출 레포는 삭제되므로 완성본에 제출 레포 PR·커밋 링크를 남기지 않고, 근거·인용의 핵심 내용을 파일 안에 직접 담는다. 레포가 사라져도 재료가 홀로 살아 있어야 한다.
- AI가 주제별 변경(신규/교체) 초안을 diff로 제시하고, 반영은 사용자가 판단한다. 교체는 명백한 개선일 때만 — 애매하면 유지.

## 2. 자산 회수 (AI + 사용자)

1번 외의 자산 — 원본 자료, 인터뷰 준비 자료, 미병합 브랜치, 이번 과제 패턴 — 을 제출 레포를 삭제해도 무방하도록 별도 보존한다.

### 2-0. 먼저 회수할 것

2-1에서 아카이브를 뜨기 전에 둘을 끝낸다. 뒤로 미루면 앞의 것은 되살릴 수 없고, 뒤의 것은 아카이브 문서를 고쳐 다시 올려야 한다.

- **PR 본문과 PR 커밋을 회수한다** — 자산 회수의 첫 명령으로 `node {{skill_dir}}/recruitment/scripts/archive-repo.mjs collect <작업폴더>`를 돌린다. PR 본문은 브랜치에 없어 제출 레포와 함께 사라진다
- **2-2에서 무엇을 옮기고 무엇을 접을지 정한다** — 그 결과가 아카이브의 `HANDOFF.md`에 적힌다. 판정 입력은 이번 과제 패턴 메모와 MP `docs/best-practices/`의 분야 목록뿐이라 지금 낼 수 있다. 파일별 diff 제시는 2-2에서 한다

### 2-1. 아카이브 레포 생성 + 원본 자산 이설

로컬 작업 저장소를 복사해 제출 레포(collaborator 초대된 실제 제출용)와 별개의 **영구 보존용 private 레포**를 만든다. 복사(복사 전 작업폴더·워크트리를 붙잡은 서버 종료 포함)·워크트리 메타데이터 정리·원격 교체·push·PR 재생성·링크 치환은 2-0의 `collect`와 같은 `archive-repo.mjs`가 맡는다. 명령 순서:

1. `create <작업폴더> recruitment-{slug}-{실행일:YYYYMMDD}` — `{slug}`는 회사명·과제명 중 아무거나
2. **여기서 멈추고 출력된 `git remote -v`를 사용자에게 보여준다** — origin이 제출 레포가 아니라 새 아카이브 레포인지 확인받은 뒤에만 다음으로 간다. 로컬 브랜치가 제출 레포로 나가면 되돌리기 어렵다
3. `push <복사본>`
4. `recreate-prs <복사본>` — 아래 「PR 재생성」
5. `relink <복사본> <문서...>` — 아래 「PR 재생성」

- **전제**: 복사는 로컬 저장소에 더 이상 커밋이 추가되지 않는 시점(게시한 PR 본문·README를 검토해 고친 것까지 반영된 뒤)에 한다. 복사 이후 로컬에 생긴 커밋은 아카이브에 안 들어간다.
- **레포 구성**:
  - `original/` — 과제 메일·요구사항 문서·피그마 캡처 등 원본 (`/plan/background/persistent/`에서 복사)
  - 인터뷰 준비 자료 — 아래 「인터뷰 준비」
  - `HANDOFF.md` — 위 갈래에 안 들어가는 자유 메모. 2-0에서 정한 이관 판정을 여기 적는다
- **`/plan/` 이설**: `/plan/`은 전역 gitignore라 그대로 두면 push되지 않는다. 아카이브에 남길 산출물은 추적되는 경로로 옮겨 담아야 실제로 보존된다.
- **이설 산출물은 PR 본문과 중복 제거(SSOT=게시본)**: 옮겨 담는 산출물이 PR 본문과 같은 주제를 다루면(특히 `decisions.md`), PR 게시본이 진실 원천이므로 **본문에 이미 있는 내용은 빼고 본문에 없는 측면만 남긴다**. 불필요한 폴더 뎁스는 평탄화한다(예: PR별 하위에 흩어진 `decisions.md`를 `decisions/pr{N}.md`로).
- **이설 산출물은 `plan` 브랜치에 — 기본 브랜치는 제출 미러 유지**: 아카이브 기본 브랜치는 제출 레포를 그대로 미러(제출된 코드·README)한다. 제출물이 아닌 계획 산출물(`archived-plan/`)은 기본 브랜치에 얹지 않고 거기서 뻗은 `plan` 브랜치에 커밋해 보존·복구한다. 기본 브랜치엔 제출 관련 변경(README·제출 레포 링크 교체 등)만 얹는다.
- **완료 판정**: 레포가 GitHub에 존재 + 위 항목이 실제로 커밋·push됐는지로 확인.

#### PR 재생성

`recreate-prs`가 2-0에서 회수한 본문·커밋으로 같은 번호·같은 스택의 PR을 만들어 닫고, 게시본과 대조한 결과를 낸다. 사람이 정할 것은 둘이다.

- **제목은 외부 독자가 읽을 서술형으로** — 원본 제목이 브랜치명에서 자동 생성된 것(`Refactor/folder` 등)이면 그대로 옮길 가치가 없다. README의 PR 요약 제목을 `--title`로 넘긴다.
- **제출 레포를 가리키는 링크를 치환할 문서를 고른다** — README 등 아카이브 안 문서가 제출 레포 PR·커밋을 링크하면 지금 링크가 살아 있어도 `relink`에 넘긴다.

#### 인터뷰 준비

면접관은 제출된 PR 본문을 읽고 "왜 그렇게 했느냐"를 묻는다. 그러므로 인터뷰 준비의 **1차 소스는 PR 본문**이다 — decisions.md가 아니다.

- **1차: PR 본문 정독** — 각 PR 본문이 내세운 근거·트레이드오프·거부한 대안을 예상 질문("왜 X 대신 Y?", "이 판단의 리스크는?")과 짝지어 정리한다.
- **2차: `decisions.md`로 보강** — PR 본문엔 지면상 못 담은 판단·기각 사유를 각 PR `persistent/decisions.md`에서 주워 1차 정리에 덧댄다.

### 2-2. best-practice 갱신

이번 과제에서 얻은 패턴·결정을 MP(monorepo-playground) `docs/best-practices/`의 해당 분야 문서에 반영한다 — 분야 목록은 그 폴더를 글롭해 확인한다. 1번 절과 동일한 패턴(diff 제시 → 사용자 판단, 명백한 개선일 때만 교체) 재사용.

- **완료 판정**: 각 파일에 대해 diff 제시 여부 + 사용자 반영/스킵 결정이 남았는지로 확인.

### 2-3. 제출 레포 로컬 폴더 삭제 (삭제는 사용자 실행 — 마지막 절차)

2-1~2-2로 원본·산출물이 아카이브 레포에 전부 보존됐음을 확인한 뒤, 제출 레포 로컬 작업 폴더는 삭제해도 된다. 채용 마무리의 **마지막 절차**다.

- **서버 종료는 AI가 먼저 한다** — `node {{contexts}}/stop-servers.mjs stop <폴더> --worktrees`로 그 폴더와 거기서 뻗은 워크트리 경로의 서버를 끄고 결과를 보고한다. 세션을 닫아도 그 세션이 띄운 서버는 남아 파일을 잡는다. 2-1 이후에 다시 띄운 서버가 있을 수 있으므로 2-1에서 껐어도 다시 돈다.
- **폴더 삭제는 AI가 실행하지 않는다** — 그 폴더(또는 그 폴더에서 만든 워크트리)를 cwd로 둔 세션이 파일을 잡고 있어 삭제가 막힌다. 사용자가 **해당 세션들을 모두 닫은 뒤** 직접 지운다. 사용자가 지우다 막혔다고 하면 서버 끄기를 다시 돌리고, 그래도 남는 경로와 에러를 함께 짚는다.
- 삭제 전 아카이브가 GitHub에 실제로 push됐는지(2-1 완료 판정) 재확인한다 — 로컬 폴더가 유일본이 아님을 확인한 뒤 지운다.
