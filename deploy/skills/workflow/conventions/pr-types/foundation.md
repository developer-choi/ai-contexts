# FOUNDATION PR

경계: 코드 스타일 기준을 세우는 첫 PR. 적용 모드: 채용 = 폴더 구조·코딩 스탠다드 마이그레이션과 전역 폰트 셋업(도구 설정은 [SETUP](setup.md)) / 개인 신규 프로젝트 = 첫 셋업([SETUP](setup.md)의 항목·stub 규칙을 그대로 따른다) / 실무·개인 기존 레포 = 없음.

아래 절은 채용 모드에만 적용한다.

## 회사 제공 베이스라인 커밋

채용과제는 빈 보일러플레이트만 주기도 하지만, **회사가 폴더 구조·부분 마크업·설정 일부를 미리 작업해 커밋으로 쌓아 제공하기도 한다**.

**판별**(착수 전): 과제 레포를 받은 시점에 있던 기존 코드가 곧 제공 베이스라인이다.

**적용 규칙**:

- **베이스라인 커밋은 immutable**. reset·force-push·rebase·squash로 되돌리거나 재작성하지 않는다
- **회사가 이미 한 작업은 다시 하지 않는다**. 폴더 마이그레이션이 이미 돼 있고 사용자가 그 구조를 유지하기로 하면 `folder-structure.md`를 "회사 제공 구조 문서화"로 작성한다
- **위에 새 커밋으로 수정하는 것은 정상 작업**. 베이스라인 파일을 건드려도 새 커밋이면 히스토리를 다시 쓰는 것이 아니다.
- **함정 가능성**. 회사가 의도적 결함(잘못된 폰트, "테스트를 가장한 안내 파일" 등)을 심었을 수 있다. 발견 시 사용자에게 보고한다. 폴더·폰트·코드 스타일 쪽이면 이 PR에서 수정 커밋으로 고치고, 아니면 [PR별 TODO 등록처](../pr-split.md#pr별-todo-등록처)대로 적는다.

## 산출 내용

- **폴더 구조 마이그레이션** + `background/retained/folder-structure.md` 작성 (디렉토리 골격 + 폴더 마이그레이션 항목). 후속 PR이 참조한다.
- **코딩 스탠다드 마이그레이션** — `/code-review --mode only-standards`에 아래 둘을 넘겨 받은 이슈대로 기존 코드를 고친다
  - coding-standards 경로: [realize-plan 「코딩 스탠다드 · 베스트프랙티스」](../../steps/realize-plan.md#코딩-스탠다드--베스트프랙티스)에서 고른 coding-standards 파일
  - 리뷰 대상: 폴더 구조 마이그레이션을 마친 뒤의 기존 파일
- **전역 폰트 셋업**

**folder-structure.md 결정 기준**: 폴더 구조는 사용자 확정을 받은 뒤 스캐폴딩·문서화한다 — 베이스라인에 기존 구조가 있거나 회사가 이미 마이그레이션했어도 같다.
BG의 [requirement 「자료 받기」](../../steps/requirement.md#자료-받기) 자료(요구사항·우대사항)로 추천은 곁들인다 — 채용공고 우대사항의 FSD 등은 지원자에게 바라는 역량이지 이 과제를 그 구조로 구현하라는 지시가 아니다.
기존 구조가 있으면 MP `docs/best-practices/setup.md`(폴더 구조·셋업)의 후보 패턴과 나란히 제시해 유지할지 옮길지 고르게 한다.
DDD로 지정되면 트리 작성 전 MP `docs/patterns/folder-structure/FolderStructure.md`를 읽고 그 패턴(디렉토리 골격·네이밍·배럴 유무)을 따른다.

**전역 폰트 셋업 기준**: [디자인 원본](../modes.md)에 지정 폰트가 있으면 그 폰트로, 없으면 `Noto Sans KR`을 기본값으로 두고 사용자 확인 후 확정한다. 디자인 원본에서는 폰트 패밀리만 본다.
