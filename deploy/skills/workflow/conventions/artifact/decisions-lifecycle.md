# decisions.md 컨벤션

`/plan/pr{N}/persistent/decisions.md`의 책임·작성 양식·생성 게이트·갱신 단일 출처.

## 책임·위치

본 PR에서 **기록할 가치가 있는** 기술 결정의 근거 + 흐름.

이 문서와 PR 본문이 다르면 PR 본문이 우선이다.

## overview.md와의 분담

- **overview.md**: 의도만 — 채택된 결과(기술명·라이브러리·패턴) 나열, 근거 없음
- **decisions.md**: 기록 대상 결정의 근거 + 흐름. 사용자 발화 인용은 그대로

## 포함·제외 기준

**기본값은 "적지 않는다".** 아래 포함 조건에 걸릴 때만 결정으로 남긴다.

### 포함 (둘 중 하나라도)

- **사용자 개입 흔적**: LLM 초안을 사용자가 거부·수정했거나 사용자가 직접 선택했다 (대화에 발화가 남는다)
- **기각한 대안을 댈 수 있다**: 둘 이상의 실재 후보를 두고 골랐고 안 고른 쪽도 합리적이었다 — "X 대신 Y, 왜냐면 Z"를 쓸 수 있다

### 제외

- **출처값 그대로 채택**: 1차 소스(공식 문서·MP 베스트프랙티스 등)의 기본값·권장값을 비교 없이 채택 → reference.md 출처 경로로 충분
- **자명한 절차 결과**: 안 할 이유가 없어 결과가 정해진 것 (예: 단일 후보뿐인 라이브러리 채택) → plan 작성 때는 implementation.md 계획에 자연 반영, 갱신 때는 적지 않는다. 단 stub 유무는 여기 해당하지 않는다 — [realize-plan 「realize-plan 커밋」](../../steps/realize-plan.md#5-realize-plan-커밋-stub-또는-실행) 판정 소관이라 plan에서 stub 없음으로 단정하지 않는다.
- **non-issue 확인 (걱정거리 해소)**: "우려했으나 확인해보니 문제 없음"으로 닫힌 항목은 결정이 아니다 (채택한 대안도 기각한 대안도 없음) → 적지 않는다. plan 작성 때 필요하면 implementation.md 메모로.
- **PR 분할·범위 변경**: 그 PR의 TODO로 적는다 ([PR 몫 TODO 등록처](../pr-split.md#pr-몫-todo-등록처))
- **단순 합의**: 트레이드오프 없이 사용자가 그냥 동의 (선택지가 사실상 하나)

### 경계 사례 — AI 단독 판단 금지

포함/제외가 애매하면 AI가 자체 판단으로 박지 않고 "이거 decisions에 적을까요?"로 확인한 뒤 추가한다.

## 세 갈래 양식

- **사용자 발화 4단계 이상 이어진 결정** (토론 결과 포함): 발화 흐름 인용 + 거부/채택 사유 + 최종 채택안 + 근거. [/discussion 토론 결과 양식](../../../discussion/SKILL.md#토론-결과-정리) 참조
- **사용자 명시 결정** (단발이지만 사용자가 LLM 초안을 거부·수정·확정): 짧은 흐름(LLM 초안 → 사용자 발화 → 채택안) + 근거
- **AI 단독 결정** (사용자 발화 없이 LLM이 컨벤션·관례에 따라 결정): 채택안 + 근거(인용한 컨벤션 라인 등)

## 작성 양식 (사용자 명시 결정)

필수 필드: 제목(`## 결정 N`)·LLM 초안·사용자 발화(차수별 인용)·LLM 보고(차수별)·최종 채택안·근거·연결(overview.md 결정·markup.md 절).

## 머리 안내문

파일 맨 위에 아래 안내문을 둔다.

```markdown
> 구현·리뷰 도중에는 고치지 않는다 — 그사이 나온 결정은 verify 「decisions.md 최신화」에서 한 번에 반영한다. 이 문서와 PR 본문이 다르면 PR 본문이 우선이다.
```

## 생성 게이트 — 단발 발화 확인

사용자의 단발 발화(특히 "그냥 ~하자", "어쩔수없을거같아", "그렇게라도 하자" 같은 체념·즉흥 결정 어조)로 결정 항목을 추가하기 전에 명시 확인을 받는다.

## 갱신 (구현·리뷰 후)

구현·리뷰 과정에서 새로 발생하거나 초기 작성 시점과 달라진 의사결정을 반영한다.

plan 작성 뒤로는 [verify 「decisions.md 최신화」](../../steps/verify.md#step-66-decisionsmd-최신화) 한 번만 고친다.

- 대상: 기술 선택 변경, 트레이드오프 새로 인지한 것, 리뷰 피드백으로 뒤집힌 결정 등
- PLAN에서 정했는데 IMPL·verify에서 접은 결정도 적는다 — 무엇으로 바뀌었는지와 함께
- 단순 코드 변경 이력은 적지 않는다. **"왜 그렇게 했는가"만 남긴다.**
- **코드에서 역산 가능한 표면값(커밋 SHA·파일 경로·폴더 구조 등)은 근거·연결 서술에 박지 않는다** (생성·갱신 공통). "왜"를 설명하려 코드 앵커가 꼭 필요하면 이름 수준(어떤 모듈·어떤 결정)에서 그친다.
