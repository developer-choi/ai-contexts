# Requirement Review

기획서, 디자인 시안, 채용 과제 요구사항을 코드로 옮기기 전에 개발자 관점에서 살펴보고, 모호한 부분과 예외 상황을 미리 찾아내는 스킬입니다. 작업 워크플로우의 배경 파악 단계에서 부릅니다.

## 동기

제가 요구사항을 받자마자 코드부터 짜면, 빈틈은 늘 짜는 도중에야 드러났습니다. "이 상태에서 뒤로 가면?" 같은 질문이 개발 중에 떠오르고, 그때마다 기획자에게 확인을 요청하느라 작업이 멈추곤 했습니다.

그 빈틈을 코드를 짜기 전에 질문으로 먼저 끄집어내 두려고 만든 스킬입니다.

## 살펴보는 자료

세 종류의 자료를 다루며, 필요한 것만 골라 켤 수 있습니다.

- **기획서**: 페이지 단위로 화면의 목적, 데이터 흐름, 예외 상황을 정리합니다.
- **디자인 시안**: 화면 크기에 따른 배치, 상태별 화면, 눌렀을 때의 반응을 검토합니다.
- **채용 과제**: 요구사항에서 숨은 평가 기준을 추론하고 어떻게 만들지 방향을 잡습니다.

기획서와 디자인 시안은 앞 단계에서 모아둔 자료를 페이지 하나씩 꺼내 같이 분석하고, 논의하고, 정한 뒤 다음 페이지로 넘어갑니다. 빠진 페이지가 있을 때만 그 페이지를 따로 요청합니다.

둘 다 켜져 있으면 같은 페이지에서 기획서를 먼저 정한 뒤 디자인을 살펴, 같은 페이지를 두 번 돌지 않습니다.

기획서도 디자인 시안도 없이 이미 돌아가는 코드만 있으면, 자료를 받는 대신 그 코드를 읽어 현재 동작을 역으로 정리합니다. 제가 미리 만들어 둔 화면 시안이 원본일 때는 그 시안을 기준으로 같은 절차를 따릅니다.

채용 과제는 페이지 개념이 없어 자체 순서를 한 번에 따릅니다. 자료를 함께 살피고, 평가 기준을 추론하고, 기술 스택과 폴더 구조 같은 프로젝트 결정을 내립니다.

그다음 화면별로 자료를 정리하며 필요한 공통 컴포넌트를 설계하고, 마지막으로 모호한 부분을 질문으로 모읍니다.

## 산출물

페이지마다 분석 문서를 하나씩 만들고, 여러 페이지에 공통으로 걸리는 내용은 전체 문서에 따로 모읍니다. 채용 과제라면 추론한 평가 기준, 대상 서비스 분석, 프로젝트 전반의 결정과 할 일을 각각의 문서로 남깁니다.

이 문서들에는 자료가 다루지 않은 예외 상황을 질문으로 뽑아 담습니다. 예를 들어 좌석 예약 기획서를 살펴보면 이런 질문이 나옵니다.

```markdown
## 기획자/디자이너 질문 목록

- 좌석을 선택한 뒤 결제하기 전에 다른 사용자가 같은 좌석을 예약하면 어떤 화면을 보여주나요?
- 예약 플로우 도중 브라우저를 닫았다가 다시 열면
  처음부터 다시 시작하나요, 이어서 진행하나요?
- 뒤로 가기로 이전 단계로 돌아갔을 때 선택했던 좌석이 그대로 유지되나요?
- 공연명이 매우 길 때 목록에서 말줄임 처리하나요, 줄바꿈하나요?
```

이렇게 정리된 결과는 이후 작업을 어떤 단위(PR)로 나눌지, 어디서부터 만들지 판단하는 데 씁니다.

## 전체 흐름

살펴볼 자료를 고르면, 자료 성격에 따라 진행 방식이 갈라져 마지막에 한 벌의 질문 목록으로 모입니다.

```
살펴볼 자료 선택
  │
  ├──→ 기획서 · 디자인 시안
  │      페이지 하나씩:  기획서 정하기 → 디자인 검토 → 다음 페이지
  │
  ├──→ 채용 과제
  │      자료 검토 → 평가 기준 추론 → 프로젝트 결정
  │
  ▼
모호한 부분 · 예외 상황을 담은 질문 목록
```

질문 목록까지 정리한 뒤에는 이번 리뷰를 되짚습니다. 정해둔 점검 항목이 놓친 문제가 없었는지 자료를 다시 보고, 항목 자체를 어떻게 보완할지 기록해 둡니다.
