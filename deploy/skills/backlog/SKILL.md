# Skill Backlog

## 목적

백로그를 잘 쌓아두고 잘 처리한다.

필기를 수집·분류·정리하여 백로그로 쌓아두는 스킬. 뒤죽박죽 메모를 destination(AC 자체·외부 레포·발행)으로 분류하고, 기존 백로그와 병합하고, 기존 스킬·프로젝트와의 관계를 식별한다. 개별 스킬의 설계·구현은 skill-creator가 담당한다.

`/backlog` 슬래시 명시 호출 시에만 동작한다. 자동 트리거 매핑은 두지 않는다 — 자연어로 들어온 메모·기록 의도는 메인 LLM이 [메모·기록 도구 분리](../../rules/global.md#메모기록-도구-분리)에 따라 처리한다.

## 인자 라우팅

호출 인자의 **첫 토큰**으로 진입 흐름을 가른다. 첫 토큰이 아래 예약어가 아니면(또는 인자가 없으면) 기본 캡처 흐름이다.

| 첫 토큰 | 진입 흐름 |
|---|---|
| (없음·메모·파일경로) | 캡처 — [입력 수집](#입력-수집) → [정리](#정리). 영역은 자동 분류 |
| `review` `[대상]` | [리뷰 모드](#리뷰-모드). 대상(프로젝트·파일)을 명시한다 — 아래 참고 |
| `exec` `[대상]` | [실행 모드](#실행-모드). 대상(프로젝트·파일)을 명시한다 — 아래 참고 |
| `orchestrate-exec` | [오케스트레이션 실행 모드](#오케스트레이션-실행-모드) — 전 영역 `status: ready` 항목을 의존성 분석·n단위 분할로 일괄 병렬 디스패치 |
| `projects` / `articles` `[메모]` | 캡처하되 [영역 분류](#1-영역-분류)를 건너뛰고 지정 영역으로 강제 라우팅. 토큰 뒤 나머지가 메모(없으면 입력 수집으로) |

- 영역 토큰은 자동 분류를 생략하는 **선택적 오버라이드**다. 토큰 없이 넣으면 자동 분류가 영역을 정한다. AC 자체(`ai-contexts`) 항목도 자동 분류로 `projects/ai-contexts/`에 들어가므로 별도 토큰을 두지 않는다.
- `review`·`exec` 대상: **기본값 없음** — 대상 프로젝트를 명시한다(생략 시 어느 프로젝트의 백로그인지 사용자에게 되묻는다). 지정 프로젝트의 `active/` 안에서 파일명 식별자(부분 일치)로 더 좁힐 수 있다.

## 범위

모든 백로그를 별도 `backlog` 레포에서 중앙 관리한다. 영역은 `projects/`(레포별 작업·지식·참고)와 `articles/`(발행 재료)이며, 두 영역의 차이는 [영역 분류](#1-영역-분류)에서 정의한다.

## 레포

백로그는 AC(public)와 분리된 **별도 private 레포 `backlog`**(약어 B)에 산다. 개인 메모라 public 노출을 막기 때문이다.

- **경로**: `~/WebstormProjects/main/backlog/`
- **원격**: `https://github.com/developer-choi/backlog` (private)
- **클론**: 레포가 없는 기기에서는 클론한다:
  ```
  git clone https://github.com/developer-choi/backlog.git ~/WebstormProjects/main/backlog
  ```

[CRITICAL] 백로그를 읽거나 쓰기 전에 `~/WebstormProjects/main/backlog/CLAUDE.md`를 Read한다. 영역별 경로·파일명, frontmatter 어휘, 항목 양식, Ready 게이트 문항, 커밋 규칙의 단일 출처다. 본 스킬은 그 규격을 중복 정의하지 않으므로, 읽지 않으면 산출물의 위치·양식을 정할 수 없다.

## 준비

### 기존 백로그 파악

`backlog/` 하위의 백로그 영역(`projects/`, `articles/`)을 읽는다.

### 기존 스킬 파악

`deploy/skills/` 하위 SKILL.md들의 description을 읽어 현재 스킬 목록을 파악한다. 필기를 분류할 때 기존 스킬과의 관계를 식별하기 위함이다.

## 정리

### 1. 영역 분류

입력된 필기를 **destination**(어디서 처리·반영되나)으로 분류한다. destination은 캡처 시점 **intent**가 정한다 — 목적지 없는 백로그는 없다. 하나의 필기가 여러 destination에 걸치면 각각에 배분한다. 단, 호출 인자에 영역 토큰(`projects`/`articles`)이 주어졌으면 [인자 라우팅](#인자-라우팅)에 따라 분류를 건너뛰고 그 영역으로 직행한다.

| 영역 | 대상 | 항목 단위 |
|------|------|-----------|
| `projects/{project}/{topic}/` | 레포별 작업·지식·참고 (AC 자체 포함 → `projects/ai-contexts/`) | 주제·역할 단위 |
| `articles/{slug}/` | 기술블로그에 발행할 포스트 재료 | 포스트 단위 |

`ai-contexts`·`private-playground`의 `active/`에 캡처하는 **fix·룰 트래커 항목**(`## 기대상황`을 갖는 양식)은 **할 일 트래커** — 기본 `status: ready` 등록 대상이고 리뷰/실행 모드의 주 무대다. 같은 폴더라도 개인 메모·완성형 지식 노트(기대상황 없는 항목)는 트래커가 아니라 `status: ready` 강제 대상이 아니다. 다른 `projects/`는 기본 무상태이되 `status: ready`를 opt-in하면 Ready 게이트가 적용된다(게이트는 영역무관 — 백로그 레포 CLAUDE.md 「Ready 게이트 — 자가검증」). `articles/`는 비-트래커(발행 재료)로 `status`를 쓰지 않는다.

#### projects의 destination은 intent로 가린다

같은 코드 주제(react 등)라도 destination은 **왜 적었는지**로 갈린다:

- **지식 이해 목적** (학습·read-later·사고 흔적) → 지식 레포 `projects/knowledge-archive/`. 이해한 뒤 코드화가 결정되면 그때 해당 레포(MP 등) 항목으로 graduate한다
- **구현 참고·레포 작업** ("누가 이렇게 개발하더라" 참고 링크, 특정 레포의 코드 작업) → 그 레포 `projects/{monorepo-playground 등}/`
- **intent 모호** → `knowledge-archive` fallback (이해가 표현에 선행하므로)

흐름은 양방향이다: 구현 참고(MP) 링크가 "개념을 모르겠다"로 이어지면 KA 항목을 파생하고, KA 지식이 코드화로 이어지면 MP 항목을 파생한다.

`projects/`와 `articles/`의 구분: projects/는 **내부 작업·지식**(처리·반영 destination이 레포)이고, articles/는 **발행 재료**(외부 공개, 나올 포스트 1편의 축)다. 같은 코드 주제라도 "이해하거나 레포에 반영"이면 projects/, "글로 써서 올릴 재료"면 articles/로 분류한다.

### 2. 기존 스킬·프로젝트 연결

`projects/` 항목(AC 자체 포함)은 아래 중 하나로 분류한다:

- **기존 스킬·프로젝트 개선**: `deploy/skills/` 또는 등록된 프로젝트의 개선. 반영 위치는 frontmatter `target`에 적는다 (표기 규격은 백로그 레포 CLAUDE.md 「frontmatter 규칙」).
- **신규**: 기존에 없는 새로운 스킬·작업.

### 3. 기존 백로그와 병합

해당 영역의 기존 `.md` 파일을 읽어 대조한다:

- `projects/{project}/{topic}/`
- `articles/`

대조 규칙:

- **중복**: 같은 내용이면 제거
- **추가**: 무상태 지식노트·발행 재료는 기존 파일에 관련 섹션이 있으면 그 섹션에 병합한다. 트래커 항목은 파일=백로그이므로 섹션으로 덧붙이지 않고 대상 target 디렉토리에 새 항목 파일을 만든다
- **신규**: 해당 주제·항목이 없으면 새로 만든다 — 지식노트는 새 섹션, 트래커는 새 파일

### 4. 배치·파일명

경로·파일명 규격은 백로그 레포 CLAUDE.md의 「영역별 경로·파일명」에 있다. 기존 디렉토리·파일이 있으면 거기에 넣는 것이 원칙이므로, 새로 만들기 전에 대상 위치를 먼저 훑는다.

### 5. 등록 상태 — 기본 ready (`ai-contexts`·`private-playground` 트래커 항목)

`ai-contexts`·`private-playground`의 `active/`에 캡처하는 **fix·룰 트래커 항목**(`## 기대상황`을 갖는 양식)은 사용자가 명시적으로 낮은 상태를 요청하지 않는 한("일단 적어만 둬", "아이디어만" 등) **frontmatter `status: ready`로 등록한다**. 작성 세션이 정보가 가장 풍부한 시점이고, 미뤄둔 보강은 잘 일어나지 않는다. 개인 메모·완성형 지식 노트(기대상황 없는 항목)는 트래커가 아니므로 이 기본-ready 대상이 아니다 — `status` 없이 둔다. 다른 projects 항목은 기본 무상태이고, `status: ready`는 opt-in이다(달면 아래 게이트가 적용된다).

- 캡처하면서 「Ready 게이트」 필수 문항을 빈칸 없이 채운다. 채울 정보가 부족하면 등록 전에 사용자에게 그 자리에서 묻는다 — 미뤄두면 안 채워진다.
- critic 서브에이전트(sonnet)로 게이트 문항을 검증하고, 미통과 보강 → 재검증을 0건까지 반복한 뒤 `status: ready`를 단다 (리뷰 모드의 critic 단계를 등록 시점으로 앞당긴 것).
- `ideation`/`draft`는 사용자가 명시적으로 요청한 경우에만 쓴다. 이때도 「Draft · Ideation 최소검증」은 채운다.

## 산출물 형식

frontmatter 어휘(`title`·`status`·`priority`·`focus`·`tags`·`target`·`scope`·`dependencies`), 항목 본문 양식, 「Ready 게이트」 문항은 백로그 레포 CLAUDE.md에 있다. 이 스킬은 그 규격을 중복 정의하지 않는다 — 작성·검증 전에 그 파일을 읽는다 ([레포](#레포)).

### 사고 회고는 발견 즉시 Ready

사고가 발생한 PR·세션 안에서 발견 즉시 `status: ready`까지 끌어올린다. 발견 시점의 정보(PR 회차, 커밋 SHA, IMPL 산출물, 수치)는 그 시점에만 풍부하고 며칠 뒤엔 휘발된다. "나중에 보강하자"가 사고 회고 백로그에는 작동하지 않는다.

## 백로그 표면화

백로그는 사용자가 의식적으로 뒤지지 않으면 무한정 쌓인다. 이를 막기 위해, **어떤 프로젝트에서 작업을 시작하는 순간** 그 프로젝트에 묶인 미해결 백로그 **폴더**를 자동으로 컨텍스트에 띄운다. 발동은 `UserPromptSubmit` hook(`deploy/hooks/surface-backlog.mjs`)이 보장하고, 유사도 판단·제안은 메인 LLM이 한다.

스킬을 거치지 않고 다이렉트 프롬프트로 작업해도 잡으려고 트리거를 **스킬 발동이 아니라 사용자 프롬프트**에 건다. 매칭 축은 **스킬이 아니라 cwd(작업 디렉터리)** 다.

대상 영역은 **`projects/`(AC 자체 `ai-contexts` 포함, 외부 레포)** 뿐이다. `articles/`·`roadmaps/`와 `archives/`(`history/` 등)는 "해결할 액션"이 아니라 발행 재료·학습 코스·종결 자료이므로 표면화하지 않는다. (projects/는 지식·참고도 담지만, 그 레포에서 작업할 때 같이 뜨는 게 맞으므로 표면화 대상이다.)

### cwd → 폴더 매핑 (설정 불필요, 파생)

hook이 cwd의 `WebstormProjects/<group>/<project>` 세그먼트에서 프로젝트명을 뽑아 폴더를 **유도**한다. 별도 매핑 설정 파일이 없다.

| cwd 프로젝트 | 가리킬 폴더 |
|---|---|
| 모든 프로젝트 (`ai-contexts`·`monorepo-playground`·`private-playground` 등) | `projects/<project>/active/` |

외부 레포는 `active/` 하위만 가리킨다 — `inactive/`는 경로에서 빠져 표면화되지 않는다(백로그 레포 CLAUDE.md 「active / inactive / domains 격리」). 해당 폴더가 존재하고 그 아래 `.md`가 하나라도 있을 때만 띄운다. 그래서 새 프로젝트의 `projects/<name>/active/`에 `.md`를 두면 **자동으로** 표면화 대상이 된다 — 매핑을 손볼 필요가 없다. 백로그 파일을 추가·수정·삭제해도 hook은 폴더만 가리키고 내용은 그 순간 LLM이 라이브로 훑으므로 항상 최신이다(파일 단위 매니페스트·frontmatter 태그가 없다).

### 노이즈 제어 — 세션당 폴더당 1회

`UserPromptSubmit`은 매 메시지마다 발동하므로, 같은 폴더에 매 턴 *전체 안내 블록*을 주입하면 시끄러울 뿐 아니라 메인 LLM을 매 턴 백로그에 과몰입시켜 표면화를 넘어 관련 없는 "저장할까요?" 제안까지 유발한다. hook은 `session_id + 폴더`를 임시 상태파일(`os.tmpdir()/claude-backlog-surfaced/<session_id>.json`)에 기록하고, **그 세션에서 그 폴더를 처음 건드릴 때 전체 블록을 1회만** 주입한다. 이미 안내한 폴더는 이후 턴에 아무것도 주입하지 않고 빠진다. 폴더는 cwd에서 파생되어 세션 내내 고정이므로 첫 주입이 무관한 프롬프트에 낭비되지 않는다. (`session_id`가 없는 폴백 환경에서는 매 턴 전체 블록으로 동작한다.)

트레이드오프: 첫 턴에 LLM이 폴더를 훑지 않고 넘어가면 이후 관련 작업이 와도 그 세션에서는 다시 안내되지 않는다(누락 위험). 매 턴 priming 제거를 누락 0보다 우선한 선택이다.

표면화된 후보를 구현 완료해 폴더에서 파일을 삭제하면(실행 모드 8번) 다음부터는 그 폴더에 안내할 항목이 줄어든다. 폴더가 비면 더 이상 뜨지 않는다.

## 리뷰 모드

기존 백로그를 순회하며 Ready 게이트로 검증하고 frontmatter `status`를 갱신하는 모드. 사용자가 백로그 본문을 매번 검수하지 않을 수 있다는 전제에서, critic 서브에이전트가 사용자 대신 객관적 게이트 역할을 한다.

1. 인자로 지정된 프로젝트의 `projects/<project>/active/` 하위 파일을 priority 순(1→2→없음)으로 순회한다(대상 미지정 시 어느 프로젝트인지 사용자에게 되묻는다 — 기본값 없음). 호출 인자에 파일명 식별자가 있으면 매칭 항목으로 좁힌다. Ready 게이트는 영역무관이므로 `status: ready`를 단(또는 달려는) 항목이면 AC·외부 레포 가리지 않고 리뷰 대상이다(전환기엔 구 `## [ready]` 헤딩 항목도 동일하게 인정한다). `articles/`는 비-트래커라 제외.
2. 각 항목에 대해 critic 서브에이전트(sonnet)를 spawn하여 「Ready 게이트」의 자가검증 문항을 적용한다
   - critic 입력: 백로그 항목 본문 + 백로그 레포 CLAUDE.md 「Ready 게이트 — 자가검증」 절 본문
   - critic 출력: 각 문항에 대해 통과/미통과를 판정하고, 미통과면 어느 정보가 비어 있는지 보고
3. critic 결과를 사용자에게 요약 보고한다
   - 전체 통과: `status: ready` 표기 가능
   - 미통과: 미통과 항목을 사용자에게 제시하고, 보강할지 사유를 명시할지 결정
4. `target`이 있으면 해당 스킬의 현재 SKILL.md를 읽고, 현재 구조와 대조하여 백로그를 더 정확하게 기술한다
5. 사용자와 대화하며 부족한 부분을 구체화한다
   - 사용자가 아이디에이션하려는 느낌이 보이면 충분히 대화한다. AI가 먼저 다음 항목으로 넘어가지 않는다
   - 사용자가 "넘어가자", "다음", "패스" 등 명시적으로 말할 때만 다음 항목으로 이동한다
   - 항목을 보여준 뒤 "이건?" 같은 되물음 금지. 사용자가 반응할 때까지 기다린다
6. 보강 후 critic 재호출 → 0건 통과까지 반복 (글로벌 룰 「검증은 수렴할 때까지 반복」을 따른다)
7. 통과한 파일은 frontmatter `status`를 `ready`로 갱신한다. 브레인스토밍 단계이면 `ideation`, 윤곽은 잡혔으나 일부 문항 미통과이면 `draft`로 표기한다

## 실행 모드

`status: ready` 항목을 priority 순(1→2→없음)으로 실행하는 모드.

1. backlog 레포에서 **인자로 지정된 프로젝트**의 `projects/<project>/active/` 하위를 priority 순(1→2→없음)으로 순회하며 `status: ready` 파일을 찾는다(전환기엔 구 `## [ready]` 섹션도 동일하게 인정한다)(대상 미지정 시 어느 프로젝트인지 사용자에게 되묻는다 — 기본값 없음). 파일명 식별자가 있으면 매칭되는 파일로 좁혀 그것부터 실행한다
   - **저집중 필터(opt-in)**: 사용자가 저집중 배치를 요청하면 `focus: low`인 파일만 대상으로 좁힌다(무표기·`focus: high` 제외). 요청 없으면 기본은 전체(현행)
   - **선행 검증**: 그 파일에 frontmatter `dependencies`가 있으면, 각 선행 경로가 해결됐는지(백로그 레포 CLAUDE.md 「부재=해결」 기준) 확인한다. 미해결 선행이 있으면 이 파일을 **건너뛰고 사용자에게 경고**한다(차단이 아니라 안내). 모두 해결됐으면 정상 진행한다
2. `status: ready` 파일을 찾으면 **그 항목의 target 레포** 기반 임시 워크트리를 만든다. 레포·기본브랜치는 항목에서 파생한다 — `<레포경로>`는 target(또는 프로젝트명)에서, `<기본브랜치>`는 `git -C <레포경로> symbolic-ref --short refs/remotes/origin/HEAD`로 구한다(레포마다 master/main 상이). `<식별>`은 실행하는 백로그 항목(파일명)에서 딴 고유 이름으로 짓는다 — 워크트리 디렉터리와 브랜치에 같은 `<식별>`을 써서, 여러 exec를 병렬로 돌려도 디렉터리·브랜치가 겹치지 않게 한다. `git worktree add`로 만들면 생성 직후 self-heal hook이 의존성을 자동 설치한다(훅 발동은 추적되는 `.githooks`가 보장하므로 이 설치는 편의):
   ```
   git -C <레포경로> worktree add -b backlog-exec-<식별> <레포경로>-<식별> <기본브랜치>
   ```
3. **반영 여부 선확인**: 임시 워크트리에서 frontmatter `target` 경로(없으면 파일이 지목하는 경로)를 읽고, 이 항목이 요구하는 변경이 이미 반영돼 있는지 대조한다
   - **이미 반영됨**: 구현하지 않는다. 사용자에게 "이미 반영돼 건너뜀"을 보고하고 7번(정리)으로 건너뛴다. 8번에서 파일 삭제는 동일하게 수행한다
   - **미반영**: 4번으로 진행한다
   - 등록 시점과 실행 시점 사이에 다른 세션·기기에서 같은 변경이 들어갔을 수 있으므로, 구현 전 항상 현재 상태를 확인한다
4. 임시 워크트리에서 해당 항목을 구현한다. **「기대상황」을 목표로 삼고, 「현재 생각중인 방법」은 작성 세션의 후보 의견으로만 참고해 재판단한다** — 더 나은 방법이 보이면 그쪽으로 간다(맹목 적용 금지). 「현재상태」는 왜 이 변경이 필요한지의 근거다
   - **`bench` 태그 항목이면 스킬 편집 스킬 선로드**: frontmatter `tags: [bench]`인 항목을 구현하기 전에 `/scw`와 `/skill-creator:skill-creator`를 로드해 그 규칙·체크리스트를 사전 적용한다. bench 항목은 벤치를 돌려 그 결과로 스킬·프롬프트 본문을 바꾸는 작업이라 두 스킬의 감사·설계 기준이 필요하다
5. 임시 워크트리에서 커밋한다 (푸시하지 않는다)
6. **기본 브랜치 통합 안내**: 기본 브랜치 머지는 사용자가 한다. AI는 보호 브랜치(레포 기본 브랜치) 포인터를 직접 옮기지 않는다 — 머지 직전까지 끝내고 사용자에게 명령을 안내한다 (`check-git-merge-policy.mjs` hook으로도 차단됨)
   - 임시 워크트리(= 구현한 세션)에서 현재 `<기본브랜치>` 위로 재배치한다. 충돌이 나면 이 워크트리에서 해결한다 — 구현 맥락이 살아있는 세션이 가장 잘 푼다. 중앙에서 모아 병합하지 않는 이유다
     ```
     git rebase <기본브랜치>
     ```
   - 재배치가 끝나면 사용자에게 그 레포의 메인 워크트리(`<기본브랜치>`)에서 실행할 ff-only 머지 명령을 안내하고 대기한다 (AI가 실행하지 않는다)
     ```
     git merge --ff-only backlog-exec-<식별>
     ```
   - 사용자 머지 중 병렬 세션이 그사이 `<기본브랜치>`를 옮겨 ff가 실패하면, 이 워크트리에서 `git rebase <기본브랜치>`부터 다시 하고 사용자에게 재안내한다 (먼저 통합한 세션이 이기고, 진 세션이 재배치로 따라붙는다)
7. **임시 워크트리·브랜치 정리**: 사용자가 기본 브랜치 머지 완료를 알리면 워크트리를 제거하고 임시 브랜치를 삭제한다 (구현을 건너뛴 경우 브랜치에 커밋이 없으므로 머지 안내 없이 바로 정리)
   ```
   git -C <레포경로> worktree remove <레포경로>-<식별>
   git -C <레포경로> branch -d backlog-exec-<식별>
   ```
8. backlog 레포에서, 방금 실행 완료한(또는 이미 반영돼 건너뛴) 파일을 삭제한다
9. backlog 레포에서 커밋한다 (post-commit이 origin으로 자동 push)
10. 다음 `status: ready` 파일로 반복한다

## 오케스트레이션 실행 모드

`status: ready` 항목 전체를 의존성으로 묶어 **서로 독립적인 n개 단위**로 쪼갠 뒤, 사용자 1회 승인으로 **병렬 디스패치**(즉시 또는 지정 시각 예약)하는 상위 모드. 「실행 모드」가 단위 실행 프리미티브이고, 이 모드는 그 위에서 수집·의존성 분석·분할·프롬프트 작성·사전 선확인을 끝낸 뒤 단위들을 던진다.

루트의 역할은 **잘 쪼개서 던지기까지**다 — 던지고 나면 결과를 모으거나 종합하지 않고, 머지하지도 않는다. 각 단위는 자기 브랜치를 그 자리에 남기고, 멈추면 멈춘 채로 둔다. 사용자가 나중에 각 브랜치를 직접 리뷰·머지한다. 「실행 모드」가 사용자 지정 한 항목을 도는 반면, 이 모드는 전 프로젝트 `projects/{project}/active/`의 `status: ready` 항목을 일괄 수집해 fan-out한다.

1. **수집**: backlog 레포에서 전 프로젝트 `projects/{project}/active/` 하위를 훑어 `status: ready` 파일을 모두 모은다(frontmatter만 읽어 본문은 로드하지 않는다; 전환기엔 구 `## [ready]` 섹션도 동일하게 인정한다). priority(1→2→없음)를 함께 기록한다. 대상이 0개면 "처리할 ready 없음"으로 끝낸다. 사용자가 저집중 배치를 요청하면 `focus: low`인 항목만 수집한다(무표기·`focus: high` 제외); 요청 없으면 전체.
2. **의존성 파악**: 항목 간 선후를 파악한다 — frontmatter `dependencies`(「부재=해결」 기준)로 파악하고, 그게 없으면 본문에서 주제·인과로 추론한다. 이 의존성은 **순서가 아니라 묶음**에 쓴다(다음 단계).
3. **서로 독립적인 단위로 분할**: `status: ready` 파일들을 묶어 작업 단위를 만들되, **각 단위가 자기 레포의 기본 브랜치에서 단독 실행 가능**하도록 쪼갠다. 의존 관계가 있는 항목들은 한 단위 안에 같이 넣어 그 세션이 내부에서 순서대로 처리한다 — 단위끼리는 서로 의존하지 않게 한다. 단위 수는 그때그때 판단(고정값 없음). `scope`에 `global` 토큰이 붙은 항목은 같은 스캔 범위끼리 한 단위로 묶어 컨텍스트 로드를 아낀다.
4. **단위별 실행 프롬프트**: 각 단위마다 자족적 프롬프트를 작성한다. 대상 `status: ready` 항목 본문, target 레포·경로, 그 레포의 커밋 컨벤션, 그리고 「실행 모드」 절차 지시를 담는다 — 다른 세션이 추가 질문 없이 실행할 수 있어야 한다.
5. **일괄 선확인**: 작성한 프롬프트 전체를 훑어, 실행 중 멈춰 물어야 할 결정·모호점을 모두 추려 사용자에게 **한 번에** 묻는다. 받은 답을 해당 프롬프트에 박아 넣는다. **디스패치되는 서브에이전트에는 사용자에게 되묻는 수단이 없다** — 그래서 여기서 해소하지 못한 결정이 남은 유닛은 중도에 멈추는 게 아니라 그 결정 지점에서 **아무것도 못 하고 종료된다**(멈춤이 아니라 무산). 사용자 입력이 필요한 항목은 이 단계에서 반드시 해소하고, 해소할 수 없으면 그 유닛을 이번 배치에서 제외한다. 예측 못 한 결정이 실행 중 튀어나오면 그 유닛만 무산되고(전체는 계속) 나중에 리뷰에서 처리한다 — 선확인은 이 무산을 줄이는 게 목적이며 0을 보장하지는 않는다.
6. **승인 게이트**: 단위 목록·각 프롬프트를 제시하고 사용자 승인을 기다린다. 여기까지가 디스패치 전 준비다.
7. **디스패치 타이밍 선택**: 승인 후 "지금 던질지, 특정 시각에 던질지" 묻는다.
   - **지금**: 8번을 즉시 실행한다.
   - **시각 지정**: 현재 로컬 시각과 지정 시각의 차이를 계산해 그 시각의 5필드 cron(`분 시 일 월 *`)을 만들고, `CronCreate(recurring: false)`로 8번 실행을 예약한다. **이 예약은 세션 전용(인메모리)이다 — 도구 설명상 `durable`은 무효이고, 이 REPL 세션이 지정 시각까지 살아있고 절전(sleep/hibernate)에 들어가지 않아야만 발동한다. 세션을 닫거나 컴퓨터가 절전되면 예약은 사라져 발동하지 않는다.** 따라서 예약을 "완료"로 단정하지 말고, **예약 직후 이 조건과 미발동 가능성을 사용자에게 반드시 선고지**한다("세션·절전 유지 시에만 발동, 못 유지하면 지금 디스패치하거나 다음 세션에서 수동 트리거"). 각 단위 프롬프트는 backlog 레포 `orchestrate-exec/<단위슬러그>.md`에 저장한다 — 재시작 생존용이 아니라, 예약이 날아가도 새 세션에서 수동 재트리거할 **복구 재료**다. 예약 프롬프트엔 "이 모드의 병렬 디스패치(8번)를 실행하라 + 단위 프롬프트는 위 경로에서 읽으라"는 자족적 지시를 담는다. 시각 계산·cron 변환 자체는 내부에서 처리하되, 위 미발동 선고지는 사용자에게 노출한다. 진짜 무인 예약(세션·절전 유지 불가)이 필요하면 세션 cron으로 보장할 수 없으므로 OS 레벨 예약(Windows 작업 스케줄러 등)을 사용자에게 안내한다.
8. **병렬 디스패치**: (지금이면 즉시, 예약이면 발동 시) 각 단위를 백그라운드 서브에이전트로 **동시에** 던진다(단위끼리 독립이므로 순서·대기 없음). 던지고 나면 루트의 일은 끝 — 단위가 멈추거나 실패해도 종합·재시도하지 않는다.

### 디스패치 단위 실행 — 「실행 모드」 재사용 + 변경점

각 단위는 「실행 모드」의 단위 절차(임시 워크트리 생성 → 반영 선확인 → 구현 → 커밋 → 기본 브랜치 위 rebase)를 그대로 따른다. 단, 던지고 끝나는 디스패치라 다음만 바꾼다:

- **머지 대기 없음**: 단위는 rebase까지만 하고 멈춘다. ff-only 머지는 사용자가 나중에 리뷰할 때 한다. 머지를 기다리며 블로킹하지 않는다.
- **파일 삭제 안 함**: backlog `status: ready` 파일은 머지가 사람 손에 확정되기 전까지 지우지 않는다 — 디스패치 중에는 그대로 둔다.
- **다중 레포**: 각 단위는 그 항목의 target 레포(AC 자체 포함, MP·KA·DC·PP 등)에서 워크트리를 만들어 작업·커밋한다. 워크트리·브랜치 식별자는 영문 소문자-하이픈 슬러그로 짓는다(레포·단위가 겹치지 않게).
