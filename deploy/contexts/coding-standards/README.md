# 코딩 스탠다드

개발하면서 반복해서 부딪히는 판단을 적어둔 기준 모음입니다.

## 다루는 기준

다음 주제들에 대한 기준을 정리하고 있습니다.

- **React 컴포넌트 패턴**: 컴포넌트 설계, props 구조, 상태 관리 방식
- **TypeScript 타입 설계**: 타입 안전성과 유지보수성을 고려한 패턴
- **코드 품질 원칙**: 가독성, 유지보수성에 대한 기준
- **네이밍 컨벤션**: 변수·함수·파일·폴더 이름을 짓는 기준
- **HTML/CSS 마크업**: 시맨틱 마크업, 스타일링 패턴
- **코드를 어디에 둘 것인가**: 어느 폴더에 두는지, 어느 쪽이 어느 쪽을 가져다 쓰는지에 대한 기준
- **서버에서 받은 데이터 검증**: Zod로 스키마를 정의하고 거기서 다른 스키마를 만들어내는 기준
- **서버 통신·폼 라이브러리 사용 패턴**: 서버에 요청을 보내는 함수의 인자 모양, react-hook-form 사용 방식
- **주석과 코드 검사 예외**: 주석을 남길 수 있는 경우, 코드 검사 도구의 경고를 끌 수 있는 경우

## 상황에 맞는 기준 적용

모든 기준을 모든 프로젝트에 똑같이 적용하지는 않습니다.

회사 프로젝트에서는 팀원 누구나 동의할 수 있는 범용적인 기준만 적용합니다.

개인 프로젝트에서는 네이밍, 폴더 구조, 주석을 남기는 조건 등 더 세밀한 개인 기준까지 적용합니다.

상황에 따라 알맞은 수준의 기준을 고르는 것도 엔지니어링 판단의 일부라고 생각합니다.

## 기준을 적어두는 이유

코딩 스탠다드에는 반복된 경험에서 얻은 엔지니어링 판단을 담습니다. "이 상황에서는 이렇게 하는 게 낫다"는 결론에 이르기까지의 맥락과 근거를 함께 기록합니다.

이렇게 적어두면 새로운 상황에서도 일관된 판단을 내릴 수 있고, 팀에 합류하는 사람에게 "왜 이렇게 하는지"를 설명하기도 수월해집니다.
