# pr-body 재료

본문에 옮겨 펼 골격이 아니라, PR 본문이 다루는 재료 목록이다. 이 파일의 제목·절 이름은 본문에 넣지 않는다.

## 안내 문구 매핑

| subtype | 안내 |
|---------|------|
| (없음, 일반 PR) | "리뷰어가 알아야 할 핵심 결정 적어줘" |
| recruitment | "너가 가장 어필하고 싶은 부분 적어줘" |

## PR 제목

패키지 본문의 H1이 PR 제목이다. 게시할 때 H1은 PR 제목 칸에, frontmatter와 H1을 뺀 나머지는 PR 본문에 넣는다.

제목은 합의한 `key_message`를 한 줄 길이로 줄이거나 늘려 짓는다. 줄일 때는 `key_message`의 주장을 남기고, 그 주장을 받치는 방법·근거부터 덜어낸다.

- 확인한 결과가 있으면 한 일이 아니라 드러난 것을 담는다
- 명사형 보고체로 끝낸다
- 끝에 마침표를 찍지 않는다
- `feat:` 같은 conventional commit 접두사를 붙이지 않는다
- 공백 포함 60자 이하

## 재료 위치 찾기

재료를 읽기 전에 한다. write-doc `plan-materials.mjs`가 대상 레포 메인 체크아웃의 `plan/` 아래 이름 목록과 todo가 든 md 목록을 낸다. `plan/`이 없다고 나오면 건너뛴다.

1. **위치 추론**: 이 PR의 재료가 어디 있는지 이름 목록**만** 보고 추론한다. 파일 내용은 열지 않는다(후보마다 열면 쓰지 않을 재료까지 컨텍스트에 실린다). 사용자가 재료를 직접 들고 왔으면(경로를 알려 줬거나 붙여 넣었으면) 이 추론은 건너뛴다.
   - 이름이 틀리게 읽힐 수 있다고 전제한다(PR 번호와 폴더 번호가 다르거나, 이미 써 둔 패키지를 다듬으러 온 경우).
   - 확신이 서면 추론 근거를 한 줄로 밝히고 진행하고, 아니면 후보 이름을 보여 사용자에게 묻는다.
2. **todo 목록**: 스크립트가 낸 todo 목록을 사용자에게 보인다. 메모 바구니(`plan/background/consumable/todo.md` 등)에 이 PR 본문에 들어갈 항목이 있을 수 있으니, 사용자가 목록을 보고 쓸 항목을 정한다.

## 재료

절은 주제마다 하나씩 세운다. 주제는 이 PR에서 내린 결정 하나, 또는 만든 동작 하나다. 절 제목은 그 주제가 말하는 내용으로 짓는다. 아래 재료 이름이나 「배경」·「요약」처럼 어느 PR에나 붙는 이름은 제목으로 쓰지 않는다.

한 절 안에서 그 주제에 있는 재료만 쓴다. 모든 재료가 다 있어야 하는 것은 아니다.

- **왜 필요했나** — 이 주제를 다루게 된 문제·요구사항·배경. 메인이 이슈·계획 문서·대화에서 추출
  - 해 보고 싶었던 것이 코드로 보여 줄 수 있는 동작이면 열 줄 안팎의 예시 코드를 둔다
  - 이 예시 코드가 PR diff에 없으면 「이렇게 써 보고 싶었다」처럼 의도로 소개한다. 「이렇게 했다」로 쓰면 리뷰어는 그 코드가 PR에 들어간 것으로 읽는다
- **무엇을 골랐고 왜** — 검토한 후보, 고른 기준, 판정. 메인이 결정 기록·대화에서 추출
- **어떻게 동작하나** — 바뀐 뒤 실제 동작. 메인이 git diff·코드에서 추출
  - 이해를 돕는 코드 조각은 붙여도 되고, 코드를 보면 아는 동작은 말로 풀지 않는다

일반 PR이면 짧게 쓰고 디테일은 뺀다. 리뷰어는 바뀐 값 하나하나까지 읽지 않는다.

커밋 목록이나 바꾼 파일·컴포넌트 나열은 넣지 않는다(GitHub PR 화면이 이미 보여준다).

일반 PR이면 이 PR 밖을 가리키는 것과 작업한 흔적은 넣지 않는다. 다른 PR 번호, 커밋 해시, 브랜치명, 백로그 번호, 작업 세션 링크, 생성 도구 표기, 작업 대화에서 나온 말("사용자 결정" 같은 것)이 여기 든다. 리뷰어와 나중에 레포를 둘러보는 사람은 그 맥락을 볼 수 없다.

## subtype별 length_target default

| subtype | default |
|---------|---------|
| (없음, 일반 PR) | 짧게: 1-2 섹션, 합쳐서 3-5문단 (약 200-400단어) |
| recruitment | 섹션당 3-4문단 (약 200-300단어), 표·이미지·commit 링크 활용. 의사결정 섹션은 30-50% 더 길게 |

frontmatter `length_target`이 있으면 그쪽을 따른다.
