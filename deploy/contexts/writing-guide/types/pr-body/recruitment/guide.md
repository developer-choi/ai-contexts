# 채용 과제 PR 본문 가이드

채용 과제 PR 본문(`subtype: recruitment`)에서 자주 쓰는 꼴 두 가지입니다. PR 성격에 맞는 쪽을 참고하고, 섞어 써도 됩니다.

## 증거형 — 측정 가능한 결과를 보이는 PR

성능 개선, 렌더링 최적화처럼 결과를 수치·화면으로 보일 수 있는 PR입니다.

> 예시: [렌더링 전략 최종 선택: Streaming](https://github.com/developer-choi/monorepo-playground/pull/6)

- 개선 포인트마다 아래 순서로 쓰면 읽기 좋습니다.
  1. **Before/After 비교표**: 스크린샷, Network Waterfall, Timing 등 시각 자료를 표로 나란히 둡니다.
  2. **커밋 링크와 개선 내역**: 무엇을 바꿨고, 어떤 효과가 있는지 적습니다.
  3. **판단 과정**: 왜 이 방식을 골랐고, 무엇과 맞바꿨는지 적습니다.
- 독자가 비교표만 봐도 개선을 체감하고, 글에서 이유를 이해할 수 있어야 합니다.
- Before/After는 같은 조건에서 잰 것을 나란히 둡니다. 한쪽만 붙이고 "개선되었습니다"로 넘기지 않습니다.

## 서사형 — 사고 과정으로 설득하는 PR

> 예시: [Feature static checking](https://github.com/developer-choi/frontend-test-v2-for-tester/pull/2)

- 이 PR이 왜 있는지는 아래 순서로 풀면 읽기 좋습니다.
  1. **최종 목표**: 무엇을 이루려는지
  2. **로드맵**: 목표를 위한 단계들
  3. **이미 끝낸 것**: 앞서 한 고민·작업(링크)
  4. **이번 PR에서 한 것**: 로드맵 중 어디를 실행했는지
  5. **다른 목표와의 연결**: 이 작업이 다른 가치에도 기여하는 점
- 독자가 그 대목만 읽고 이 PR이 왜 있는지 알 수 있어야 합니다.
- 추상적 설명보다 코드 예시로 "이걸 막았다"를 보입니다.
- 도구·구조를 왜 들였는지는 기술적 동작 방식이 아니라 도입 동기(팀에 어떤 가치를 주는가)로 씁니다. 기술 선택이면 대안과 견줘 왜 이것을 골랐는지까지 씁니다.
