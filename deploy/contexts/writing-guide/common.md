## 독자는 채용담당자

모든 글의 독자는 글쓴이가 개발 역량을 어필해야 하는 채용담당자입니다. 구현 디테일에 너무 깊이 들어가지도, 개발을 모르는 사람에게 하듯 얕게 풀지도 않습니다. 그 독자가 이 글의 소재를 얼마나 아는지는 패키지 `audience_knowledge`가 정합니다.

## 기본 톤

- **습니다체** 사용. 유형별 예외는 그 유형의 가이드가 정합니다.

## 글쓴이 측은 「저희」

글쓴이(필자·팀·회사)를 가리킬 때 「저희」가 자연스러운 맥락이면 「우리」 대신 「저희」를 씁니다. 독자인 채용담당자는 외부인이라 겸양 호칭이 톤에 맞습니다.

## 독자가 볼 수 없는 작업 흔적은 싣지 않는다

백로그 번호, 작업 세션 링크, 작업 메모·AI 지시문 같은 내부 작업 문서 링크, 작업 대화에서만 통하는 말("사용자 결정" 같은 것)은 본문에 넣지 않습니다. 독자는 그 대화와 작업 기록을 볼 수 없습니다.

## 글쓴이 쪽 고유 이름은 풀어 쓴다

정의 없이 던지는 내부 약어(KA, AC 등)는 풀어서 쓰거나 링크합니다. 그림 노드나 본문에 쓴 시스템 고유 이름(세션·단계·역할 이름)에는 옆에 일상어 설명을 붙입니다(예: `BG · 배경 파악과 PR 분할`).

## 화면 문구는 큰따옴표, UI 요소 이름은 대괄호

화면에 뜨는 문구는 큰따옴표로 감쌉니다. 버튼·탭·메뉴처럼 누르거나 고르는 UI 요소 이름은 대괄호로 감쌉니다.

본문 글자로 쓰는 대괄호는 UI 요소 이름에만 씁니다. 마크다운 링크·체크박스 문법의 대괄호는 여기 들지 않습니다.

## 외국어 원문은 글 끝에 출처별로 모은다

- 본문에는 한국어 주장만 씁니다. 외국어 원문을 문단 사이에 끼우면 독자가 주장을 따라가던 흐름이 끊깁니다.
- 원문은 글 맨 끝에 출처별로 모읍니다. 헤딩은 `## References: [문서 제목](URL)`입니다.
- 각 References 절 안은 `> 원문` 인용블록 다음에 `- 한국어 해설` 불릿을 둡니다.
- 출처가 여럿이면 References 절을 출처마다 나란히 둡니다. 하나로 합치면 독자가 어느 문서의 말인지 잃습니다.

## 의문형은 물음표로 닫는다

의문형으로 쓴 문장과 헤딩 끝에 물음표를 붙입니다.

## 헤딩은 핵심 문장의 한 단계를 맡는다

헤딩마다 글의 핵심 문장(`key_message`)의 어느 단계를 맡습니다. 어느 단계도 못 맡거나, 앞 헤딩과 같은 단계를 맡거나, 앞 헤딩과 한 짝인 대비면 헤딩으로 세우지 않습니다. 템플릿·가이드 골격의 칸 헤딩(사례마다 되풀이되는 칸, 나란히 견주는 방법·단계)과 글 끝 References 절은 이 판정에서 뺍니다.

## 분량

frontmatter `length_target`이 있으면 그것을 따르고, 없으면 사용자가 준 텍스트의 2~3배를 넘기지 않습니다.

## 한 문단 = 한 논점

한 문단에 논점을 하나만 담습니다. 장점→단점 전환, 비교 대상 전환 시 문단을 나눕니다. 논점 전환 시 접속사로 문장 간 관계를 명시합니다.

## 연쇄 연결 금지

짧은 절에서 원인-결과 연쇄를 남발하지 않습니다. 1~2줄로 쓰는 bullet에서 특히 주의합니다. 원인 체인이 길수록 읽기 부담이 커지므로, 핵심만 남긴 한 줄이 더 강하게 전달됩니다.

## 비교/나열은 리스트로

선택지를 비교하거나, 항목마다 설명이 붙는 나열은 쉼표로 이어 붙이지 않고 리스트로 분리합니다. 짧은 이름만 늘어놓는 나열은 문장 안에 둡니다. 독자가 각 항목을 개별적으로 비교할 수 있어야 합니다.

## 읽는 순서 = 이해 순서

결론·주제어를 먼저, 디테일·근거·자랑은 뒤에 둡니다. 어필성 문서도 "무엇을 했는가" → "어떤 효과인가" → "구현 규모(자랑)" 순입니다.

### 정의 → 사용 순서

기반 개념을 먼저, 그 개념을 쓰는 로직을 뒤에 둡니다.

## 한 번 고른 이름은 끝까지 그것만 씁니다

같은 대상을 여러 이름으로 부르면 독자가 볼 때마다 "아까 그건가"를 확인해야 하고, 문서가 여럿이면 그 확인이 문서마다 반복됩니다. 같은 뜻의 다른 이름을 알려줘야 하면 정의하는 자리에서 한 번만 묶어 보이고, 그 뒤로는 고른 이름만 씁니다.

## 사례

### 헤딩-본문 시제 어긋남

> 관련: "시제는 문서 유형에 일관되게 적용"

**Bad (AI)**

```
1. 성능을 최적화합니다.
    - Streaming SSR로 전환하여 TTFB를 39% 단축했습니다.

2. 에러를 체계적으로 관리합니다.
    - 원인 기반 커스텀 에러 클래스를 도입하여 Sentry 이슈 98%를 해결했습니다.
```

- 헤딩은 현재형(`~합니다`), bullet 본문은 과거형(`~했습니다`) — 한 문서에서 시제 충돌
- 이력서는 과거 성과를 서술하는 문서이므로 본문은 과거형이 자연스러움

**Result (사용자 확정)**

```
1. 성능 최적화
    - Streaming SSR로 전환하여 TTFB를 39% 단축했습니다.

2. 에러의 체계적 관리
    - 원인 기반 커스텀 에러 클래스를 도입하여 Sentry 이슈 98%를 해결했습니다.
```

### 오해를 부정문으로 바로잡음

> 관련: "오해는 부정으로 짚지 않고 긍정 서술로 비운다"

**Bad**

```
다만 자료를 넣으면 자동으로 PR이 나오는 기계는 아닙니다. AI가 제 작업 순서를 그대로 밟고, 단계마다 제가 끼어들어 방향을 정합니다.
```

- "기계는 아니다"라는 부정이 자동 산출 오해를 먼저 심음

**Good**

```
AI가 제 작업 순서를 그대로 밟고, 단계마다 제가 끼어들어 방향을 정하면서 마지막에 PR에 다다릅니다.
```

### 링크를 열어야만 맥락이 잡힘

> 관련: "링크 참조 시 내용 요약 먼저"

**Bad**

```
[에러 처리는 왜 필요한가?](링크)에서 정리했듯이, 예방이 더 중요합니다.
```

- 링크를 읽어야만 맥락을 알 수 있음. 불친절함

**Good**

```
에러 처리는 예전에 고민을 마쳤었는데, 확인해주시면 감사하겠습니다: [에러 처리는 왜 필요한가?](링크)
```

### 목적 먼저, 구현 나중에

> 관련: "읽는 순서 = 이해 순서"

**Bad (AI)**

```
구조: mode 옵션 설명 → 코드 → 데모 → "왜 onSubmit인가"
소개: "react-hook-form의 useForm()은 mode 옵션으로 에러 노출 시점을 결정합니다."
라벨: onChange, onBlur, onSubmit
```

- 라이브러리 기능 설명부터 시작 → "뭘 왜 하는 건지" 파악 전에 "어떻게"가 먼저 나옴
- 기술 용어(onChange 등)로 라벨링 → 목적이 아닌 구현 관점

**Result (사용자 확정)**

```
구조: UX 관점(에러 시점 3가지) → 라이브러리 해결법 → 데모 → 코드 → 한계
소개: "에러를 보여주는 시점은 크게 세 가지입니다."
라벨: 입력 시점, 포커스가 빠진 시점, 제출 시점
```

### 결론 → 디테일 → 자랑 순서 위반

> 관련: "읽는 순서 = 이해 순서"

**Bad (AI)**

```
2. 에러의 체계적 관리
    - beforeSend() 훅 하나와 커스텀 에러 클래스 필드만 추가하는 n줄 규모의 최소 구조로 Sentry를 연동했습니다. 동료는 Sentry 스펙을 몰라도 기존 throw 흐름만 유지하면 모든 에러의 단서가 자동 수집됩니다.
    - 원인 기반 커스텀 에러 클래스 n개와 4단계 우선순위 정책을 도입하여, Sentry 이슈 98%를 해결했습니다.
    - 페이지 n개·버튼 n개에서 발생하는 에러를 n줄의 공통 로직으로 처리했습니다.
```

- 첫 bullet이 "n줄 규모의 최소 구조" 자랑으로 시작 — 독자는 "뭘 한 건지(Sentry 연동)"를 끝에서야 만남
- 첫 bullet 한 문장에 "어떻게(beforeSend 추가) + 규모(n줄) + 무엇(Sentry 연동) + 효과(자동 수집)"가 한꺼번에 들어가 무거움

**Result (사용자 확정)**

```
2. 에러의 체계적 관리
    - Sentry를 도입해, 동료가 Sentry 스펙을 몰라도 기존 throw 흐름만 유지하면 모든 에러의 단서가 자동 수집되도록 했습니다.
    - 원인 기반 커스텀 에러 클래스 n개와 4단계 우선순위 정책을 도입하여, Sentry 이슈 98%를 해결했습니다.
    - 페이지 n개·버튼 n개에서 발생하는 에러를 n줄의 공통 로직으로 처리했습니다.
    - beforeSend() 훅 하나와 커스텀 에러 클래스 필드, 총 n줄만으로 위 모든 효과가 동작했습니다.
```
