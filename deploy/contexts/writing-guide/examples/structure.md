# 구조 교정 사례

## 목적 먼저, 구현 나중에

**Bad (AI)**

```
구조: mode 옵션 설명 → 코드 → 데모 → "왜 onSubmit인가"
소개: "react-hook-form의 useForm()은 mode 옵션으로 에러 노출 시점을 결정합니다."
라벨: onChange, onBlur, onSubmit
```

- 라이브러리 기능 설명부터 시작 → "뭘 왜 하는 건지" 파악 전에 "어떻게"가 먼저 나옴
- 기술 용어(onChange 등)로 라벨링 → 목적이 아닌 구현 관점

**Result (사용자 확정)**

```
구조: UX 관점(에러 시점 3가지) → 라이브러리 해결법 → 데모 → 코드 → 한계
소개: "에러를 보여주는 시점은 크게 세 가지입니다."
라벨: 입력 시점, 포커스가 빠진 시점, 제출 시점
```

- 목적(언제 에러를 보여줄 것인가)을 먼저 설명하고, 구현(mode 옵션)은 다음에
- UX 관점의 라벨 → 기술 용어 없이도 의미 전달

## 목적 먼저, 수단 나중 (섹션 순서)

**Bad (AI)**

```
섹션 순서: 에러 클래스(수단) → 에러 문구(UX) → 에러 잡는 구조(목적)
```

**Result (사용자 확정)**

```
섹션 순서: 에러 잡는 구조(목적) → 에러 문구(UX) → 에러 클래스(수단)
```

- 독자는 "왜"를 먼저 알아야 "어떻게"에 납득합니다.
- 수단·구현 세부사항이 먼저 나오면 목적을 파악하기 전에 피로해집니다.
- 섹션 내 문장 순서뿐 아니라 섹션 배치 순서도 이 원칙을 따릅니다.

## 비교 나열을 쉼표로 연결 — 리스트로 분리

> 관련: tone.md "비교/나열은 리스트로"

**배경**: README. API 1초 고정 제약에 대한 로딩 전략 선택지 비교.

**Bad (AI)**

```
실시간 검색 미리보기는 타이핑할 때마다 1초를 기다려야 하므로 입력이 반영된 건지 알 수 없고, 이전 데이터를 유지하는 방식은 1초간 화면이 전혀 변하지 않아 검색이 실행된 건지 피드백이 없습니다. 검색 실행 즉시 스켈레톤을 보여주어 "로딩 중"이라는 피드백을 바로 제공하는 방식을 선택했습니다.
```

- 선택지 2개 + 결론이 한 문장에 쉼표로 연결
- 어디서 끊어 읽어야 하는지 불분명

**Result (사용자 확정)**

```
1. 실시간 검색 미리보기는 타이핑할 때마다 1초를 기다려야 하므로 입력이 반영된 건지 알 수 없고,
2. 이전 데이터를 유지하는 방식은 1초간 화면이 전혀 변하지 않아 검색이 실행된 건지 피드백이 없습니다.
3. 따라서, 검색 실행 즉시 스켈레톤을 보여주어 "로딩 중"이라는 피드백을 바로 제공하는 방식을 선택했습니다.
```

- 각 선택지를 리스트로 분리하여 개별 비교 가능
- 마지막 항목에 "따라서,"로 결론 연결

## 전제+목적+비교가 한 문장에 — 볼드 분리 + 문단 나누기

> 관련: tone.md "한 문단 = 한 논점"

**배경**: PR 본문. DDD 폴더 구조 선택 이유.

**Bad (AI)**

```
라포랩스 담당자님이 위에서부터 폴더를 탐색할 때, "이 로직은 어떤 도메인인가?" 한 가지 질문만으로 파일을 찾을 수 있게 하려고 했습니다. FSD 같은 구조는 Layer/Slice/Segment 규칙을 먼저 알아야 탐색이 가능한데, 이 규모에서는 러닝커브 대비 이점이 적다고 판단했습니다.
```

- 핵심 전제(누가, 언제) + 목적 + 대안 비교가 한 문단에 뭉침
- "한 가지 질문만으로"는 중간 설명으로, 핵심(러닝커브 없이)을 희석

**Result (사용자 확정)**

```
**라포랩스 담당자님이 위에서부터 폴더를 탐색할 때**, 러닝커브 없이 파일을 찾을 수 있게 하려고 했습니다.

FSD 같은 구조는 Layer/Slice/Segment 규칙을 먼저 알아야 탐색이 가능한데, 이 규모에서는 러닝커브 대비 이점이 적다고 판단했습니다.
```

- 핵심 전제를 볼드로 강조하여 독자의 시선을 잡음
- 대안 비교는 별도 문단으로 분리
- 불필요한 중간 설명 삭제, 직접적 표현으로 압축

## 서술 사례와 코드 예제의 주체 불일치

> 관련: tone.md "그림·예제와 옆 설명은 같은 것을 가리킵니다"

**배경**: 기술 필기. 일반 주장을 펼치는 서술 뒤에 코드 예제가 따라오는 흐름.

**Bad (AI)**

```
초기 배치를 잘못 하면 나중에 해체 비용이 큽니다. 실제로 langdy-admin의 outro 타입이 그랬습니다. 메인 챕터 파일에 타입이 정의되어 있고 문법·발음 도메인이 그걸 직접 import하는 구조였습니다.

```ts
// article-types.ts
export interface ArticleContent { ... }

// notice-logic.ts (남의 도메인)
import type { ArticleContent } from '../article/article-types';
```
```

- 서술은 langdy-admin outro 사례인데 뒤따르는 코드는 Article·Notice·FAQ — 주체가 다름
- 독자가 "사례 얘기 따로, 예제 얘기 따로"로 맥락을 잃음

**Result (사용자 확정)**

```
초기 배치를 잘못 하면 나중에 해체 비용이 큽니다. 예를 들어 형제 도메인 중 하나에 타입이 정의되어 있고 나머지가 그걸 직접 import하는 구조를 생각해 봅니다. Article·Notice·FAQ 세 도메인으로 단순화하면 다음과 같습니다.

```ts
// article-types.ts
export interface ArticleContent { ... }

// notice-logic.ts (남의 도메인)
import type { ArticleContent } from '../article/article-types';
```
```

- 서술을 일반화하여 코드 예제와 주체 일치
- "세 도메인으로 단순화하면 다음과 같습니다" 연결 문구로 서술→예제 흐름 명시

## 결론 → 디테일 → 자랑 순서 위반

> 관련: tone.md "읽는 순서 = 이해 순서"

**배경**: 이력서 한줄소개 2번 항목. 첫 bullet에 "어떻게 구현했고 코드는 n줄"이라는 자랑부터 등장. 독자는 "뭘 한 건지(Sentry 연동)" 결론을 끝에서야 받음.

**Bad (AI)**

```
2. 에러의 체계적 관리
    - beforeSend() 훅 하나와 커스텀 에러 클래스 필드만 추가하는 n줄 규모의 최소 구조로 Sentry를 연동했습니다. 동료는 Sentry 스펙을 몰라도 기존 throw 흐름만 유지하면 모든 에러의 단서가 자동 수집됩니다.
    - 원인 기반 커스텀 에러 클래스 n개와 4단계 우선순위 정책을 도입하여, Sentry 이슈 98%를 해결했습니다.
    - 페이지 n개·버튼 n개에서 발생하는 에러를 n줄의 공통 로직으로 처리했습니다.
```

- 첫 bullet이 "n줄 규모의 최소 구조" 자랑으로 시작 — 독자는 "뭘 한 건지(Sentry 연동)"를 끝에서야 만남
- 첫 bullet 한 문장에 "어떻게(beforeSend 추가) + 규모(n줄) + 무엇(Sentry 연동) + 효과(자동 수집)"가 한꺼번에 들어가 무거움

**Result (사용자 확정)**

```
2. 에러의 체계적 관리
    - Sentry를 도입해, 동료가 Sentry 스펙을 몰라도 기존 throw 흐름만 유지하면 모든 에러의 단서가 자동 수집되도록 했습니다.
    - 원인 기반 커스텀 에러 클래스 n개와 4단계 우선순위 정책을 도입하여, Sentry 이슈 98%를 해결했습니다.
    - 페이지 n개·버튼 n개에서 발생하는 에러를 n줄의 공통 로직으로 처리했습니다.
    - beforeSend() 훅 하나와 커스텀 에러 클래스 필드, 총 n줄만으로 위 모든 효과가 동작했습니다.
```

- 첫 bullet = "무엇을 했는가/어떤 효과인가"(Sentry 도입 + 자동 수집)
- 마지막 bullet = "구현 규모/자랑"(n줄)
- 위에서 아래로 읽으면 결론 → 디테일 → 자랑 순서가 자연스러움

## 문서 첫머리 메타 독자 안내 섹션

> 관련: tone.md "메타 독자 안내 섹션 금지"

**배경**: 히스토리 문서 H1 바로 아래에 `## 이 문서를 읽는 독자에게` 메타 헤더를 달고 "~을 정리한다" 류 메타 종결 문장으로 문단을 마감.

**Bad (AI)**

```
# 메인챕터 프레이밍 아웃트로 편집 UI 제거 히스토리

## 이 문서를 읽는 독자에게

어드민 코드에서 `FramingOutroEditItem`, `AddOutroItemModal` 같은 컴포넌트가 한동안 존재했다가 최근에 사라졌습니다. 이 UI는 2025-12에 새로 만들어 약 4개월 운영했다가 2026-04-20에 제거된 기능입니다.
짧게 살다 간 컴포넌트라 코드 트리만 보면 "왜 있다가 왜 없어졌지?" 싶을 수 있어, 도입·유지·제거 단계별로 맥락을 정리합니다.
```

- `## 이 문서를 읽는 독자에게` 헤더 — frontmatter `purpose`·`audience`와 중복되는 메타 서술
- "~을 정리합니다" 메타 종결 — 독자에게 문서 자체를 설명하는 투라 오글거리게 읽힘

**Result (사용자 확정)**

```
# 메인챕터 프레이밍 아웃트로 편집 UI 제거 히스토리

어드민 코드에서 `FramingOutroEditItem`, `AddOutroItemModal` 같은 컴포넌트가 한동안 존재했다가 최근에 사라졌습니다. 이 UI는 2025-12에 새로 만들어 약 4개월 운영했다가 2026-04-20에 제거된 기능입니다.
```

- 메타 헤더 제거, 인트로 문단만 H1 아래에 바로 배치
- 메타 종결 문장 삭제 — 독자는 문서 제목으로 이미 맥락을 파악

## 리드 문단에 수치·용어 뭉침

> 관련: tone.md "괄호 안에 긴 용어 나열 금지", "읽는 순서 = 이해 순서"

**배경**: 이력서·README 리드 문단. 용어 정의(괄호 병기)와 수치가 한 문장에 뒤엉키면 독자가 숨 돌릴 곳 없이 정보 폭격을 받음.

**Bad (AI)**

```
페이지가 처음 반응하기까지 걸리는 시간(TTFB, Time to First Byte)이 545ms에서 333ms로 39% 줄었고, 자바스크립트 묶음(Bundle) 크기도 10.7kB에서 5.5kB로 48% 감소했다
```

- 한 문장에 용어 정의 2개(`TTFB`, `Bundle`) + 수치 2세트(`545→333`, `10.7→5.5`)가 몰림
- 괄호 병기가 주절 리듬을 끊음

**Result (사용자 확정)**

쉬운 말 주절 + 괄호 병기로 용어를 먼저 풀고, 수치 두 세트를 bullet 2개로 분해.

```
페이지가 처음 반응하기까지 걸리는 시간이 545ms에서 333ms로 39% 줄었습니다. 이 시간은 TTFB(Time to First Byte)라고 부릅니다.
브라우저가 내려받는 자바스크립트 파일 크기가 10.7kB에서 5.5kB로 48% 줄었습니다.
```

- 리드 한 문장에 너무 많이 담으려 하면 "AI가 쓴 것처럼" 무거워짐

## 결론 섹션이 앞 섹션의 논점을 반복

> 관련: tone.md "독자가 이미 알거나 추론할 수 있는 내용은 쓰지 않는다", "한 문단 = 한 논점"

**배경**: ADR 3회차 문서의 결론 섹션이 5문단에 걸쳐 앞 섹션들(`## 요지 미리 보기`, `## 2차 소비자 관점`, `## 검증`)의 내용을 부분적으로 반복하고, 마지막엔 리드 문장과 동어인 마무리까지 붙어 있음.

**Bad (AI)**

```
## 결론

**복합 케이스에서도 2회차와 동일하게 방법 1이 더 적합하다고 판단합니다.**

두 방식 모두 복합 케이스에서 원하는 포커스 동작을 실제로 낼 수 있습니다. … 이 회차의 질문은 "가능한가"가 아니라 "어느 쪽이 덜 번거로운가"였고, 답은 label 쪽으로 기웁니다.   ← (※ 요지 미리 보기 섹션과 중복)

핵심 비대칭은 … 이 비대칭은 2차 소비자로 슬롯이 뚫리는 경우에도 유지됩니다 — …   ← (※ 2차 소비자 섹션과 중복)

div + handleClick 쪽도 같은 결과를 낼 수 있지만 … label 쪽에서 감수하는 비용은 복합 필드에만 국한되는 반면, div 쪽에서 감수하는 비용은 단순 필드에도 기본값으로 따라옵니다.

이로써 2회차 결론이 복합 케이스까지 일관되게 유지됩니다.   ← (※ 리드 문장과 동어 반복)
```

- 결론이 리드 + "앞 섹션의 요약" + "또 다른 앞 섹션의 요약" + 새 논점 + "리드 재언급"으로 팽창
- 이미 아는 논점을 여러 번 재확인하면서 결론의 힘이 희석됨

**Result (사용자 확정)**

```
## 결론

**복합 케이스에서도 2회차와 동일하게 방법 1이 더 적합하다고 판단합니다.**

핵심 비대칭은 **선언적 쌍 vs 명령적 JS**입니다. label 방식은 `htmlFor`와 `id` 속성 한 쌍만으로 타겟 지정이 끝나는 반면, div 방식은 `useRef` 생성, `inputRef` prop 배선, `.focus()` 호출을 JS로 작성해야 합니다.

게다가 label에서 감수하는 비용은 복합 필드에만 국한되지만, div 비용은 TextField 같은 단순 필드에도 기본값으로 따라옵니다. 복합 케이스를 근거로 div 방식으로 돌아갈 이유가 보이지 않는다고 봅니다.

후속 필드(…)도 이 전제 위에서 구현합니다.
```

- 5문단 → 4문단
- 유지: 리드 + 핵심 비대칭 + 새 논점(비용 확장성) + 후속 전제
- 삭제: "가능한가 vs 번거로운가" 재언급, "2차 소비자에서도 유지" 재언급, "결론이 유지됩니다" 동어 반복
- 결론 섹션 검토 시 앞 섹션의 논점을 나열해 대조하면 중복이 드러남

## 같은 글 코드 블록 표기 일관성

> 관련: tone.md "기술 용어와 사실 관계는 정확하게 사용"

**배경**: 비개발자(채용담당자) 대상 블로그 포스트. 같은 글에 scss 코드 블록 두 개가 등장. "함정 코드"와 "원칙 코드"인데, 함정 쪽은 raw 값(`#eee`, `4px`), 원칙 쪽은 디자인 토큰(`variables.$gray100`, `variables.spacing(0.5)`)으로 표기가 혼재.

**Bad (AI)**

```scss
/* 함정 코드 (CardSkeleton.module.scss) */
.skeletonCard {
  background: #eee;
  border-radius: 4px;
}

/* 원칙 코드 (.bone) */
.bone {
  background: variables.$gray100;
  border-radius: variables.spacing(0.5);
  animation: pulse 1.5s ease-in-out infinite;
}
```

- 두 코드 블록이 같은 회색 박스를 정의하는데 표기가 다름 — `#eee` vs `variables.$gray100`, `4px` vs `variables.spacing(0.5)`
- 비개발자 독자가 "왜 한쪽은 #eee고 다른 한쪽은 variables.$gray100이지?" 의문을 가짐
- 변수/토큰 풀이를 본문에 추가해야 하거나, 의미 차이가 있는 줄로 오해할 위험

**Result (사용자 확정)**

raw 값으로 통일.

```scss
/* 함정 코드 */
.skeletonCard {
  background: #eee;
  border-radius: 4px;
}

/* 원칙 코드 */
.bone {
  background: #eee;
  border-radius: 4px;
  animation: pulse 1.5s ease-in-out infinite;
}
```

- 같은 글 안에서 같은 의미의 값은 같은 표기로 (raw 또는 변수 중 하나로 통일)
- 비개발자 독자에게는 raw 값이 더 직관 (`#eee`=회색, `4px`=픽셀)이라 raw로 통일하는 쪽이 일반적

## 문서 성격에 맞는 제목

**배경**: 폼 에러 피드백 예제 페이지. 기술 레퍼런스가 아니라 UX 관점에서 "왜 이렇게 해야 하는가"를 설명하는 에세이 형태의 문서.

**Bad (AI)**

```
1. Validation Mode
```

- 기술 레퍼런스/API 문서라면 기능명 제목이 맞음
- 하지만 이 문서는 독자에게 UX 판단 근거를 설명하는 에세이 — 기능명을 나열하면 매뉴얼이 됨

**Result (사용자 확정)**

```
1. 유효성검증은 언제 해야 하는가?
```

- 독자의 질문을 제목으로 → 읽는 목적과 일치
- 문서 성격(에세이/설명문)에 맞는 질문형 제목
