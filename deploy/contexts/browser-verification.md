# 브라우저를 조작할 때

## 콘솔·대시보드 폼을 채울 때

웹 콘솔·대시보드 설정 작업을 사용자에게 넘기기 전에 브라우저로 확정 직전까지 채울 수 있는지 본다. 되면 채운 값을 보여 주고 확정 버튼만 넘긴다. 그 밖에 사용자에게 넘기는 것은 로그인·결제·CAPTCHA뿐이다.

- **확정 버튼이 여러 개면 대상마다 탭을 나눠 저장 직전 상태로 둔다.**
- **사용자가 누른 뒤 페이지를 새로고침해 저장된 값을 읽는다.**

## 띄우는 명령을 실제로 돌리는 것부터가 검증이다

파일을 만들어놓고 제어 가능한 탭에서만 열면, 사용자가 실제로 그것을 여는 경로(예약작업·기본 브라우저 연결)가 사는지는 안 드러난다. 띄우는 명령을 먼저 그대로 돌리고, 그다음 같은 파일을 조작 가능한 탭에서 연다.

## 막히는 자리

아래는 실제로 막혀 본 자리다. 모르고 들어가면 벽에서 되돌아 나오게 된다.

- **`file://`은 확장이 막는다.** 로컬 서버로 띄워야 열린다. `localhost`는 보안 컨텍스트라 클립보드 동작 확인에는 오히려 정확하다.
- **페이지 안에서 클립보드를 읽으면 권한 게이트에 걸려 렌더러가 멎는다.** 복사 버튼을 실제로 누르고 OS 클립보드를 읽으면 사용자가 붙여넣을 값 그 자체가 나온다.
- **요소 참조로 누른 클릭이 핸들러를 못 깨우는 일이 있다.** 좌표 클릭으로 바꾼다.
- **페이지가 스크립트에서 나오는지, 스킬 본문의 템플릿을 그때 렌더하는지 먼저 가른다.** 후자는 넘길 스펙이 없어 템플릿을 더미 값으로 채워야 한다.
- **JS 대화상자(alert·confirm·prompt)를 띄우면 이후 제어가 통째로 멎는다.** 그 버튼을 눌러야 하면 먼저 사용자에게 알린다.

## 멈출 지점을 어떻게 찾나

산출물을 확인하다 저장까지 돌릴 때, 저장이 진짜 데이터를 건드리는 지점은 대개 파일 하나 안에 있다. 저장 스크립트가 검증을 쓰기보다 앞에 두면 거부 갈래는 오염 없이 끝까지 돌아가므로, 어디서 쓰기가 시작되는지 보고 선을 긋는다 — 저장 단계 전체를 통째로 건너뛰면 안 돌려봐도 될 것까지 안 돌린 게 된다.
