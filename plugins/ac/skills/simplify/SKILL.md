# AI 행동 가이드

## 목적

라이브러리를 학습에 필요한 구현만 남겨 단순화한다.

> **용어 정의**
> - **SIMPLIFY_SOURCE**: 이 스킬의 원본 폴더 (`${CLAUDE_SKILL_DIR}`). 워크플로우, 패턴 참조, 문서 양식 등 규칙 파일이 있는 곳.
> - **SIMPLIFY_TARGET**: 간소화 대상 프로젝트 (`simplified-[라이브러리명]`). 실제 코드를 읽고 단순화하는 작업 프로젝트.

## [CRITICAL] 지킬 원칙

아래 원칙이 다른 모든 지침(형제 컴포넌트 컨벤션, 패턴 카탈로그 포함)에 우선한다.

### 간소화는 기능 단위까지 간다

Scope 제거·forwardRef 제거 같은 구조적/기계적 변환은 **최소선**이지 목표가 아니다. 코드가 짧거나 동작이 유지된다고 해서 간소화할 게 없는 것이 아니다.

### 제거/유지 판정 — 학습 범위 테스트

각 기능·서브시스템마다 묻는다: **"이 대상의 핵심 개념을 학습하는 데 이 구현이 필요한가?"**

- 핵심 흐름 이해에 없어도 되는 것 = **제거 대상**
- 핵심 동작·접근성·합성 구조에 필수인 것 = **유지**
- **delta-over-sibling**: 이미 간소화된 더 단순한 형제와 비교한다.
    - 빼면 그 형제와 **구별되지 않게 되는** 기능 = 이 대상이 형제보다 더 가르치는 **delta** = 학습 포인트 = **유지**. 더 단순한 형제에 **아예 없는** 고유 기능일수록 delta일 가능성이 높다(없다고 제거 후보가 아니다).
    - 더 단순한 형제도 **이미 제거했거나 기본값으로 고정한** 기능 = 제거 선례 있음 = **제거 후보**.
    - 애매하면 **제거 쪽으로 추천 판정**하고 근거를 커밋 계획에 남긴다. 학습에 불필요하면 제거가 기본값이다.
- "동작이 바뀐다"는 사실 자체는 유지 사유가 아니다. 단, 기능을 제거할 때 **유지하기로 한 다른 기능을 떠받치는 필수 코드**까지 함께 지우지 않는다(부분 해부 — `common-patterns.md`).

### 형제는 컨벤션 참고일 뿐, 제거 범위의 기준이 아니다

이미 간소화된 형제는 **코드 스타일·구조적 변환 패턴을 미러링**할 때만 참고한다. **형제가 기능을 남겼다는 사실은 이 대상에서 기능을 유지할 근거가 못 된다**(sibling-mimicry 금지).

### 제거 범위는 AI가 판단해 추천대로 진행한다

간소화 단계에서는 어떤 기능을 제거/유지할지 **AI가 학습 범위 테스트로 판단해 추천대로 곧장 진행**한다.
**도중에 사용자에게 묻거나 승인을 기다리지 않는다** — 판정 근거는 커밋 계획과 `*-simplified.md`에 명시한다. 공개 API가 바뀌어도 근거를 적고 진행한다.
(이 항목은 "여러 항목 하나씩 제시"·"대규모 변경 시 승인" 류의 일반 선호를 간소화 단계에 한해 덮어쓴다.)

- **예외**: 새 프로젝트 **초기 세팅(`initialize.md`)** 단계에서는 `initialize.md`가 정한 지점에서 사용자 확인을 받는다.

## 작업 공통 규칙 (모든 단계 적용)

### 코드 읽기 전용

이 프로젝트의 목적은 소스 코드를 읽고 이해하는 것이다. 의존성 설치·실행·빌드를 하지 않는다.

### 산출물 문서는 별도 커밋

분석 문서(`*-original.md`, `*-simplified.md`, `analysis-queue.md` 등)는 코드 변경과 같은 커밋에 섞지 않고 별도 커밋한다.

## 새 프로젝트 시작 (`init`)

1. **초기 세팅**: `initialize.md` 읽기

## 기존 프로젝트 현행화 (`renew`)

옛 스킬로 init된 `simplified-*` 프로젝트의 인프라만 현행 표준으로 갱신할 때(소스 재간소화 없이): `renew.md` 읽기

## 단순화 작업 진행

1. **작업 프로세스**: `main.md` 읽기
2. **문서 양식**: 산출물 문서를 쓸 때 SIMPLIFY_SOURCE `format/`의 해당 양식을 읽는다 — 이 스킬이 만드는 모든 산출물의 양식이 여기 있다.
   - 양식은 컴포넌트 라이브러리를 기준으로 쓰였다. 비컴포넌트(상태관리·hooks·유틸 등)도 같은 양식을 쓰되, 컴포넌트 전용 필드(렌더링 구조·Props)는 대상에 맞게 적응한다(모듈/클래스 공개 API·호출 구조 등).
