# 프롬프트 문서 리뷰

## 목적

스킬·규칙·프롬프트 문서를 기준 문서로 리뷰하고 지적을 반영해 고친다.

## 입력

- 리뷰할 파일·폴더 경로
- `--simplify`: 붙이면 구조 단순화 대안까지 받는다

## 출력

```markdown
### 반영한 것

- {작성된 위치}: {무엇을 고쳤나}

### 미룬 것

- {작성된 위치}: {무엇을} → {어느 파일 차례로}

### 넣지 않은 것

- {작성된 위치}: {무엇을} → {넣지 않은 근거}

### 판단이 어려워 가져온 것

**{번호}. {작성된 위치}**
- Before: {지금 문장}
- After: {바꿀 문장}
- 문제: {지금 무엇이 문제인가}
- 장점: {고치면 좋아지는 것}
- 단점: {고치면 드는 비용·잃는 것}
- 추천: {넣는다/안 넣는다와 그 근거}

### 확인 라운드

- 확인 라운드에서 낸 지적 {N}건 → 반영 {M}건 (돌지 못했으면 "못 돎: {사유}")

### 크기 변화

- 파일 트리: {고치기 전} → {고친 뒤}
- {파일}: {전}B → {후}B ({늘거나 준 이유})

### 리뷰어·에이전트의 모델

- {리뷰어·서브에이전트}: {모델} ({선택한 근거. Gemini면 ask-llm이 stderr에 낸 모델 이름})
```

## 기준

| 리뷰어 | 맡는 기준 | 문서 |
|---|---|---|
| BODY | 필요한 것만 짧게 적었나 | [trimming.md](../../contexts/prompt-standards/trimming.md) |
| BODY | 코드로 옮길 수 있나 | [rules-as-code.md](../../contexts/rules-as-code.md) |
| STRUCTURE | 정본과 참조 | [sources-and-links.md](../../contexts/prompt-standards/sources-and-links.md) |
| STRUCTURE | 파일·폴더 나누기, 크기 | [file-layout.md](../../contexts/prompt-standards/file-layout.md) |
| AGENT | 에이전트 나누기 (대상이 에이전트를 띄울 때) | [skill-structure.md](../../contexts/prompt-standards/skill-structure.md) |
| WORKFLOW | workflow 특화 (대상이 workflow 스킬일 때) | [targets/workflow.md](targets/workflow.md) |
| CODE | 스킬·규칙이 사용하는 코드·데이터의 이름 (대상 md가 호출하는 스크립트·json 중 작업 브랜치에서 바뀐 것이 있을 때) | [naming.md](../../contexts/coding-standards/rules/personal/naming.md) |

대상이 ai-contexts 체크아웃(워크트리 포함) 안에 있으면 이 문서의 경로를 아래처럼 그 체크아웃 안으로 바꿔 읽는다. 그 브랜치에서 고친 기준으로 리뷰하기 위해서다.

- 상대 경로: 그 체크아웃의 `plugins/ac/skills/prompt-review/` 기준
- `~/.ai-contexts/<스크립트>`: 그 체크아웃의 `scripts/hooks/<스크립트>`
- `${CLAUDE_SKILL_DIR}`: 그 체크아웃의 `plugins/ac/skills/prompt-review`

## 절차

### 1. 리뷰하고 대상 파일 고치기

1. 기계 검사를 돌린다. 처음 돌린 크기 출력과 대상의 파일 트리는 크기 변화의 "전" 값으로 남겨 둔다.
   - 크기: `node ~/.ai-contexts/check-md-size.mjs --report <대상 경로>`.
   - 낱말·긴 줄: `node ~/.ai-contexts/check-wording.mjs --report <대상 경로>`. 걸린 줄은 리뷰어 지적에 추가한다.
2. 리뷰어에게 맡긴다.
   - [기준](#기준) 표에서 조건에 맞는 리뷰어마다 Gemini Argon에 그 리뷰어가 붙은 행의 기준을 맡긴다.
     - 보낼 내용은 `node "${CLAUDE_SKILL_DIR}/scripts/build-review-request.mjs"`로 파일 하나로 묶는다. 인자는 [scripts/build-review-request.md](scripts/build-review-request.md)를 본다.
     - 묶은 파일은 읽지 않고 `node "${CLAUDE_SKILL_DIR}/../../contexts/ask-llm.mjs" --vendor gemini --model Argon --timeout 480 <그 파일>`로 보낸다(셸 도구 `timeout`은 [ask-llm.md](../../contexts/ask-llm.md#인자)대로). 메인이 재료를 읽으면 절약하려던 Claude 토큰이 그대로 든다.
     - 호출이 실패하면 다른 모델로 바꾸거나 대신 리뷰하지 않고 사유를 사용자에게 보이고 멈춘다. 어느 모델로 리뷰됐는지 사용자가 알아야 해서다. 사용자가 다른 모델(예: Neon)을 대면 그 모델로 다시 보낸다.
   - 규칙에 없는 문제를 보는 자유 리뷰어는 이름 있는 팀원으로 띄운다([team-agent](../../contexts/team-agent.md#claude-code)). 레포의 다른 파일을 직접 찾아 읽어야 다른 규칙과의 충돌이 보이는데, Gemini는 보낸 것만 본다.
   - 리뷰 대상(입력으로 받은 파일·폴더)이 바뀌면 팀원을 끝내고 새로 띄운다. 앞 대상을 본 맥락이 새 대상 판정에 섞이지 않게 하기 위해서다.
   - 이 절차에서 띄우는 팀원·서브에이전트의 모델은 [에이전트 나누기](../../contexts/prompt-standards/skill-structure.md#에이전트-설계)대로 선택한다.
   - BODY 답에 [how 최소화 원칙](../../contexts/prompt-standards/trimming.md#how-최소화-원칙) 판정 표가 없으면 다시 맡긴다.
   - 회차마다 리뷰어에게 보내는 말에 무엇을 바꿨는지, 어디를 의심하는지, 어디만 볼지는 넣지 않는다. 리뷰어가 그 대목에 쏠려 나머지를 덜 본다.
3. 지적을 모아 [지적 판단](#지적-판단)대로 처리한다.
4. 반영하며 사람이 처음 읽어도 바로 이해되게 다듬은 뒤, 기계 검사를 다시 돌리고, 같은 리뷰어들에게 다시 리뷰를 맡긴다. 새 지적이 0건이 될 때까지, 최대 10회 돈다.
   - 넣지 않았거나 사용자에게 가져갈 지적과 그 근거를 넘긴다. Gemini 리뷰어에게는 앞 회차 대화 대신 그것을 파일에 적어 스크립트에 `--findings`로 넘긴다. 대화를 통째로 다시 보내면 요청이 회차마다 배로 불어난다.
   - 새 지적이 0건이 되면 자유 리뷰어 팀원을 끝내고 새로 띄워 대상 전체를 한 번 더 리뷰받는다(확인 라운드). 같은 팀원은 앞 회차에 판정한 곳을 다시 읽지 않고 그 판정을 그대로 가져오는 일이 있어서다. Gemini 리뷰어는 호출마다 새 대화라 다시 호출하지 않는다.
     - 새 자유 리뷰어 팀원에게도 지금까지 넘긴 지적과 근거만 넘긴다.
     - 지적이 나오면 지적을 모아 처리하는 단계부터 이어 간다.
     - 확인 라운드는 대상 하나에 한 번만 돌고, 10회 상한에 함께 센다.
   - 10회째에도 남은 지적은 "판단이 어려워 가져온 것"에 넣는다.
   - 사용자가 선택한 것(구조 단순화 대안, "판단이 어려워 가져온 것")을 반영했을 때도 이 재리뷰를 돈 뒤 6단계로 간다.
5. `--simplify`가 있으면 구조 단순화 대안을 받는다.
   - 대상 전체를 서브에이전트 하나에게 맡겨, 목적에 비해 구조(분기·모드·플래그·파일 나누기)가 복잡한지, 같은 목적을 더 쉽게 달성할 대안이 있는지 보게 한다. 지적은 Before/After와 잃는 것으로 받는다.
   - 받은 지적은 반영하지 않고 그대로 사용자에게 보이고 반영할 것을 선택하게 한다. 지금 구조가 왜 그렇게 됐는지는 그 서브에이전트가 모른다.
6. [출력](#출력) 꼴로 결과를 내며, [후속 작업](#후속-작업) 목록을 그대로 보여 주고 필요한지, 사용자가 대상을 직접 리뷰할지 묻는다.

### 2. 리뷰가 놓친 지적의 원인 찾기

1. 같은 대화에서 리뷰한 대상에 사용자가 문제를 짚었고 그것을 반영하기로 했으면, 그 문제를 맡았어야 할 리뷰어에게 그 대목에 기준을 다시 적용하게 한다. Gemini 리뷰어면 이 요청을 파일에 적어 스크립트에 `--ask`로 넘긴다.
   - "왜 못 봤나"는 묻지 않는다. 받을 답은 적용될 기준 문장 원문, 그 문장대로의 판정, 지적하지 않는 쪽으로 판정을 민 문장 원문이다. 민 문장이 없으면 실제로 어떤 단위로 비교했는지 받는다
2. 답을 모아 원인과 고칠 안을 사용자에게 제시한다. 고칠 안은 [지적 판단](#지적-판단)대로 선택하되, 사실을 몰라서 놓쳤으면 그 사실을 스크립트·훅이 알려 주게 한다. 기준 문서에 문장을 추가하는 안은 넣기 전에 벤치(`/ac:bench`)로 효과를 확인한다.

## 지적 판단

지적은 기본으로 반영하고, 반영해도 되는지 판단이 어려운 것만 사용자에게 가져온다. 고칠 안은 문장을 추가하기 전에 있는 문장을 지우거나 줄여서 풀리는지를 먼저 본다([how 최소화 원칙](../../contexts/prompt-standards/trimming.md#how-최소화-원칙)). 아래 유형에 해당하면 그 기준을 더 본다.

| 유형 | 더 볼 기준 |
|---|---|
| 문서끼리 어긋남 | 그 문서의 목적을 기준으로 어느 쪽을 남길지 정해 맞춘다 |
| 엣지케이스 보완 | 그 문서가 쓰이는 상황에서 자주 날지, 드물어도 나면 치명적인지 본다 |
| 코드로 강제 | [rules-as-code](../../contexts/rules-as-code.md) 기준으로 손익을 비교해 합리적이면 넣는다 |
| 다른 파일과 함께 고칠 것 | 그 파일도 이어서 다룰 예정이면 그 차례로 미룬다 |

## 후속 작업
