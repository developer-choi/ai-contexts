# Workflow

제가 일하는 방식을 프롬프트로 옮긴 것입니다. 기획서나 피그마 디자인, 채용 과제 같은 자료에서 출발합니다.

AI가 제 작업 순서를 그대로 밟고, 단계마다 제가 끼어들어 방향을 정하면서 마지막에 PR에 다다릅니다.

PR 본문은 글쓰기 스킬(write-doc)로 따로 씁니다. 쓰는 시점은 자유입니다.

## 동기

기획서를 받았다고 바로 코드를 작성하면, 배경을 잘못 이해한 채로 작업이 굴러가거나 한 PR이 너무 커져서 리뷰가 어려워집니다.

그래서 저는 먼저 배경을 파악하고, 작업을 PR 단위로 나누고, 어떻게 만들지 방침을 세운 뒤에 코드를 작성합니다. 다 만들고 나면 코드 품질을 점검합니다.

이 순서를 프롬프트로 옮겨서 AI도 같은 방식으로 일하도록 만든 것이 이 워크플로우입니다.

또 하나의 목표는 작업을 가능한 한 겹쳐 돌려 기다리는 시간을 줄이는 것입니다. 어떤 PR의 구현과 그 PR에 의존하는 PR의 설계를 겹치고, 화면 마크업은 PR 작업과 동시에 진행하고, 리뷰어를 종류별로 나눠 동시에 돌립니다.

## 작업에 맞춘 조절

작업마다 어디까지 파고들지를 조절합니다. 정확성이 더 중요한 작업은 방법을 더 탐색하고 토론과 리뷰를 충분히 거치고, 속도가 더 중요한 작업은 그 과정을 줄여 빠르게 갑니다.

깊이 들어갈수록 결과물의 질이 더 올라갑니다. 더 나은 방법이 있으면 제가 모르던 것까지 그 자리에서 배워 적용하므로, 처음부터 제가 알던 범위를 넘어선 결과가 나올 수 있습니다.

## 단계에 맞는 스킬 호출

각 단계는 그 단계에 맞는 하위 스킬을 불러오고, 작업 종류(채용 과제, 실무, 개인 프로젝트)에 따라 기준 자료와 절차 일부가 갈립니다. 워크플로우 자체는 "언제 어떤 스킬을 불러올지"를 판단하는 지휘자 역할을 합니다.

## 만들고, 검사하고, 0건까지 고치는 공용 절차

화면 마크업을 만드는 작업과 로직을 구현하는 작업은 겉보기엔 다르지만 골격이 같습니다. "만들고 → 정답과 대조하고 → 틀린 게 0건이 될 때까지 고친다"는 뼈대를 공유합니다.

다른 것은 무엇을 정답으로 보느냐뿐입니다. 마크업의 정답은 디자인 원본(채용·실무는 피그마, 개인 프로젝트는 제가 만든 시안)이고, 로직의 정답은 실제로 동작하는지(테스트 통과)입니다.

그래서 이 반복 과정을 하나의 공용 절차로 빼고, 두 작업이 정답과 검사 기준만 바꿔 끼워 같이 씁니다.

이 절차는 여러 AI를 한 팀으로 묶어 돌립니다. Claude Code의 [Agent Teams](https://code.claude.com/docs/en/agent-teams) 기능으로, 만드는 역할과 검사하는 역할을 나눕니다.

- **만드는 역할**: 마크업을 작성하고 작업 기록(커밋)을 남깁니다.
- **정답 대조 역할**: 원본을 직접 열어 결과물이 원본대로 나왔는지 대조합니다.
- **코딩 규칙 검사 역할**: 정해 둔 코딩 규칙 문서를 직접 읽고 어긋난 곳을 찾습니다.
- **깊이 있는 품질 검사 역할**: 더 무거운 판단이 필요한 코드 품질을 살핍니다.
- **지휘 역할**: 사용자와 소통하고 검사 결과를 모읍니다.

원본과 비교해야 하는 경우(마크업, 도구 설정)에만 대조 역할을 붙이고, 로직처럼 테스트 실행 결과가 곧 판정인 경우는 지휘 역할이 직접 만듭니다. 만드는 역할을 따로 두는 것은 마크업뿐입니다.

만드는 역할이 작업 기록을 남기면 검사 역할이 살펴보고, 어긋난 점이 있으면 만든 역할에게 다시 돌려보냅니다.

## 설계 근거

### 만든 사람과 검사하는 사람을 나눈 이유

코드를 작성한 쪽이 직접 검사하면, 자기가 잡은 방향에 치우쳐서 문제를 놓치기 쉽습니다. 독립된 검사자가 처음 보는 시선으로 살펴야 실제 문제를 잡아냅니다.

### 검사자를 여러 명으로 나눈 이유

먼저 정확도입니다. 지켜야 할 코딩 규칙이 많아서 한 명이 전부 동시에 보면 놓치는 게 생깁니다. 종류별로 나누면 각자 맡은 부분에만 집중할 수 있습니다.

다음은 비용입니다. 검사자를 나눈 김에 일의 성격에 맞게 AI 모델도 다르게 배정했습니다. 기계적으로 대조하는 일은 가벼운 모델에, 깊은 판단이 필요한 검사는 무거운 모델에 맡깁니다.

### 0건까지 반복하는 이유

리뷰에서 찾은 문제를 고친 뒤 다시 확인하면 여전히 문제가 남아 있는 경우가 있어, 0건이 나올 때까지 검사와 수정을 되풀이합니다.

### 검사 기준은 항상 원본

검사할 때 기준으로 삼는 것은 언제나 원본입니다. 코딩 규칙도 규칙 문서 그 자체를 기준으로 삼습니다.

AI가 중간에 만들어 둔 정리본은 만들 때 빠뜨린 부분이 있을 수 있고, 그것을 기준으로 삼으면 검사자도 같은 빠뜨림을 못 보고 지나칩니다.

정리본은 원본을 빠르게 찾기 위한 메모로만 씁니다.

## 세션 라인업

작업을 여러 세션으로 나눠 각각 별도의 맥락에서 진행합니다. 다음에 열 세션은 AI가 안내합니다(FINALIZE는 제가 직접 엽니다).

- **BG** (배경 파악과 PR 확정): 기획서, 피그마, 채용 원본을 읽고 무엇을 왜 해야 하는지 정리합니다. 모든 작업의 출발점입니다.
  - **읽어나가면서 "이건 더 안 봐도 정할 수 있다" 싶은 PR부터 하나씩 확정**하고, 확정할 때마다 그 PR의 설계 세션을 안내합니다.
- **MARKUP** (화면 마크업): 시안을 페이지, 구역, 작은 부품 단위로 잘라 마크업 화면을 만들고, 원본과 0건까지 대조해 검증합니다.
  - 검증을 마친 마크업은 각 PR이 그대로 가져다 씁니다. 여러 화면에 반복해서 나오는 부품은 전 화면을 훑는 이 세션이 공통 부품으로 정해 따로 내놓고, 그 결과는 공통 부품 PR이 가져다 씁니다.
  - 시간이 오래 걸리는 작업이라 따로 떼어 일찍 시작하되, AI는 이미 있는 코드 스타일을 따라 만들므로 코드 스타일 기준이 선 뒤에 출발합니다 — 기초 다지기 PR이 있으면 그 PR의 마무리 점검 뒤, 없으면 저장소를 확보한 직후입니다.
- **PR_{N}_PLAN** (PR 설계와 뼈대): 그 PR이 무엇을 하는지 정의하고 구현 방침을 정합니다.
  - 정한 것을 코드 뼈대로 커밋하고, 속을 채우는 일은 다음 구현 세션에 넘깁니다. 뼈대와 구현 계획은 사용자가 승인해야 세션이 끝납니다.
  - **이 PR에 의존하는 다른 PR**은 승인된 뼈대를 딛고 바로 출발하므로, 의존하는 쪽 PR의 설계와 이번 PR의 구현이 동시에 굴러갑니다. 의존하는 PR이 바로 다음 번호일 필요는 없고, 여럿일 수도 있습니다.
  - 코드 스타일 기준을 세우는 기초 다지기(FOUNDATION PR — 채용 과제는 폴더 구조와 코딩 규칙 정리, 새 개인 프로젝트는 첫 셋업)도 한 PR로 이 흐름을 탑니다.
  - 채용 과제는 코드를 자동으로 검사하고 배포용으로 묶는 도구 설정을 별개 PR로 두고, 폴더 구조에 의존하는 설정이 없으면 기초 다지기와 동시에 출발할 수 있습니다. 새 개인 프로젝트는 이 설정이 기초 다지기 안에 들어갑니다.
- **PR_{N}_IMPL** (구현과 마무리 점검): 설계 세션이 넘긴 뼈대의 속을 채우고, 리뷰·동작 테스트·커밋 정리까지 마칩니다.
- **FINALIZE** (마무리 정리): 모든 PR의 구현이 끝난 뒤 마지막에 한 번 돌립니다.
  - 그동안 쌓인 커밋 기록에서 엉뚱한 PR에 섞여 들어간 것을 제자리로 되돌리고, 각 커밋에 붙은 설명을 리뷰어나 채용담당자가 읽어도 알아볼 수 있는 말로 다시 씁니다.
  - 실무·개인은 합치는 순서를 안내하고 끝나고, 채용 과제는 같은 세션에서 제출까지 이어갑니다.

아래는 큰 흐름입니다. 옆으로 갈라지는 가지는 동시에 진행되는 작업입니다.

```
BG
  │
  ├──→ MARKUP (기초 다지기 PR이 있으면 그 PR의 마무리 점검 뒤)
  │       └─ 공통 부품 확정 → 공통 부품 PR의 PLAN 출발
  ▼
PLAN
  │
  ├──→ 이 PR에 의존하는 PR의 PLAN
  │
  ▼
IMPL
  │
  ▼
FINALIZE
```
