# Design

## 목적

작업 중인 레포의 화면 디자인과 마크업을 claude.ai/code에 맡기고, 기능 개발(데이터·로직)에 들어가기 전에 디자인 QA까지 마친 결과를 사용자에게 준다. 개발을 다 끝낸 뒤 QA를 받으면 지적이 쏟아지기 때문이다.

## 디자인을 코드로 받는 이유

피그마가 없어서 디자인을 그 레포의 코드로 받는다. 웹은 그 레포의 컴포넌트·토큰 위에서 작업하고, 사용자는 그 코드를 로컬에서 띄운 화면을 본다. 그래서 디자인과 배포될 화면이 어긋나지 않는다. 레포 밖에서 그린 시안(claude.ai 채팅의 HTML 미리보기 등)은 실제 컴포넌트와 치수가 달라져 이 보장이 깨지므로 사용하지 않는다.

## 맡는 쪽

| 이름 | 무엇 |
|---|---|
| CLI | 이 스킬을 돌리는 이 세션. 세션을 열고, 말을 나르고, QA를 돌리고, 결과를 보고한다 |
| 웹 | 디자인·마크업을 하는 claude.ai/code 세션. CLI가 크롬 탭으로 조작한다 |
| QA 디자이너 | CLI가 `name: "qa-designer"`로 띄우는 팀원. 웹이 받은 지시와 구현 사정을 모르는 사용자의 눈으로 화면을 본다 |

qa-designer에게 답을 받아야 하는 전송(Agent로 띄우기, 다시 보게 하기, 의견 묻기)에는 답을 SendMessage로 to: main에 보내라고 붙이고, 답이 올 때까지 턴을 끝내지 않는다. 알리기만 하는 전송(7의 사용자 결정)에는 붙이지 않는다.

코드는 웹만 고친다. 웹이 만든 `claude/...` 브랜치 하나를 끝까지 같이 사용한다.

CLI는 웹과 사용자 사이의 말을 그대로 넘긴다. 6에서 웹에 보내는 지적·답은 CLI가 쓴다.

## 1. 사전 확정

AskUserQuestion으로 사용자에게 확정받는다. 웹의 디자인과 QA 디자이너의 검수가 같은 기준을 봐야 해서 CLI가 묻는다.

- 시작 브랜치: 기본값은 CLI가 작업 중인 레포에서 지금 체크아웃된 브랜치. 웹은 GitHub에 푸시된 것만 보므로, 그 브랜치가 원격에 없거나 원격보다 앞선 커밋이 있으면 푸시할지 함께 묻는다. 커밋하지 않은 변경은 웹이 못 본다고 알리기만 한다
- 지원 범위: 기본값은 PC 1440×900, 태블릿 820×1000, 휴대폰 384×832
- 기존 페이지를 고치면: 고칠 라우트·파일, 바꿀 부분과 건드리지 말 부분, 그 페이지의 기존 QA 자료(정한 것·기각한 지적)

## 2. 세션 열기

크롬 조작은 [chrome.md](chrome.md)를 따른다. `https://claude.ai/code`를 새 탭으로 열고, 입력창 아래 칩에서 아래처럼 맞춘다. 칩을 맞추지 못하면 멈추고 사용자에게 화면 상태를 알린다.

- 환경: `Default`(네트워크 액세스 전체)
- 저장소: CLI가 작업 중인 레포(`git remote get-url origin`의 GitHub `owner/name`)
- 브랜치: 1에서 정한 시작 브랜치
- 모델: 선택할 수 있는 가장 상위 Opus

## 3. 킥오프

사용자가 요청한 내용, 1에서 정한 것, [edge-cases.md](../workflow/requirement-review/planning/checklist/edge-cases.md) 원문, [kickoff.md](kickoff.md)의 킥오프 문단을 붙여 보낸다.

## 4. 응답 읽기

웹에 보낸 뒤에는 턴을 끝내지 않고 응답이 끝날 때까지 같은 턴에서 기다린다. 웹은 끝나도 CLI를 깨우지 않는다. 진행 상황을 알릴 때는 다음 대기 호출과 같은 응답에 붙인다. 글만 내고 응답을 끝내면 그대로 멈춘다. [chrome.md](chrome.md) "응답이 끝났는지 판단"의 대기 상한을 넘기면 화면 상태를 알리고 더 기다릴지 묻는다.

응답이 끝나면(7의 PR 요청은 빼고) 마지막 응답의 첫 줄로 다음 행동을 정한다.

- `[질문]`: 6에 들어가기 전(처음 5를 통과하기 전)이면 선택지째 AskUserQuestion으로 사용자에게 보이고, 받은 답은 질문 번호를 붙여 웹에 보낸다.
  6에 들어간 뒤면 사용자가 정한 것과 QA 디자이너 의견(있으면 SendMessage로 `to: "qa-designer"`에게 묻는다)으로 답하고, 그것으로 답할 수 없을 때만 사용자에게 묻는다.
- `[완료]`: 5로 간다.
- 표시가 없으면: 6에 들어간 뒤이고 에러가 아니면 `[완료]` 형식으로 다시 보고해 달라고 하고 4로 돌아간다(같은 응답에 한 번만). 그 밖에는 마지막 응답을 사용자에게 전하고, 사용자의 답을 웹에 보낸다.

## 5. 완료 보고 확인

`[완료]`에 킥오프 문단의 [완료 보고] 항목이 다 있는지 본다. 빠졌으면 웹에 한 번 다시 달라고 하고 4로 돌아간다. 그래도 빠지면 사용자에게 알린다. 다 있으면 6-1로 간다.

## 6. 디자인 QA

채택·기각은 CLI와 QA 디자이너가 정한다.

- **6-1** 웹의 브랜치를 로컬 빌드로 띄운다. 미리보기 링크는 실제 동작과 다를 수 있다.
  - 사용자의 작업 트리를 바꾸지 않게, 원격을 fetch한 뒤 그 레포의 `.claude/worktrees/` 아래에 `git worktree`로 받는다. 설치·빌드·실행은 포트까지 `[완료]`의 "로컬 실행 방법"대로 한다
  - 두 번째부터는 앞서 띄운 서버를 끄고 작업 트리를 그 브랜치의 원격 끝으로 맞춘다
  - 빌드가 실패하면 에러 원문을 웹에 보내고 4로 간다. 이것은 수정 왕복 횟수에 넣지 않고, 연속 3회 실패하면 멈추고 사용자에게 에러를 보고한다. 웹이 고칠 수 없는 로컬 전용 사정으로 실패하면 웹에 보내지 않고 사용자에게 알린다
- **6-2** QA 디자이너가 이미 있으면 SendMessage로 `to: "qa-designer"`에게 이번 `[완료]`의 화면 주소와 반영을 요청한 지적을 보내 다시 보게 하고 6-3으로 간다. 자기 지적과 기각을 기억하게 하려는 것이다.
  없으면 Agent 호출에 `name: "qa-designer"`를 붙여 띄운다. 화면을 보고 디자인을 판단하는 일이라 `model`에 CLI와 같은 모델을 지정하고, 띄울 때 사용자에게 모델과 그 이유를 한 줄로 알린다. 넘길 것:
  - 요청 원문, 지원 범위, `[완료]`의 "정한 것"에 있는 화면 목적·핵심 행동
  - 그 레포가 사용하는 디자인 시스템의 문서 링크와 토큰 **값**. MP(`@developer-choi/design-system`)면 kickoff.md 고정 스펙의 MP Storybook 주소와 6-1 작업 트리의 `node_modules/@developer-choi/design-system/dist/design-system.css` 값
  - QA할 화면의 로컬 주소, 정한 것과 일부러 이렇게 한 것("다시 제안하지 말 것")
  - 이번 QA는 구현 전 디자인 단계라는 것: 레포·코드가 아니라 화면만 근거로 보고, 킥오프 고정 스펙이 웹에 뺀 범위를 풀어 넘기고 그 범위는 지적하지 않는다. 웹이 레포 규칙을 따라 바꾼 것은 `[완료]`의 "정한 것"을 기준으로 본다
  - [chrome.md](chrome.md)의 "숨은 탭"·"휴대폰 폭" 두 항목을 풀어 쓴 것, "자기가 연 탭만 사용할 것"
  - 답 형식(화면·위치·문제·제안, 짧게)
- **6-3** QA 디자이너가 Claude in Chrome으로 화면 × 지원 폭마다 직접 클릭하며 보고 지적 목록을 보낸다.
- **6-4** CLI가 지적을 코드, 사용자가 정한 것과 대조해 채택·기각을 정한다.
  - 틀린 전제는 사실을 넘겨 한 번 다시 묻는다
  - 그래도 갈리면 QA 디자이너 판단을 따른다. 사용자가 정한 것과 부딪히면 사용자 결정을 따른다
- **6-5** 채택이 없거나 수정을 이미 5회 보냈으면 7로 간다(남은 채택은 미반영 지적). 그 밖에는 CLI가 채택한 지적을 정리해 웹에 보내 같은 브랜치에 푸시하게 하고 4로 간다. 웹에 수정을 보낸 것을 1회로 센다.

## 7. 보고와 마무리

사용자에게 아래를 보고한다. 약칭·대명사 대신 화면·버튼 이름을 사용하고, 반영한 지적은 QA 전/반영 후를 나란히 놓는다.

- QA할 화면(라우트·쿼리 조합)마다 6-1에서 띄운 클릭할 수 있는 로컬 주소
- 반영한 지적
- 기각한 지적과 이유: 사용자가 뒤집을 수 있게
- 미반영 지적
- 디자인 시스템에 추가할 것
- 다음에 선택할 것: 더 지적하기, PR 승인, 마치기

사용자가 기각을 뒤집거나 새로 지적하면 사용자 결정이라고 밝혀 6-5로 보내고, 5회 제한은 새로 센다. qa-designer에게도 "사용자 결정, 다시 지적하지 말 것"으로 알린다.

사용자가 PR을 승인하면 웹에 "사용자가 PR을 승인했어. PR 올려 줘"를 보내고, 응답이 끝나면 PR 링크든 아니든 그대로 사용자에게 전한다. 사용자가 마쳤다고 하면 연 탭, 로컬 서버, 6-1의 작업 트리, qa-designer를 정리한다. 웹이 푸시한 `claude/...` 원격 브랜치는 사용자가 정한다.
