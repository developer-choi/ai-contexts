# 벤치·eval

## 목적

벤치·eval을 돌려 스킬·규칙의 효과를 검증하거나, 어떤 작업을 Gemini에 넘겨도 되는지 판단한다.

## 흐름

벤치는 종류 선택 → 설계 → 실행 → 측정 → 채점 → 기록·정리 순으로 간다. 선택한 종류 파일은 처음에 통째로 읽고, 아래 공통 절차와 함께 따른다.

**`scripts/`의 `.mjs`는 소스를 읽지 않고 실행한다.** 명령·인자는 같은 폴더의 같은 이름 `.md`를 본다.

### 종류 선택: 무엇을 확인하러 왔나

| 확인할 것 | 종류 파일 |
|---|---|
| 스킬이 설계대로 도는가(기능테스트) | [kinds/function-test.md](kinds/function-test.md) |
| description이 정확히 트리거되는가 | [kinds/trigger-eval.md](kinds/trigger-eval.md) |
| 규칙 문장을 넣고 뺀 효과 | [kinds/rule-ablation.md](kinds/rule-ablation.md) |
| 이름 있는 팀원을 띄우는 스킬 | [kinds/delegation.md](kinds/delegation.md) |
| 이 작업을 Gemini에 넘겨도 되는가(모델 간 비교) | [kinds/gemini-handoff.md](kinds/gemini-handoff.md) |

### 설계

- **앞선 측정부터 찾는다.** 종류 파일이 앞선 측정을 찾을 자리를 정해 두었으면, 같은 대상을 이미 측정했는지 그 자리에서 먼저 찾는다. 있으면 그 결론과 한계를 먼저 읽고, 이번에 새로 판단할 것을 정한다.
- **정답이 정해지는 과제면 정답은 1차 소스로 확정한다.** 스킬을 측정하는 벤치면 스킬 본문에 적힌 요약을 정답으로 삼지 않는다.
  그 요약이 원본과 어긋나 있을 가능성이 바로 벤치가 잡을 대상이라, 그걸 정답으로 삼으면 처음부터 측정하지 못한다.
  스킬이 "저쪽이 단일 출처"라고 위임하고 있으면 그 문서를 열고, 위임 대상이 또 다른 원본(마커·용어 정의 등)을 가리키면 거기까지 따라간다.
- **피실험 쪽이 정답을 볼 수 없게 한다.** 정답이나 앞 회차 채점 기록을 읽을 수 있으면, 실력으로 맞힌 것인지 답을 보고 맞힌 것인지 판단할 수 없다.
  - 피실험 쪽은 git 기록도 열어 보고, 주는 폴더에 벤치 기록이 있으면 지난 벤치의 정답을 읽는다
  - 린터처럼 고칠 내용까지 출력하는 도구를 주는 것도 정답을 보여 주는 것과 같다
  - 정답이 대상 파일·cwd에 이미 들어 있으면 "읽고 확인"만으로 통과한다. 정답이 들어 있지 않은(빈·오답) 대상으로 시나리오를 구성한다

### 실행

- **시나리오마다 벤치를 설계한 세션이 아닌 새 세션에서 실행한다.** 한 세션에서 같은 팀·작업자를 여러 시나리오에 걸쳐 재사용하면 앞 시나리오의 맥락이 섞인다. 서브에이전트·`claude -p`처럼 설계 세션의 대화를 물려받지 않는 실행은 새 세션으로 친다. 메인이 직접 돌리는 종류(delegation)면 그 시나리오용으로 새로 연 세션이 메인이다.
- **실행 전에 실제 레포의 `git status`를 적어 둔다.** 아래 시나리오마다 하는 점검의 비교 기준이다. 재벤치는 대개 대상 문서를 고친 채 돌아 레포가 처음부터 비어 있지 않다.
- **실제로 받은 입력과 읽은 문서는 회차마다 로그로 확인한다.** 입력이 일부만 전달돼도 응답은 그럴듯하게 나와서, 산출물만 보면 입력을 못 받은 것인지 받고도 안 따른 것인지 알 수 없다. 스킬이 읽으라고 한 문서를 실제로 열었는지도 로그의 도구 호출로 본다.
  - Claude Code: `~/.claude/projects/<인코딩된 경로>/<세션 id>.jsonl`, 서브에이전트는 `<세션 id>/subagents/agent-<id>.jsonl`
  - Antigravity CLI(`agy`): `~/.gemini/antigravity-cli/conversations/`의 SQLite
  - `bench-trigger.mjs`: 세션 로그를 남기지 않는다. `BENCH_DUMP_DIR`로 남긴 stream-json을 본다
  - `bench-ablation.mjs`: 세션 로그도 도구 호출도 남기지 않는다. 받은 입력은 stderr의 `주입 <비교군>:` 줄의 글자 수·작업 폴더가 eval-set의 비교군 텍스트·`variant_cwds`와 맞는지로 보고, 파일을 열었는지는 `--dump-dir` run 파일의 응답이 그 파일 내용을 담고 있는지로만 가늠한다
  - ask-llm: 로그를 남기지 않는다. 표준입력(`-`)이 아니라 파일로 보내고 회차마다 남겨 둔다. 그 파일이 곧 받은 입력이다
- **시나리오마다 끝난 직후 실제 레포의 `git status`를 실행 전과 대조한다.** 피실험 쪽은 지시와 달리 레포에 파일을 만들거나 `git add`까지 할 수 있다. 실행 전에 없던 파일·staging만, 다음 시나리오를 돌리기 전에 정리한다.
  - 트리거 eval은 로컬 스킬이면 레포 안에서 돌 수밖에 없다. 트리거되지 않은 액션형 쿼리가 `claude -p`로 본문 작업까지 수행한 일이 있다(early-kill은 트리거됐을 때만 끊는다).

### 기록·정리

- 벤치를 끝내고 마지막 결과를 보고한 직후, 묻지 않고 벤치가 남긴 것을 전부 지운다. 종류 파일이 남기라고 정한 기록·재료는 지우지 않는다.
- 측정용 워크트리만은 그 보고에 대한 검증·리뷰가 끝난 뒤 지운다. 먼저 지우면 리뷰가 확인할 대상이 없어진다.

## 재벤치: 언제 다시 돌리고 언제 멈추나

문서를 고쳐 다시 측정할 때, 아래 둘 중 하나에 닿으면 멈춘다. 고치기 전 측정은 회차로 세지 않고, 첫 수정 뒤 측정이 1회차다.

- 2회 연속 뚜렷한 성과가 없다. 중간에 성과가 한 번 나면 연속은 처음부터 다시 센다.
- 고치고 다시 측정한 회차가 5회에 닿았다. 성과와 상관없다.

성과는 직전 측정보다 기대와 어긋난 결과가 뚜렷이 줄었는가로 본다. 같은 문서로 돌려도 LLM 결과는 조금씩 오르내리므로, 그 정도 차이는 성과로 보지 않는다.

스크립트 출력의 판정 열에 실행 실패로 `보류`가 찍힌 행은 그 행을 다시 측정해 채운 뒤 판정한다.

## 모델

측정 모델은 측정 대상 스킬·규칙이 실제로 쓰이는 환경의 모델에 맞추고, 다르면 결과 보고에 적는다. 벤치가 띄우는 팀원·서브에이전트의 모델은 [에이전트 나누기](../../contexts/prompt-standards/skill-structure.md#에이전트-설계)대로 선택한다.
